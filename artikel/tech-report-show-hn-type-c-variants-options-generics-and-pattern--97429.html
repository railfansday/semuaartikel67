In a recent development, type-C is C11 with the types C is missing: variants that match checks, distinct types for ids and units, generic types, and errors as values with try and defer. Its compiler, typec, takes the command line of cc, turns Type-C into C that you can read, and hands that C to your C compiler. A C11 file is already a Type-C file, so a program adopts it one file at a time.

Type-C is early: every example on this page works today, and the rest of the language is designed but not built yet (Status).

It has been revealed that option(T) is a generic variant that every Type-C file has: None, or Some of a value. It replaces the -1 or NULL that means "not found", which a caller can forget to test:.

result(T, E) is another generic variant that every Type-C file has: Ok of a value, or Err of an error, which can be a variant with fields of its own. try gives the value of a result, or returns its error from the function at once:.

A call that drops a result, as a statement of its own, is an error:.

C drops a return code without a word unless its function is declared [[nodiscard]] (C23) or warn_unused_result, and then it warns.

C releases resources at one label that each error path must jump to; here an error path written later returns past it:.

A defer, written on the line after an acquisition, releases the resource at every exit after it: each exit runs the deferred statements in force there, in reverse order, so the return in the loop closes both files. A deferred statement cannot report an error, so the function flushes out itself before its last exit:.

Sources indicate that typec writes a copy of each deferred statement at each exit (What the C looks like). An analyzer finds some leaks of C by following paths: GCC's -fanalyzer reports both of copy.c, in either order.

A match with a default covers a upcoming case as C's default does; but a default that covers no case is refused, so one cannot be written "just in case" before the case exists. A value whose tag is none of its cases, which C code, casts and unions can make, stops the program when it is matched, at run time. private binds Type-C files only: C code reads and writes the layout as C does, the zero value is open to every file, and Type-C code that reinterprets storage, as *(port *)p does, is not refused. The guarantees and what each depends on are in design 14.

A C11 translation unit is a Type-C unit with the same meaning (design 2.2): each Type-C construct begins with tokens that C refuses, and the words Type-C adds, such as type, match and result, stay free for C's identifiers (design 2.3). So a file renamed to .tc compiles before any Type-C is written in it, and while it uses no Type-C construct, typec hands the C compiler its preprocessed text byte for byte: the object equals the one that the C compiler builds from that same preprocessed text with the same options (test/run/pipeline.t). In a recent development, the code that you write in Type-C compiles to plain C (What the C looks like). Of the code that the compiler adds without the source spelling it out, the traps of matching, the cleanups of defer and slice bounds checks are built; checked mode will add the rest (principle 4). The rest of a program links as before: Type-C functions are C functions under their own names, with no mangling, and typec adds no library to the link (design 10.4). Sources indicate that typec writes plain C11 with the GNU extensions that GCC and Clang share, and --emit-c prints it. A variant is a structure of an enumeration, its tag, and a union of one structure for each case that has fields. The enumeration ends with a hidden enumerator of the value INT_MAX, so the tag has the size of int with or without -fshort-enums. A match is a switch on the tag that copies the fields an arm binds into const locals, and traps after each arm and in the default that it adds for a tag that is none of the cases, beside the case of the hidden enumerator. A C switch on a tag needs a default too, or -Wswitch reports that enumerator. A distinct type is a typedef of the type it is made from, and an instance of a generic type is a structure named after its arguments, as list__i is list(int). C code and Type-C code call each other with no glue. C text that uses no Type-C construct is written out as it was read.

Pilot B, the plan's test of Stage 2 on real code (plan, Stage 2), rewrote the parser of tomlc99, a TOML library in C (toml.c, 2392 lines), with result, try and defer. Its header toml.h, its C programs and its tests did not change and link against the Type-C object. The pilot's repository is not published; the numbers here are from its record.

Fault injection fails each allocation of a parse in turn, one run for each. Over the library's 62 example files, 1416 runs, the original went wrong in 34: 25 leaks and 9 uses after free, from two defects in the code that grows an array or a table. The rewrite went wrong in none, built by Clang or GCC, and the address, undefined behavior and leak sanitizers reported nothing. Over the 146 files of toml-spec-tests, 18847 runs, the original leaked in 1022, 1000 of them in one deeply nested file, and crashed in 9; the rewrite did neither.

try and defer did not remove the defects by themselves. A variant of the rewrite whose three faulty functions only put a try in place of each if (!x) return kept all 34 bad runs. Adding a defer that frees each new object until it is linked into the tree removed the 25 leaks but not the 9 uses after free, which came from the order of the steps: the old buffer of an array was freed before its new element existed. Reordering the steps, so that each grown buffer is stored and counted before the next allocation, removed them. The language puts the question "who owns this object if this step fails?" at every try; the rewrite had to answer it.

One line each on the principles of design section 1, which states them in full:.

...turn on more warnings, or run an analyzer? Use them: Type-C code still gets the warnings of the C compiler. Warnings see only the forms they were written for, and no flag that comparison.t tries catches a read of the wrong member, swapped ids or a value made outside its module. An analyzer finds what the paths it explores reach. In Type-C these mistakes are type errors that every build checks, with no extra tool.

Industry observers note that ...use Rust, Zig or OCaml? All three have tagged unions whose matches are checked for missing cases, and generic types, and safe Rust and OCaml are memory safe, which Type-C is not (design 14). All three call C, but C code gains their checks only when it is rewritten in their language, and the build gains their toolchain and a boundary between the languages: Rust reads C's declarations through extern "C" blocks, written by hand or generated by bindgen, Zig translates C headers into Zig, and OCaml calls C through stubs written against its runtime, which brings a garbage collector. typec is a tool to add too, but in Type-C the checks start in the one file you rename. It includes the same headers as they are, is compiled by the same C compiler, and gives an object with the C ABI, which links with the rest as before (Adopting one file).

...use C++? std::variant, enum class and templates do much of this, in another language. A C file is not always a C++ file (int *p = malloc(n); is an error in C++), C++ reaches C functions through extern "C" declarations, and C++ brings exceptions and a runtime library to link. A C file stays valid Type-C, and typec writes C.

Sources indicate that ...write macros? A macro that writes struct { T *data; ... } makes a new type at each use, so the VECTOR(int) of one declaration does not pass where another VECTOR(int) is wanted, and C refuses the call. The usual fix declares each instance once by name, by hand. A generic type such as vector(int) is one type wherever it is written. A macro cannot check a switch either.

Type-C 1.0 is the core language, frozen: variants, match, if (case ...) and nested patterns, distinct types, private and interface files (.tci), generic types and functions, option and result, try and defer, and slices with checked indexing and str. typec --emit-c-header writes the C header of an interface for C clients. The design specifies the whole language, and the strategy built it in stages, each ending in a measured gate, and the three pilots build with this release (Measured on a real library).

The test suite passes with Clang and with GCC on macOS, x86-64 and arm64, and on Linux, with glibc on x86-64 and with musl on x86-64 and arm64 (Building and testing).

Designed and not yet implemented: a checked mode, whose rules are provisional, that rules out specific classes of memory errors in the functions it covers (Stage 5 of the initiative).

Recent findings suggest that the backend is the program named by the last --cc=PATH option, else by the TYPEC_CC environment variable when it is set and not empty, else cc. A name without a slash is looked up in PATH. typec consumes --cc=, --print-target, --emit-c, --emit-c-header, --stats, --trap-function= and --version where an option can stand (the value of -o is never one) and forwards every other argument, --cc without = included, in its original order. The backend is run with an argument vector, never through a shell, so TYPEC_CC names one program: it cannot carry extra arguments such as ccache gcc.

According to recent reports, A backend that runs typec again, such as a cc first on PATH that is typec itself, is refused: typec sets TYPEC_OUTER_CC to the backend's name in the environment of every backend it runs, and a typec that starts with it set exits with 81 after one message naming that backend. The whole process tree of the backend inherits the mark, so a typec that a wrapper backend runs on purpose is refused too. To install typec as cc, set TYPEC_CC to the path of the real C compiler.

Recent findings suggest that the backend is GCC or Clang, Apple's included, no older than the releases that minimum_major_version in src/sema/target.ml names. typec refuses an older one with a message naming the oldest supported releases.

Without a .tc input typec replaces itself with the backend. Exit status: the backend's own; a backend ended by a signal ends typec with the same signal. typec exits with 81 when --cc= has no path, --trap-function= names no C identifier or one reserved to typec, the backend cannot be started or the backend runs typec again, after one message on stderr (with --print-target, a second notes that the backend gave no target model).

typec's own failures have statuses of their own, which src/driver/exit_status.ml defines and design 13.2 explains: 80 when it refuses the program (a diagnostic about the source), 81 for an error of its environment (the command line, the backend, a file it cannot read or write) and 82 for an internal error, a bug in typec. Every other status is the backend's.

An input whose name ends in .tc, with no -x other than -x none before it, goes through three steps:.

On Clang, steps 1 and 3 also get -Wno-unused-command-line-argument before OPTIONS, so that Clang does not warn about an option of the command line that the step does not use. GCC does not know the option, so its steps go without it. The query for the target model runs before the backend is known and gets it on both.

Industry observers note that -std=gnu17 is left out when the command line gives -std= for C11 or C17 (c11, c17, c18, gnu11, gnu17, gnu18, c1x, gnu1x, iso9899:2011, iso9899:2017, iso9899:2018); any other -std= is a usage error. Step 2 reads asm and typeof as keywords in the GNU forms and as identifiers in the ISO forms, as GCC and Clang do; -fasm and -fno-asm select the GNU and the ISO keywords whatever -std= notes. The options of step 1 are those that matter to preprocessing and to code generation, those of step 3 the latter only; src/driver/cc_option.ml is the one table that tells them apart and says which options take a separate value. The output is named as cc names it: after -o, else after the input in the current directory. When the command line links and has no input but .tc ones, step 3 is the final command: the backend compiles and links the command line with each .tc input replaced by -x cpp-output EMITTED, where EMITTED is named as the input with the suffix .c, in a directory of its own. The backend thus leaves what it leaves for a one-step build of C sources, named as there: on macOS the .dSYM bundle of -g, and the files of -gsplit-dwarf, -fstack-usage and -fcallgraph-info. When the command line links with other inputs, each .tc input becomes an object in the temporary directory and the backend links the command line with those objects in place of the .tc inputs, and the side outputs of step 3 are lost with the objects; without linking, the other inputs are compiled by one more backend command without the .tc inputs. A .c input is thus compiled exactly as without typec.

In a recent development, with -MD or -MMD the dependency file comes from step 1, named as cc names it: after -MF, else after -o with the suffix .d, else after the input; its target is the -MT or -MQ value, else the real output. With -M or -MM the command line compiles nothing: step 1 of each .tc input prints its rule in place of the preprocessed text, to the -o file or stdout, and one more backend command gets the command line without the .tc inputs, when other inputs remain, to print theirs.

--emit-c stops after step 2 and writes the C to the -o file, or to stdout; the command line then has exactly one input, a .tc file.

In a recent development, --trap-function=NAME makes every trap of the emitted C (a corrupted tag, a slice index out of range) call _Noreturn void NAME(void), which the program supplies, instead of executing __builtin_trap() alone; a freestanding program uses it to report the failure (design 10.5). NAME is a C identifier of ASCII letters, digits and underscores outside the names reserved to typec, which begin with __tc_, and the last --trap-function= wins. NAME is the name the program defines, not a macro: the emitted C is already preprocessed, so -DNAME=... does not change it. A .tc unit that holds a Type-C construct declares NAME after its own text, so a declaration of NAME in the program with another type is a backend error reported at typec's text ().

In a recent development, --stats prints on stderr, for each .tc input and for the .tci input of --emit-c-header, one line typec: stats: FILE: and the fields unit_bytes (the preprocessed unit), instance_bytes (charged to the instance budget), copy_bytes (the front end's charge to the output limit for the copies of deferred statements, which output_bytes counts again), output_bytes (charged to the output limit by lowering, the unit's own text included, and for a header then every byte of the header, its macro brackets and macro probe among them), output_limit, longest_instance_code (the most bytes of the code of one instance, its generic's name and the encodings of its arguments, that the bound on encodings holds) and longest_name (of a type declaration or a generic function, the universe text included), each as name=value: the counts of design 3.5 rule 7 that the measurements of P30 read. Then come the slice tests of the unit and of each instance that it uses, which the measurements of P28 read: slice_indexes, slice_subs and slice_conversions (those that C evaluates, which lowering writes with a test), slice_untested (those that C does not evaluate) and slice_late_calls (the tested indexes and slice_subs with a call or a statement expression in an operand after the first). Last come the most steps (selection_steps), nodes (selection_nodes) and nodes on one path (selection_depth) that building the selection tree of one match or test of the unit or of an instance took, which the measurements of P32 read, each the most over all of them. The holders of a try of the unit and of each instance come last, which the measurements of P33 to P35 read: try_holders (the holders), try_tries (their try expressions), try_first_operands (the hoisted operands that are the first operand of &&, || or a conditional operator or the left operand of a comma), try_conditioned (the hoisted operands under a condition) and try_multiple (the holders with more than one hoisted operand). A unit that typec refuses reports none.

A .tc input refuses the option that stops the backend at preprocessing (-E), the options that change the preprocessed text (-P, -C, -CC, -fuse-line-directives, -traditional-cpp, -fdirectives-only), every -d option of dumps (-dD, -dM, -dI and the like), alone or passed on by -Wp,, -Xpreprocessor or -Xclang (which so refuses Clang's -Xclang -disable-O0-optnone too), -save-temps, -###, -ansi, --, the options that name a file of further options (response files, @FILE, -specs= and --config=) and the queries that print a fact of the backend (-print-file-name= and every other -print- option, -dumpmachine), with a usage error naming the option. It refuses a long option, spelled with --, that it does not know, as GCC reads --NAME as -fNAME and accepts abbreviations, so that --preprocess, --write-user-dep or --short-enums cannot reach the backend unseen; an option that also has a form with one - passes in that form. It refuses the options known to change a type of C without changing a macro that the target model reads, which the model therefore cannot see: -funsigned-bitfields or -fno-signed-bitfields, and -fsingle-precision-constant, even when a later option undoes them. -fshort-enums passes: the target query learns the enumeration representation by its probe compiles (Printing the target model). Other routes to these types, such as a config file, a wrapper or a target whose default differs, fail in step 3: the C of a unit with a Type-C construct ends, after a line marker for with flag 3, with a static assertion of each such type that typec assumes, whose message names the option that would break it; that of the enumeration rule also states the representation that typec expects. Flag 3 keeps the user's warning options off typec's own text. An option that changes a macro the model reads, such as -funsigned-char or -fshort-wchar, reaches the target model. It refuses -fpack-struct without a value, under which GCC ignores the #pragma pack lines that typec writes around an instance of a generic and warns of each; -fpack-struct=n passes. A unit that holds such lines also ends with a probe that fails where the backend reads #pragma pack() as a pop, as Clang does under -fapple-pragma-pack. It also refuses -arch options that name more than one architecture: cc builds a universal binary from them, but step 1 preprocesses for one architecture only. Build each architecture with its own -arch and join the results with lipo -create.

It has been revealed that A freestanding build passes -ffreestanding -nostdlib as for C. The objects need from the environment what the same C needs, such as memset, and nothing more: a trap is __builtin_trap(), an instruction on x86-64 and AArch64 (design 10.4).

According to recent reports, the temporary directory is made with mode 0700 in TMPDIR, or /tmp, and removed on every way out. SIGHUP, SIGINT, SIGPIPE, SIGQUIT and SIGTERM are passed on to the running backend; typec then removes the directory and ends by the same signal.

Exit status: 0 when every step succeeds; else the status of the first backend step that fails, or the signal that ended it; 80 when the reader or the front end refuses the preprocessed text; 81 for a usage error, when the backend cannot be started or gives no target model, or when a file cannot be read or written; 82 for an internal error.

typec --print-target [OPTIONS] runs the backend as BACKEND OPTIONS -dM -E -x c /dev/null and prints the target model that its predefined macros give: the backend and its major version, the sizes of the scalar types, the signedness of char, the types behind size_t and the other standard typedefs, the byte order and __STDC_VERSION__, one field: value per line, and last the enumeration representation, int-sized or short (as under -fshort-enums), which no macro states: typec learns it by two compiles of a probe, BACKEND OPTIONS -fsyntax-only -w -dumpdir DIR/ -x c -, each of which compiles under one representation alone. Whether the backend has __float128, among the optional floating types, comes from a third compile of the same form, since no macro indicates so on every target. The other arguments are the backend options that select the target or the dialect, such as -m32, -funsigned-char or -std=gnu17; inputs, -o and dependency options do not belong there.

Exit status: 0 with the model on stdout; 81 when the backend fails, cannot be started, is not supported or prints macros the model cannot be read from, when it compiles neither probe or both, or for a usage error; 82 for an internal error.

Industry observers note that typec --version runs BACKEND --version, passes on its output, then prints typec and its release on a last line, such as typec 1.0. A build tool that tells compilers apart by the output of $CC --version, such as Meson, or a script that reads its first line thus sees the backend. The rest of the command line does not reach the backend and nothing is compiled, as GCC and Clang compile nothing with their --version; an error in one of typec's own options, such as --cc= without a path, is still one. The status is the backend's, or 81 when it cannot be started, or 0 when SIGPIPE ended the backend and the reader of the output is gone, as a reader such as head -1 that stops early is no failure; a backend that fails or cannot be started is named on stderr, and typec's line is still printed. The release has one source, the version field of dune-project, which the build writes into typec; a release tag vX.Y is made after it is set.

docs/typec.1, in mdoc(7), is installed by dune install as man/man1/typec.1 under the prefix, or under the directory of --mandir. test/unit/test_manual.ml checks its lists of typec's options and exit statuses against the driver's tables, and mandoc -Tlint -Wwarning docs/typec.1 checks its markup.
