There is this cool idea: incremental computations. The concept is simple, if you calculated something and then inputs change, it doesn't have to mean that you need to recompute everything. Most of your computations might still be valid, and quite often it is the case that you only need to redo a small chunk of changes.

According to recent reports, this concept usually works the best when you need to compute a lot of stuff, and there are a lot of inputs, and these inputs change independently with different degree of likelihood. Probably, the most common example is incremental compilation, which makes the compilation reuse as much work as possible, making iterations during development much faster. The interesting part is "iterating": note that incremental compilation doesn't necessarily makes cold builds faster. The compiler performance might be roughly the same with and without incrementality, it's just repeated reuse of compiler artifacts becomes more efficient. Most likely you've heard of it. And if you did, you probably know that incremental compilation is not easy (1, 2, 3). But it's cool!

And if incremental computations concept applies well to compilers, it applies even better to LSP servers, because user makes edits in the editor much more often than they recompile code, and each keystroke must change the editor state in milliseconds (unless you go full vibe and don't need an IDE anymore, that is).

It has been revealed that it could be somewhat related to the fact that rust-analyzer uses salsa as the central part of its architecture. Salsa is a library that makes incremental computations very convenient and efficient. There is one drawback, though. It is mainly designed to work in memory. And we'll touch on how it works in a bit.

In a recent development, for project like Rust Glancer that tries to keep the memory usage as low as possible, this doesn't work. Because of that, for a long time Rust Glancer didn't use incremental computations, and instead had a sophisticated network of persistent caches with sharding and targeted optimizations to make computations efficient. And it worked, for a while. But this approach doesn't scale very well: if you need to maintain a manually implemented custom cache format, optimize it, and tie computations to it, then the more efficiency you seek, the more complexity you get. Basically, the complexity is "quadratic": it grows as O(computations_complexity * cache_implementation_complexity) because both are interconnected (sorry, CS purists, for this crime).

So... Rust Glancer got to a point where it would really benefit from persistent incremental computations. And the search for it turned out to be really interesting, so in this blog post we'll be discussing how incremental computations can work in memory and how to make this approach work with persistency.

And most importantly, we don't need to write any of this tracking code ourselves, Salsa gives it to us for free.

Imagine that each query, combined with its arguments, is an object. This object can have a bunch of metadata, stating whether it was already computed, when it happened, what was the output, and what's the object dependencies. Let's call this metadata a "memo".

Side note: why is "combined with its arguments?" notable? Because we cannot memoize is_haha_number, but we can memoize is_haha_number(420), so you can think of it as a mapping of (function, arguments) -> output.

And imagine that you have inputs: something that user provides, and this something can be explicitly requested by a query.

It has been revealed that we might also say that the database has a revision, initially 1. When you change some input, the revision gets bumped to 2, and so on. This revision can be used as "when it happened" (or rather, "when it change last time") inside of the memo.

Now, we've provided our inputs and invoke a query. It has some associated code that can internally do two things:.

Recent findings suggest that if query requests an input, it should record that it depends on this input. So if input changes, it must be recomputed.

In a recent development, if query requests another query, we might check if the corresponding query has a memo with a computed value. If it has, we need to make sure that it is valid for the revision we're at. If it is: great! It can be reused, and we don't need to recompute it. Otherwise, we need to recursively go into this query. Obviously, we also record a dependency on this query.

During the execution, we'll collect all the inputs and all the dependency queries, and ultimately we'll finally compute the result of our query. And when we do, we can fill out the memo: record the revision and the output.

And... done! Next time you request an output, we will look at this query object memo. If inputs did not change, we can just hand out the result. If they changed, we go down the query line, and do the same thing. So naturally only the things that actually might have changed will be recomputed.

Industry observers note that oh, but there is one more key detail here, that makes everything even better. If revision changed, it does not automatically mean that we need to recompute this query. We might recompute dependencies, and compare them to the old values. If all the outputs are the equal to the old ones (imagine that word_count(a) changed from 67 to 69, but is_haha_number still returns true true: the query that depends on is_haha_number might not get invalidated), we can just mark the current version as verified and return the old result. And it can matter a lot when the expensive query has a lot of cheap dependencies.

Obviously, it's an overly simplified explanation. In practice, there are many, many caveats, tricky parts, and optimizations that make the experience work well. But my job here is to give you an idea; if you've become interested in the topic, I'd recommend looking to Salsa source code, it's very interesting.

On a serious note, the main difference is the focus. When you start working on a project like that, choosing your priority can influence the design a lot. And the choice made here is being persistent-first. While Ajika provides an in-memory backend, it's mostly meant for tests. The intended use case is to use your disk.

And it starts with a very basic question that in-memory database does not have: what happens if I restart the application?

If you already have a cache locally, many things can make this cache invalid:.

Recent findings suggest that and similarly, given that we cache computations, it's basically an optimization. If cache gets corrupted or removed while the application is running, user would most likely prefer the cache to be discarded and computations to be repeated one more time, rather than the app crashing with "cache is not available, what do I do???".

As a result, the cache must be throw-away. Both Ajika and application supply schema versions to identify the revision, and if the stored cache doesn't match it, we reset it. If cache gets corrupted, Ajika will attempt recovery over hard failing, even if it means re-computing data from scratch.

In a recent development, the next most noticeable change is that most operations are fallible. Since IO is the basic property for us, and IO can fail, we need to think about it. Failed operation does not mean that cache is corrupted, but it does mean that the current query might not be computed. Typically, it can be retried, though.

Industry observers note that finally, the persistence is, unfortunately, a leaky abstraction. You cannot really hide from the fact that the data is outside of memory, because everything you persist must be serializable. And your interim query data might be reusable but not serializable (imagine an AST that borrows the source text: making it own the data likely will be worse), so some of the queries might be transient: we compute them once and retain while the current operation runs, but drop instead of persisting once operation ends.

Sources indicate that together, these properties start working rather nicely, however: your application has to be aware of persistence, but not in an annoying way. If something fails, you know about it, but you don't have to worry, since Ajika will repair things for you. If something is not serializable and it doesn't matter, it can be turned into a transient query. If you don't want your tests to rely on persistence, you just plug a memory backend in.

It has been revealed that database is an entrypoint. You choose either an in-memory or persistent backend, supply Inputs and then run your operation.

Queries are the actual logic we want to execute. They are defined via ajika::query macro and in general pretty straightforward. More details on queries themselves are in the book, and we'll look at how queries are executed and what this Db object is a bit later in this post.

Inputs are somewhat more interesting. Your input type is defined through the ajika::input procedural macro, which would do some wrapping for you. And your input structure is basically a mapping: you specify a key, for example, String, and then you can use database to get an input value (or lack thereof) for whatever key you have, be it "foo" or even "bar". If you have a singleton value, like a config, you can use () as a key. Again, more on inputs can be found in the book, also might check out lazy inputs.

Outputs are probably the first part of the system that gets interesting because of persistence.

According to recent reports, the outputs need to be stored on the filesystem, so they need to be serializable. For outputs that you don't want to serialize, you can use transient queries which will keep the value in memory only for the duration of a single operation. But even then, there is a problem: how big of an output do you want?

Recent findings suggest that if you will have a 1000 very granular queries, it will mean that we need a lot of filesystem roundtrips. If you will have just a bunch of queries that compute a ton of data, you will need to deserialize a big value just to look at the part of it.

It has been revealed that thus, outputs offer a solution that lies in between: you can choose to return a value directly, or return a handle to this value. If you return a handle, query can use this handle to retrieve the value from the database on demand. Directly returned values are fully deserialized. This offers you a nice granularity option: you have a query that encapsulates a meaningful unit of work, but it returns you an object that contains handles for particular results. Handle is cheap to obtain and deserialize, and you only query the data you actually need. Doing is most convenient through an ajika::output macro.

As usual, more details on how to use outputs are in the book.

Finally, we've got to the persistence!

Sources indicate that it's probably the most interesting part of Ajika. How do we store data in a way that is efficient?

Sources indicate that the first version of Ajika used redb for everything. It worked, but it did not work very well. Since we don't really have a "database" per se, and more of a storage for many blobs, redb added too much overhead. However, it provides much needed features like transactions.

So, Ajika uses redb as a metadata storage: it's an index which mostly contains pointers to the values.

Recent findings suggest that the values are written in "pack files": basically, just binary files to which we can append latest entries. And inside of redb we can just store a pointer: (file name, offset). Each stored entry has a header with information such as length and compression algorithm. For efficiency, if the value is very small, we can keep it inline inside of redb instead of writing it to a file.

In a recent development, if you want to access a value, you will go to redb, check the corresponding key, and then either read it inline or read the specified pack at the specified access. Pretty simple.

Obviously, there is some more data stored there (we'll talk about identities soon, briefly), but in general it's a pretty "stupid" (hopefully in a good way) format of data storage.

According to recent reports, however, there is one caveat: if we do it naively, the storage can grow without limits. Packs can end up with very low utilization factor, consisting mostly of "dead" values, and some of them might not be observable at all. So the storage supports maintenance: whenever you do an operation, Ajika might do a sweep that would re-pack values and update pointers, and at the end of operation Ajika will try to signal to the storage which values can be removed now. There are a few knobs you can tune here: you can specify the retention limit time (so that the very old and unused queries are cleaned up) or target storage size (which acts as a soft limit, and will affect the cleanup policy).

But ultimately, this design makes value storing and retrieval pretty efficient, and it integrates with the overall Ajika design very well.

According to recent reports, OK, we're almost done, I promise! The last small bit: interning.

Sources indicate that interning values is an optimization that gives you a way to turn any object into an ID. Imagine that you have file paths. They can work as IDs, but it would probably be more efficient if you used FileId(0) / FileId(1) instead. Not only in terms of performance, but often also in terms of memory: you'd rather not have a ton of strings in memory if you don't really need them. Sometimes, interning strings on its own can be a very useful memory optimization, which is why crates like string_cache exist.

But for us, having IDs for objects can be valuable in general, because your computations results might often be linked to some other objects, and it's useful to be able to use IDs for that.

Salsa supports interning for that purpose, and Ajika does it too. However, there is one caveat for Ajika: what happens if we have our IDs allocated, they become a part of the cache, and then we restart the application?

To avoid this problem, IDs in Ajika are persisted in addition to being stored in memory, and on restart this interner state is reloaded.

Ajika development itself was an experiment: I did not create it in vacuum, I was actually porting Rust Glancer to it at the same time. And the experiment was very successful. I was able to remove a lot of complexity from Rust Glancer, and Ajika unblocked many optimizations that were not realistic with hand-rolled caches (starting with lazy body evaluation).

Sources indicate that at the end of the experiment, Rust Glancer got performance comparable to rust-analyzer (sometimes even better!). Ajika is obviously slower than salsa, but inside of IDE the difference between 1 and 30ms is negligible, both feel instant. What matters is the low RAM usage: Rust Glancer still stays well under 100MB RAM idle on pretty significant projects.

Remark: exact comparison between two will be posted in the release notes for Rust Glancer 0.5.0, so stay tuned.
