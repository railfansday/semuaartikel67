In a recent development, AWS recently doubled the maximum timeout of on-demand Lambda Event Functions from 15 to 30 minutes. The upcoming limit applies to synchronous, asynchronous, and event source mapping invocations in all commercial regions, at standard pricing and without an opt-in. The 15-minute ceiling had stood since 2018, after 60 seconds at launch in 2014 and five minutes from 2015.

Raising the limit is a configuration change per function, and Lambda rejects any value above 1,800 seconds with a validation error:.

In a recent development, the change covers one of the three shapes Lambda took this year. Web Functions keep 15 minutes, and Lambda MicroVMs allow eight hours, while on Lambda Managed Instances synchronous invocations now get 30 minutes and asynchronous ones keep the 90 minutes introduced in September. AWS names agentic AI requests that chain model and tool calls, media transcoding, Monte Carlo simulations, and report generation as the workloads that outgrew 15 minutes.

According to Tarun Rai Madan, Dan Slusariuc, and Snehil Ameta, the authors of the announcement, the first thing to check before raising the timeout is capacity:.

In a recent development, concurrency equals requests per second multiplied by average duration in seconds. At the same request rate, a function that runs for 30 minutes instead of 15 needs twice the concurrency. For example, 1 request per second at 30 minutes each needs 1,800 concurrent executions.

Industry observers note that the rest of the post is about what sits around the function. An SQS queue's visibility timeout has to be at least six times the function timeout, which means three hours. Kinesis and DynamoDB Streams read one batch per shard at a time, so a slow function slows the shard. Amazon MQ, DocumentDB and Kafka mappings created before November 19 stay at 14 minutes. A NAT gateway still drops idle connections after 350 seconds, and the Init phase keeps its 10-second limit.

Wibo van der Sluis, an independent AWS practitioner, tested the SQS rule in eu-west-1 by raising a function to 1,800 seconds behind a queue with a 90-minute visibility timeout and then lowering the queue to 60 seconds. The comments under the post took two directions. Magnus Eriksson, architect and former AWS employee, notes that Lambda "is anyhow quite expensive per CPU second compared to EC2" and would still reserve it for short-lived spiky loads. Matthew Bonig, AWS DevTools Hero and co-author of The CDK Book, looked further ahead: "Eventually it'll be 8 hours, and then nobody will be able to understand when to use it vs. MicroVMs.".

On Reddit, the most-upvoted reply welcomed the change because it avoids Fargate and ECS for hour-long batch jobs. The answer under it was that Fargate is beautifully simple. One commenter sets out where the longer limit fits:.

A 30 minute run still bills for the full duration at your configured memory, so check the cost per invocation before moving batch style work here, and keep the handler idempotent with a dead letter queue, because a failure or timeout partway through a long run can leave partial work behind. For multi step work, long running jobs, or anything that needs clear state and retries, Step Functions with Fargate or ECS is still usually cleaner.

Joseph Emison, CTO of Branch Insurance, reads the move as Lambda team recognizing that Cloud Run is its most compelling competitor. Cloud Run services allow 60 minutes per request, and Azure Functions on the Flex Consumption and Premium prepares enforce no maximum, with a 60-minute grace period during scale-in. AWS has not remarked whether the Lambda limit will move again.
