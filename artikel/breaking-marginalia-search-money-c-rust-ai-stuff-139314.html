On a related matter, I’ve been pretty slow about mailing out free API keys,you might have to wait a week or sometimes two.

I swear this isn’t because I’m nefariously trying to push people to buy a key, I’ve been getting over a dozen emails per day some days with people wanting a key, and they sometimes pile up into mountains of emails I need to reply to, and hoo boy is the process of handling these ever a bunch of manual copying of things from email to form, and then copying from form back to email again (ironically the exact sort of tedious workflow I’ve spent a good part of my career helping people streamline and automate).

Apart from fixing bugs and minor improvements, I’ve been experimenting with migrating the index code off Java to C++.

I’ve still not fully decided whether this is the direction we want to go, in general rewrites especially across language boundaries just aren’t worth it and it kinda goes against my better judgement, but we’re at the moment CPU bottlenecked and there might be some juice left to squeeze by skipping the JVM tax, and additionally Java really chafes for this sort of use case.

Don’t get me wrong, the new Java FFM API is miles better than anything we had before, but handling off-heap memory is still awkward and leads to a bunch of duplicated implementations or reimplementations of stuff like sorting and searching algorithms that already exists for on-heap structures but not off; bobbing in and out of native code is awkward and makes the logic difficult to follow, it just chafes.

Recent findings suggest that should be noted the reason I’m even chasing optimizations in the index boils down to the fact that for an internet search engine, performance is recall. The search engine is only as good as the number of results it can rank within the query’s execution budget.

To be honest I’m not 100% convinced we’ll see that much performance impact, and if we do I doubt it will be massive, as the Java implementation is already very optimized, and what we’re mostly bottlenecked on isn’t the sort of places where you see big differences between the languages.

Thus far the buffer pool has been translated, and part of the main inverse index structure. These are some of the most finnicky parts of the index, and a reasonable canary for whether it’s plausible. Based on what I’ve accomplished it’s encouraging to see how much more expressive C++ is for this type of work. The vastly improved ergonomics may be a motivating factor for continuing this even if the performance doesn’t materialize.

In a recent development, I’m doing this quite slowly one component at a time, measuring twice and cutting once, finding good abstractions that lean into C++’s strengths rather than doing a straight translation. In part because this is supremely fiddly and technical work, and in part because there genuinely isn’t any rush and if there is much performance to gain it’s probably in staring at the problem long enough I find better alternative approaches. I did manage to lean more into lock-free algorithms in the buffer pool for example. Translation probably won’t be finished this year at this pace.

Many things are undecided: Haven’t decided on where to draw the interface boundary yet. Neither do I have a public git repo for this. May still scrap the entire idea as a silly boondoggle. We’ll just have to see where it goes.
