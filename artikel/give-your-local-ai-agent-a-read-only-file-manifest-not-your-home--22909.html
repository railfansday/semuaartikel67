Give Your Local AI Agent a Read-Only File Manifest, Not Your Home Directory

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

In a recent development, an agent that can read your entire home directory has more context than it needs and more access than you can easily review. A denylist of sensitive filenames helps, but it grows by exception: .env, .ssh, browser profiles, cloud credentials, and the next file you forgot existed.

A smaller interface is easier to reason about: choose the files yourself, read them once, and hand the model an immutable manifest of text snapshots. The model can request only entries in that manifest. It cannot ask your tool to open a latest path.

The Node.js process still runs with your operating-system permissions. This design does not sandbox it: another tool or a bug could still give it access to other files.

For one task, define a short list such as README.md, src/config.ts, and src/routes.ts. At setup time, the host reads each approved file and stores its text and metadata in memory. Later model requests use an ID like file-2, never a path. That gives the task a stable view: if a file changes after snapshotting, the model continues to see the captured text.

Sources indicate that each task gets a known set of captured text. Include a content hash and capture timestamp so you can identify the bytes used in that task, even after the source file changes.

Prerequisite: Node.js 20 or newer and a directory containing the files you intend to expose. Save this as manifest.mjs; pass the project root as the first argument. Edit approved before running it.

Run node manifest.mjs /path/to/project. The JSON is the complete handoff for this exercise; in an agent host, keep snapshot in memory and expose a lookup by id. Validate the ID against the manifest and return only its stored text. Never turn a model-supplied string into a filesystem path.

Industry observers note that the code rejects lexical .., checks every component with lstat, resolves the final path, and verifies it remains below the root. These checks help with an ordinary, stable directory tree. They are not atomic. Between lstat or realpath and readFile, another process with write access could replace a component or file. That is a time-of-check-to-time-of-use (TOCTOU) race. An attacker able to mutate the tree at the same time may exploit it.

For a hostile, concurrently writable directory, use OS-level isolation or platform APIs that open files relative to a trusted directory handle with no-follow semantics. Portable Node.js path helpers alone do not provide that security boundary. A read-only container mount can reduce what the process may change, but it is a separate control to configure and verify.

In a recent development, UTF-8 decoding can replace invalid byte sequences, and an approved file can contain prompt injection. Reject binary content and treat file text as untrusted data in the prompt. A content hash identifies the bytes; it indicates nothing about whether the text is safe to follow.

Industry observers note that cap the number of entries, reject files above a byte ceiling before reading them, and keep a total snapshot-size budget. A manifest of hundreds of approved files can quietly become a whole-repository dump. If a file is too large, split it deliberately or leave it out and tell the agent that it was omitted. Fail visibly on unreadable or invalid text so a partial snapshot cannot pass for a complete one.

Recent findings suggest that keep the manifest with the task record. When a summary refers to an outdated setting in src/config.ts, its snapshot ID and hash let you check exactly which version the model read.

References: Node.js file system APIs document lstat, realpath, and file reads; Node.js path APIs document path resolution and platform-specific behavior.
