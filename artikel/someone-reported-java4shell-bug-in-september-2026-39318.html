Recent findings suggest that in StubGenerator::generate_base64_decodeBlock() (x86_64 AVX-512 VBMI path), L_finalBit handles 1-63 leftover bytes with a masked vector sequence that computes output_size = (len/4)*3. Valid inputs always have a length multiple of 4, so this bug triggers only on invalid inputs: with length < 4 (e.g. "A".repeat(64)+"=" leaves 1 byte after L_process64Loop), output_size starts at 0 and the padding path decrements it below zero, producing a wrong output_mask. The stub stores past the logical output length before returning to Java, corrupting the heap.

The suggested fix is to early-return to Java if length < 4.
