Breaking: Our push notifications arrived silent, empty, and wrong about the time. Three bugs, one night.

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Recent findings suggest that here is what was actually wrong. Three separate bugs, found one at a time, because each fix revealed the next one.

Bug 1: the permission prompt never fired.

The app only asks for notification permission when you turn a toggle on. The toggles were already on — carried over from the previous build — so the prompt never appeared, and the phone had no permission to show anything. The send still reported alerts_sent: 1, errors: [], because from the server's side everything worked. The failure was invisible to every log we had.

Recent findings suggest that the fix was a phone tap, not code: flip Weather alerts off and back on, which fires the prompt, tap Allow. The next notification arrived in the shade. But it arrived silent, with no title and no body.

Bug 2: one line in the server payload turned a data message into an empty system notification.

This was the real one. Our shared sender built the FCM message like this:.

android: { priority: "high", notification: { channel_id } }.

In a recent development, that notification block changes what the message is. With it present, FCM treats the message as a notification message: when the app is backgrounded, the system displays it itself — and our payload carries no title or body, so the system displayed nothing. The app's own onMessageReceived, the code that builds the real notification with the title, the body, and the tap-to-Weather deep link, never ran.

Industry observers note that the fix was deleting the block. Pure data-only now; the app picks its own channel from the message kind. We deployed the sender (news-weather-alerts v10, news-email-send v57), re-fired the warning, and at 3:11 in the morning the verdict came back: "Yes it buzzed." Full text in the shade — "StarBrook Weather — Freeze Warning — Oklahoma City, OK, until 3:30 PM CT" — and tapping it opened the Weather screen. Arrive, text, buzz, tap: all four proven on a real phone.

Except the time in that notification was wrong.

Bug 3: the push used the wrong NWS field for "until".

The notification said "until 3:30 PM." The app's own Weather banner said "until November 24 at 8:00 AM." We assumed the app was stale. It wasn't — the push was wrong.

Industry observers note that the National Weather Service alert carries two different fields: expires (when the alert product drops off the feed — 3:30 PM) and ends (when the freeze itself ends — 8:00 AM the next day). The push used expires. The fix: props.ends || props.expires, plus a helper that adds the weekday when the end isn't today, so the newly introduced wording reads "until Tue 8:00 AM." Deployed as news-weather-alerts v11 and re-fired. (One footnote: the ?dry_run=true flag on that re-fire didn't take effect — it sent for real. The phone got a second freeze warning at 3 in the morning. Test flags deserve the same skepticism as test data.).

The bug the phone found that the server couldn't see.

The off-and-on toggle flip exposed one more: a race in the app itself. The toggle setter wrote the newly introduced preference to DataStore fire-and-forget, while the re-registration read the preference immediately — fast enough to read the stale value and re-register without weather. The server row had to be fixed by hand that night. The app fix (Build #25) made the four toggle setters plain suspend passthroughs and runs write → permission prompt → re-register in a single coroutine, and the same race got fixed on the Settings ZIP save while we were in there. That build also fixed a settings screen where the Culture chip rendered vertically and the Save button hid under the floating Portal star. Build #25 shipped that evening, and Build #26 is live now.

What the night actually taught us.

In a recent development, starBrook News is free, no paywall, no ads, no account needed to read. The notifications are one toggle: on means news pushes and weather pushes. The app is in beta; the build that carries these fixes is live now.
