During the past year, we have significantly improved the reliability and correctness of Aerogramme's IMAP implementation. This is the first part in a series of blog posts elaborating on why implementing IMAP correctly is not so easy, and the set of techniques we have been using to make our IMAP code as high-quality as we can. In this first part, we focus on one challenging aspect of IMAP: fine-grained retrieval and querying of emails.

According to recent reports, aerogramme is an experimental email server (& calendar, contacts), designed to be geo-distributed, hosted outside of datacenters, on refurbished hardware, and reliable even in presence of network problems and hardware failures. It is built on top of Garage and shares the same philosophy. Aerogramme is AI-free: we do not wish to use unethical technology and prefer to spend effort on careful craftmanship and community-building.

Industry observers note that implementing an IMAP server is not easy. Partly because IMAP is an old protocol, with a good number of extensions that has accumulated quite a bit of complexity over time. On top of that IMAP provides - for good reasons - two classes of features that are fundamentally challenging to implement: fine-grained retrieval and querying of email contents and concurrent multi-client multi-session access to mailboxes.

This is the first part in a series of posts discussing how we have been approaching IMAP access. In the past year, we have been refining Aerogramme's IMAP implementation to be "more correct", in a context where "correctness" is unfortunately not always well specified: IMAP and email are defined in documents that are often vague, and furthermore, real-world implementations do not always follow specifications.

Today, we'll walk you though our work on the correctness and reliability of Aerogramme for retrieving and querying emails, and explain why your mailbox is, in fact, a database...

This work was funded by NLNet under the "Aerogramme 1.0" grant, and could not have been possible without their support.

One challenge of the IMAP specification is the rich feature-set it provides for retrieving mailbox and email contents. We may sometimes think of a mailbox as a directory containing plain email files; however, from the point of view of an IMAP server (or client), a mailbox is closer to a database, accessed using a dedicated query language.

It has been revealed that for instance, mobile clients, which have slower and unreliable connectivity, benefit from fine-grained querying of a mailbox contents. User experience is much better if an email client can selectively fetch the subject of upcoming emails (to enhancement the list of emails in the mailbox) without having to first download all of their attachments or doing a sync of the entire mailbox.

To facilitate the mobile client use-case, IMAP specifies two key mechanisms for querying and (partial) retrieval of emails in a mailbox:.

Recent findings suggest that A direct consequence of these features is that an IMAP server actually needs to parse the emails, not just store them. It then needs to (correctly) interpret the (sometimes tricky) query language of SEARCH and FETCH, and internally support a data architecture that enable efficiently searching and querying over the emails.

Our implementation of SEARCH and FETCH is backed by the three following components:.

The logic for SEARCH and FETCH is implemented as an interpreter that takes already parsed emails and walks down their AST to evaluate IMAP-specific queries1. This separates email structure (email ASTs do not depend on IMAP concepts) from IMAP-specific business logic. This layer has been significantly reworked in the last months, fixing a good number of logic bugs and edge cases in our implementation of the SEARCH and FETCH IMAP specification.

Email parsing is done using the eml-codec companion library, that we also develop and maintain. The eml-codec library parses emails into a rich, structured AST while also giving access to raw input slices that correspond to relevant AST nodes; this is required for implementing FETCH. In the past year, eml-codec has evolved from an email parsing library with IMAP-specific quirks to a robust, well-tested, general-purpose email library with support for both parsing and printing of emails. You can read more about the library design choices in our work-in-progress design document.

Aerogramme's internal data architecture splits mailbox state, email metadata, and email contents. It is briefly described in Aerogramme's documentation. Mailbox state (emails IDs and flags) and email metadata (parsed headers, date, size) are stored in Aerogramme's metadata storage using Garage K2V, while email contents are stored in blob storage using Garage S3. This allows SEARCH to be efficient by only reading pre-computed information in metadata storage. At the moment there are no other significant optimizations for FETCH/SEARCH; the likely next step would be to add a full-text search engine.

These components are all quite non-trivial! Let's now talk about the strategies we've deployed to make them as correct as we could.

We ran our implementation of FETCH and SEARCH through ImapTest: a testing tool for IMAP servers maintained by the Dovecot developers. ImapTest was invaluable in surfacing issues with FETCH and SEARCH, but is equally useful to test all other aspects of IMAP.

According to recent reports, most relevant for FETCH and SEARCH was the test suite provided with ImapTest: a collection of hand-crafted test scenarios testing many subtle or "interesting" aspects of the IMAP specification. Each scenario consists of IMAP commands to send to the server, and a specification of the corresponding expected responses.

Running the ImapTest test suite found a small number of bugs in SEARCH, mostly in edge-cases of the specification. However, testing FETCH revealed that our initial implementation of the BODY[] subcommand was conceptually wrong in many cases! This subcommand of FETCH retrieves a sub-part of an email by following its structure, which we implement by walking down the email's AST. Our initial implementation was done by reading the IMAP specification and interpreting its sometimes vague wording as best as we could; only testing with ImapTest made us realize that our best-guess interpretation was wrong in many cases. More precisely: it did not match ImapTest's reading of the spec, which, in doubt, is what we prefer to follow!

ImapTest was also relatively pleasant to use to do manual "differential testing" for any remaining edge-cases: when we had any doubt, we could easily write additional scenarios and compare Aerogramme's output with Dovecot's; treating Dovecot as an oracle. After a few rounds of bugfixing, Aerogramme's implementation of FETCH and SEARCH is now in much better shape.

FETCH and SEARCH operate on the parsed email ASTs produced by eml-codec. How do we ensure that we have correctly implemented all the subtleties of the email format in eml-codec, which is itself described in an old and tricky set of specifications? As often, the answer is: more testing.

The explanation for this behavior follows from the specification (which is fairly clear on this aspect): the set of ASCII characters that can be used unescaped in depends on the context in which the encoded word appears.

In a recent development, encoded words can appear in From headers (for example From: =?utf-8?q?a=C3=A9rogramme?= is valid), but in that context they cannot use @ or [ unescaped, which is why the first example does not in fact contain a valid encoded word. In the context of a Subject header, the set of valid unescaped characters is broader and includes both @ and [, making =?utf-8?q?@[?= is a valid encoded word representing the string @[.

It has been revealed that to implement this behavior, we needed to correctly track the context in which we parse encoded words, "tokenize" them according to that context, and also track context sensitivity in our email AST and during printing. Getting every detail to align properly between parsing, our internal AST, and printing took us several attempts! In that process, our property-testing setup was extremely useful, as it could quickly come up with fresh convoluted examples like the one above that revealed bugs in edge cases of our code.

The lesson here is that email specifications can be quite complicated and tricky to implement, even when they are clear! And, in our experience, without automatic test generation (like our fuzzer setup), it is very hard to manually come up with examples that actually cover edge cases...

We tested eml-codec on collections of real-world emails (more than 100k emails) to evaluate and improve the recovery strategies of eml-codec's parser on invalid or broken syntax.

Recent findings suggest that many legitimate emails found in the real world are, indeed, incorrect with respect to email specifications. Often, the use of invalid or broken syntax is local (to specific headers, or parts of a header); in some cases, it is "only" a minor deviation from the specification.

The case of "message IDs" can be taken as an example. Emails can be given an identifier (specified using the Message-ID header) so that later emails can reference it (using the In-Reply-To and References headers). This is useful to display email "threads" in email clients, for example. The message ID syntax is also used to identify attachments with the Content-ID header.

Recent findings suggest that the consequence is that eml-codec needs to be able to recover from broken syntax: on an email containing invalid syntax, it should be able to discard the broken parts and parse as much as it can from the rest of the email, instead of simply returning an error. It should also ideally be able to parse invalid but common deviations from the specifications in order to recover information instead of discarding them.

We first extended eml-codec with coarse-grained recovery strategies, such as discarding an entire header field if we couldn't parse it. This allowed us to quickly reach a state where the eml-codec parser is a total function: for any input bytes, it always returns an email AST representing an RFC-compliant email3, discarding any part of the input it does not understand.

Recent findings suggest that we then instrumented the parser to log each time it discards broken input when recovering, and ran the instrumented parser on the email that we collected. This gave us a lot of examples of legitimate emails with broken syntax. This whole process was particularly interesting because it made us face the many subtleties of real-world emails (sometimes far from the "truth" of specifications); eml-codec is now much more robust operating on real-world emails!

Industry observers note that this methodology involves a lot of tradeoffs and judgment calls: there is a limit to the amount of parsing hacks that we can add in terms of code quality but also parsing ambiguity; and some classes of emails are more critical than others (e.g. we should not spend too much effort supporting spam emails). A strong design constraint of eml-codec is that, up to a few exceptions, we want its internal AST to only represent RFC-compliant emails, so we did not want to pollute it to include random broken syntax just for the sake of "recovering more". The whole process, in particular, helped us clarify the design of eml-codec as a library.

Recent findings suggest that for more details, you can look at the release notes of eml-codec 0.3.1 where the bulk of the work is done, building on eml-codec 0.2 for the initial setup of parsing recovery. Both shipped with Aerogramme 0.4.

IMAP's search and retrieval features are essential because they allow clients to have a snappy UX while handling mailboxes with thousands of emails. This post focused on getting those basic features right. But, more broadly, we think that the "mailbox as database" perspective is useful because it raises the question: which end-user workflows can we enable and support? Which features should we prioritize or optimize to best support the workflows of day-to-day email users?
