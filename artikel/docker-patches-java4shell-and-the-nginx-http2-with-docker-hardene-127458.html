OpenJDK and Oracle disclosed Java4Shell (CVE-2026-114938) on November 17, and NGINX released fixes for two HTTP/2 flaws the next day. Docker began publishing fixed images for both in the Docker Hardened Images (DHI) catalog starting that same day.

Sources indicate that what we know about Java4Shell is that it’s a memory-corruption bug in the Java runtime that can let an attacker with no credentials run code inside a Java application. Many container images contain a Java runtime, including application images that bundle their own, so it affects teams well beyond the ones that write Java.

Sources indicate that docker Hardened Images are the trusted foundation your applications should run on, because a flaw in the runtime inside an image is fixed only when that image is rebuilt, and Docker rebuilds its hardened images as soon as upstream fixes become available. Fixed images for the Amazon Corretto, SapMachine and Azul Zulu runtimes and for NGINX are in the catalog today, with Eclipse Temurin following as soon as Adoptium completes its fixed builds.

Recent findings suggest that to decode Base64 swiftly, the HotSpot JVM uses a hand-written routine built on AVX-512 instructions. That routine miscalculates a length when the input ends in unexpected padding and writes up to 62 bytes past the end of a buffer on the Java heap. Calif, the researchers who found it, turned that into heap disclosure and remote code execution.

They demonstrated code execution before authentication against default installations of Keycloak, Jira, Confluence, Artifactory, Jenkins and PingFederate, and after authentication against Kafka, Solr, Elasticsearch, Gerrit and Spinnaker. They note there is no universal exploit: each application needs its own, and they have not published those. As of November 18 there are no public reports of exploitation in the wild.

Oracle rates the matter 8.1 (High) under CVSS 3.1. The researchers rate it 9.2 (Critical) under CVSS 4.0. CISA has issued an alert urging immediate patching.

All three of these must be true.

Recent findings suggest that to check a host’s CPU, run this on the host or Kubernetes node. Hardened runtime images have no shell, so it will not run inside the container.

grep -m1 ‘^flags’ /proc/cpuinfo | tr ‘ ‘ ‘\n’ | grep -E ‘^(avx512f|avx512bw|avx512vbmi|bmi2)$’.

The host is affected if all four flags are printed.

Two other ways to check, for when a shell on the node is hard to get.

In a recent development, ask the JVM. This works in hardened images:.

docker run –rm –entrypoint java -XX:+PrintFlagsFinal -version | grep -w UseAVX.

Sources indicate that useAVX = 3 means the JVM is using AVX-512 on that host. Treat the host as affected until the full check claims otherwise. A value of 0 to 2 means AVX-512 is not in use. On ARM64 nothing is printed. The answer applies only to the host the command ran on.

Set the mitigation flag yourself on every JVM that is still waiting for a fixed runtime, and check what each image already sets before you do. Treat the flag as a stopgap, because a JVM is protected only if the flag reaches it when it starts, and a deployment setting or a start script can override it or drop it. Recent findings suggest that check what the image already sets before you set anything. In Docker and Kubernetes, your value replaces the image’s value. It is not appended.

docker inspect –format ‘{{range .Config.Env}}{{println .}}{{end}}’ \  | grep -E ‘^(JAVA_TOOL_OPTIONS|JDK_JAVA_OPTIONS)=’.

Our FIPS images use these variables to configure the FIPS provider. dhi.io/eclipse-temurin:21-fips sets both. When we replaced its JDK_JAVA_OPTIONS with only the flag, the JVM started normally, but the org.bouncycastle.fips.approved_only property was gone. Nothing warned us. If the command prints a value, copy it and add the flag at the end:.

Keep JAVA_TOOL_OPTIONS away from Java 8. Java 8 is not affected and does not know the flag:.

Java 11 accepts the flag, so it is harmless there.

In a recent development, verify the process, not the environment. Running java -XX:+PrintFlagsFinal -version inside a container starts a newly introduced JVM. It tells you what the environment gives a new JVM, not what the JVM already serving traffic was started with. For the running process, use the startup log line. According to recent reports, the day after Java4Shell, NGINX released fixes for two memory errors in the way it handles HTTP/2 connections, tracked as CVE-2026-123007 and CVE-2026-123633. A crafted request can crash a worker process, and where an attacker gets past the operating system’s memory protections it can run code inside that worker. Both flaws need HTTP/2 to be enabled on the server, and the same releases fix other NGINX issues that do not depend on HTTP/2, so revision either way.

The Docker Hardened Images for NGINX were rebuilt on NGINX 1.30.7 and 1.31.9 and published on November 18, the same day as the upstream release. To patch, pull the image again and redeploy, and move any tag pinned to an older exact version to a fixed one. nginx -v prints the version, and the fixed ones are 1.30.7 and 1.31.9. The notes on pull policy, mirrors and your own images in the section above apply to NGINX images in the same way.
