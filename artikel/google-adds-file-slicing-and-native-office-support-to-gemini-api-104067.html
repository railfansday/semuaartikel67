Google Adds File Slicing and Native Office Support to Gemini API

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Google on November 23, 2026, launched native file-slicing controls in the Gemini API, together with native upload support for Microsoft Office and OpenDocument files. Developers can request selected pages, spreadsheet ranges and media segments, with tokens billed only for the content Gemini inspects.

Recent findings suggest that the patch is aimed at agents that need a chart in a long report, one worksheet in a workbook or a short passage in a recording. Instead of converting and loading an entire file in the client, developers can send a Files API URI and have Google slice, render and tokenize it server-side, reducing prompt-token use and the local processing needed around the model.

For PDFs, documents and presentations, the document-processing controls accept inclusive start and end pages, a choice of extracted page text, rendered page images or both, and low, medium or high resolution for rendering. Spreadsheet requests can select a worksheet by tab position and an A1-style visible_cells range, then choose evaluated data, raw formulas or a rendered visual for charts and layout.

The video-processing and audio-clipping references extend the same approach to recordings. Static video mode, which samples frames at a fixed rate, supports start and end offsets, custom sampling up to 24 frames per second, and transcript, frames or audio layers. Billing covers only the clipped interval and selected layers. Audio accepts offsets in seconds, with an omitted start defaulting to zero and an omitted end to the file’s end; only the selected duration is billed.

According to recent reports, A file can be uploaded once and its URI reused across turns and tool calls. Tools can return sliced pages, spreadsheet ranges or media clips inside function_result, the response a tool sends back to the model. The function-calling reference says the model automatically receives page counts and worksheet names so it can request narrower ranges later. That enables a cheap text or transcript skim before a high-resolution inspection of a relevant page or clip.

Industry observers note that gemini counts and bills tokens only for the sliced output sent to the model. For Gemini 3 and Gemini 4 page images, Google estimates approximately 280 tokens per page at low resolution, 560 at medium and 1,120 at high. Resolution therefore becomes a cost control as well as a detail setting: a team can use text for discovery and reserve rendered images for charts or dense layouts.

For supported Office and OpenDocument files, omitted processing options leave Gemini 4 and later models with medium-resolution page or slide images for documents and presentations, and all sheets with values, formulas and sheet names for spreadsheets.

For documents, slicing does not relax the original upload limits: 50 MB per file, 1,000 pages per PDF, 2,000 pages or slides per Office or OpenDocument file, and 50,000 cells per spreadsheet sheet. Files API uploads are stored for 48 hours, and the Files API is available at no cost in regions where the Gemini API is available.

Vercel reported that, in its production test, extracting text to skim a document page used 14 times fewer tokens than rendering the whole PDF.

Sources indicate that liteLLM reported that slicing cut prompt tokens by 67% for a PDF and 33% for a workbook in its testing. The feature works through LiteLLM’s Gemini routes without additional setup.

Recent findings suggest that native slicing, content-layer controls and the expanded file support are available through the API in Google AI Studio and Gemini for business. Google says native slicing works across all Gemini 4 models, and the document, presentation and spreadsheet controls also support Gemini 3.

For agent builders, the trade-off is explicit: text and transcripts provide a low-cost way to locate material, while page, frame and resolution choices control the cost of closer inspection. The quality of that first-pass search is therefore central to whether the partner-reported savings carry over to other document and media workflows.
