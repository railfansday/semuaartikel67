Kameshwar Singh is a Director of Engineering at Cohesity focused on Enterprise AI, Agentic AI, AI governance, automation, and responsible AI.

Nearly every enterprise AI discussion I sit in begins with the same question: Which model should we standardize on? Fair, but no longer the most important one. As AI moves from pilots into co-pilots, production applications and agents that act on their own, leaders need harder answers. Which AI systems are running in our environment, who or what is calling them, what can they reach and do, and how fast can we pull the plug?

Industry observers note that scale makes these questions pressing. Gartner projects that a typical large global enterprise will be running more than 150,000 agents by 2028, up from fewer than 15 in 2025, yet only 13% of organizations are confident their agent governance is adequate.

Enterprise AI needs a control plane: not another product on the shortlist, but an architectural layer providing visibility, enforceable policy and the ability to intervene across everything AI touches.

Each agent should carry its own identity, defined permissions, a named human owner and a documented purpose. That sounds elementary, yet CyberArk’s 2025 State of Machine Identity Security Report counts 82 machine identities for every person, and most identity programs were built for human employees.

Recent findings suggest that I came up through Unix, and I think about agents the way I think about a shell: You do not need hundreds of commands when one capable interface can run nearly anything beneath it. An agent with one open-ended “execute script” tool may pose far more risk than one with 50 tightly scoped tools.

Sources indicate that so the useful question is not which tools an agent may call, but what this identity can ultimately do, against which resources, under what conditions. Least privilege, time-limited access and approvals should bind to the identity, not to a tool catalog.

AI workloads do not all carry the same risk, so they should not all be routed the same way. Policy sets the boundaries first: Data sensitivity, jurisdiction and risk tolerance decide which models are even eligible. Capability comes next: Among the eligible models, which one can actually do the job? Cost and latency settle the choice last.

A workload touching regulated customer data may belong on a privately hosted model; a sovereignty-sensitive one may require an approved regional environment. Routine summarization can run on a smaller open-weight model, while a hard reasoning problem may still deserve a frontier model. The strongest model is rarely required; the cheapest is not automatically right.

Industry observers note that the FinOps Foundation’s State of FinOps 2026 report found that 98% of FinOps teams expect to be managing AI spend within the year, up from 31% two years earlier. Token consumption belongs in the same telemetry as security events, because a spend spike is often the first sign an agent has gone off script.

In a recent development, the model is one component among many. The moment an agent can retrieve sensitive information through an API or invoke powerful actions through a Model Context Protocol (MCP) server, those interfaces become part of the AI control boundary. IBM’s 2026 Cost of a Data Breach Report found that more than 20% of organizations reported a breach involving AI models or applications, and the most frequent causes were compromised APIs, applications and plug-ins around the model rather than the model itself.

Recent findings suggest that I picture the full chain of an interaction: identity, application, agent, model, data, tool and action. Visibility must cover every link, because attackers target the unwatched one. OWASP’s Top 10 for Agentic Applications makes the same case from the offensive side, listing goal hijacking, tool misuse and privilege abuse. The control plane should span that whole chain, with a loop from the final action back to the originating identity so any link can be revoked, blocked or isolated.

It has been revealed that when an agent begins reading datasets it has never touched, extracting far more records than usual or running up abnormal costs, an alert is not enough. You need the ability to respond: revoke credentials, terminate the session, block the tool or isolate the workload. Ask your security team whether they could shut down one misbehaving agent within minutes without disrupting the application around it.

According to recent reports, gartner expects that by 2027, 40% of enterprises will demote or decommission autonomous agents because governance gaps surfaced only after a production incident. Controls should scale with autonomy and risk, not one rulebook for all.

In the reference architecture I have been developing, the control plane comprises seven capabilities: inventory and ownership; identity and access; data and knowledge governance; model policy and routing; API, MCP and tool governance; observability and FinOps; and threat detection and response.

The structure should also remain open. AI is moving too fast to anchor an enterprise to one model, platform or vendor. Products will come and go; the architecture should not have to. Every component ought to be replaceable, which means open standards and loose coupling.

According to recent reports, the hardest design decision is what to centralize. My answer: Centralize the inventory, policy definitions and audit trail, because each needs a single source of truth, and keep enforcement distributed across the identity, security, data and application platforms you already run, because that is where controls execute. Governance is an operating model, not a product.

For CIOs, CISOs and CTOs, here are four steps to follow for the coming quarter:.

It has been revealed that 1. Inventory every AI application, agent, model, MCP server and API in use, and attach a named owner to each.

2. Assign every agent a unique identity and review what it can ultimately do, not merely which tools it lists.

3. Write a routing policy that decides in order of policy, capability and cost.

4. Rehearse containment: Revoke, terminate and isolate a test agent, and record how long it takes.

The organizations that scale AI safely will not be the ones with the best model, but the ones with the best architecture around it.​.
