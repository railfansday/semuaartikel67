Proof automation in a language

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Industry observers note that as I wrote previously, we have proof automation now. Given that fact, I think a very timely question is: how can we use it to improve software quality? The same machines that can write these proofs can also write large amounts of code. So an adjacent question is: how can we use them to improve software understandability?

Recent findings suggest that it would be a mistake to start off afresh on those problems because there have been a lot of ideas in programming language design over the decades. The viability of ideas shifts as the underlying cost structures change, so things that didn't take off at the time might suddenly make a lot more sense. Still, language design involves a lot of tradeoffs, and features sometimes interact in surprising ways, so a lot of the work involves mixing some interesting-seeming ingredients together, baking, and asking “what is this? Is this a cake?”.

So I wanted to give a taste of some of the ingredients that I'm thinking about at the moment, and of the result.

It has been revealed that value semantics roughly indicates that you can't observe mutations to one variable through a different name. Value semantics are great for reasoning locally about code as, without them, you're constantly unsure what non-local effects might be happening.

It has been revealed that when you work in a language, you instinctively know when it's using value semantics and when it's using reference semantics. Take Python:.

It has been revealed that over the span of four lines of code, this is irrelevant. But as the scope of the sharing increases, so does the mental complexity. If you want to be able to jump into a bit of code and understand what it's doing, knowing that there is no such aliasing is a huge boon.

Functional programming resolves this by eliminating mutation: if there's no mutation then you certainly can't observe mutations via a different variable name. But mutation is important for efficiency and a lot of work is then required to get the efficiency back. Lean, for example, will do in-place mutations if there's only a single reference to an object. That's great! But it has the sharp edge that innocent-looking changes can mean that there's now a hidden reference kept somewhere and performance crashes.

Rust claims to fix both complications by restricting references so that you can't ever have both a mutable reference to something, and an active alias to it. (We'll ignore Rc> and friends.).

Industry observers note that certainly Rust's restrictions help a great deal, but Mutable Value Semantics states that Rust goes too far by making references first-class, i.e. something that you can return and store in structures. First-class references lead to the borrow checker, which has undergone several deep rewrites (original to NLL, next to Polonius) to try and perfect it, and they lead to lifetimes, DerefMut etc., and much more complexity in the type system in general.

Sources indicate that so an MVS system avoids all that by further restricting references and not allowing them in the type system. These ideas started in Swift and are currently championed in Hylo. The best introduction I've found is this talk.

In an MVS system, functions can take three sorts of arguments: immutable, mutable, and owned. Immutable arguments might be a reference or a copy; the semantics are the same. Mutable arguments are conceptually copied in at call time and copied back out when a function returns, but of course that's semantically the same as taking a pointer. Lastly, owned arguments transfer ownership to the function and make it unusable in the caller afterwards.

In a recent development, but there are no references in the type system, so a function can't return or store them. But the inability to return references implies so much copying that MVS systems need to provide an alternative.

Hylo has a very cute system of scoped coroutines, inspired by Swift. These coroutines yield a value and, at the call site, all their arguments are locked for the duration of that value's span. At the end of the span, the coroutine continues running.

Industry observers note that one of the common examples is that a coroutine can return a mutable bool for a vector of bits that have been packed into bytes. Then, when the coroutine continues once the return value is no longer used, it can write the new value of that bool back into the array of bytes. This wouldn't be possible without a coroutine because the function would have to return a pointer to a bool that exists nowhere in memory.

According to recent reports, having just lionised this feature, I should note that in my experiments I haven't actually included it because it makes the semantics more complex and I'm spending a lot of complexity budget on verification instead. Which brings us to another idea that combines with MVS….

If you want to do formal verification on a language like C, then you need to model the heap and you immediately hit the aliasing problems above. Then you end up with a separation logic which lets you model disjoint areas of the heap (i.e. areas with no aliasing between them). Once you can speak about independent heaps, you can reason about a function that operates on one heap and hold the remainder constant.

Sources indicate that this can work. The example that I'm (passingly) familiar with is the Verified Software Toolchain which connects to CompCert's semantics and allows you to state properties about C programs (with a separation logic) and thus verify C code all the way to machine code. But it's complex.

Recent findings suggest that however! If you have restricted references then you can drop a huge amount of complexity from such systems! Aeneas/Charon is the current canonical example of this which can translate a subset of Rust code into Lean (and other languages) where things can then be proved about it. Because of Rust's restrictions, the translation doesn't need a separation logic.

But by being more restrictive than Rust, MVS languages are even more amenable to such translation, and thus to formal verification, without going all the way to being functional languages and banning mutation completely.

It has been revealed that eiffel is the standard reference here. It introduced preconditions, postconditions, and invariants for functions/classes:.

While you've probably never used Eiffel, these notions are quite widespread now, although in common programming languages they are at best encoded in assertions if simple, comments if not, but mostly remain only in the author's head.

Eiffel did all its checks at run-time. There has been a lot of work on the balance between run-time and compile-time for these assertions, and on how to discharge assertions statically. Briefly, some work in this space that I'm aware of:.

Dafny allows a mixture of run-time and static assertions, and discharges the static ones via SMT solvers. F* does everything statically, again using SMT solvers, but with a functional language. SPARK has a mixture of run-time and static checks, using SMT solvers or (albeit very challenging to use) provers via Why3. I've never touched Verus but it's worth a mention because it's the most recent entry in this lineage and is Rust-based.

Recent findings suggest that the problem with these systems is that the compile-time checking is much more powerful, because it can cover all possible values of the arguments, but the proof burden is significant. SMT solvers help a lot, but they can quickly hit (effective) non-termination for non-trivial cases. I did an F* summer school in Paris once, and the experienced people there had developed a sixth sense about what would displease the SMT solver and would instinctively code around it. It was an impressive skill! But not reassuring.

This is the key cost that has changed: SMT solvers were inadequate for more complex cases, and dropping into a proof assistant overwhelmed you with lots of inscrutable proof states. All this can be largely handled by models now.

In a recent development, also, I claim that there are some interesting synergies between MVS and design-by-contract. In Rust, and more so in an MVS system, you end up using indices into arenas of objects to replace arbitrary pointers. (Which can be faster due to cache locality.).

Industry observers note that given that one has all these indices flying around, wouldn't it be nice to have explicit invariants about them? Hopefully proven?

It has been revealed that when writing code I will fairly often have some structure which has invariants that enhancement as processing progresses. At some early part of the pipeline, the structure may be relatively arbitrary, perhaps freshly parsed from a file, and then as various checks and transforms are applied we know more and more about the value.

It has been revealed that but in traditional languages, the structure has one type: its structural type. Even with Eiffel-style Design by Contract, invariants on a type are fixed.

The idea of being able to attach more invariants to a structure without duplicating most of it showed up as Subtypes in proof systems, and refinement types in ML. You'll also see Rust code do this (mostly at run-time) with checked constructors like NonZero and NonNull. But those are run-time checks that the type system carries a certificate of. Similar to the evolution of Eiffel-style conditions, we can hope to make them static checks now, discharged via our newly introduced proof automation.

Literate programming was the title of a paper by Knuth in the 80s, and WEB was the original implementation. The idea is that code should be written to be read and thus that it should be ordered for human, not machine, consumption, and that exposition should be at least as important as the code, and not relegated to comments.

Nearly twenty years ago I wanted to understand critbit trees and so wrote an implementation using CWEB to explore both ideas.

Relatedly, in my mind code has a graph structure deriving from which functions call which other functions. Source files are groups of strongly connected functions and I generally have little memory for what order functions have in a given source file. With the widespread use of LSPs and thus code indexing, we are edging slowly towards being less file orientated but I still feel that we could do much more.

Industry observers note that there was a burst of such ideas in the 80s: Knuth's work, also Smalltalk & Lisp systems which kept code in databases rather than text files. Given the ecosystem of version control that assumes text-based files, code databases might be too awkward now, but I still feel the itch of dissatisfaction here.

At the top of this post I also set a goal for code to be more understandable and, to that end, the easiest code to understand is the code that you didn't have to read because the contract claims all that you need to know about it.

It's worth discussing the more bitter flavours in this cake too.

Industry observers note that the front end of the compiler emits lots of verification conditions for the code to be correct. Every arithmetic operation emits overflow checks, every indexing operation emits range checks, every invariant and postcondition results in checks, every loop must be shown to be terminating, etc.

Sources indicate that the little DER tag example above results in 149 of them. Each is first sent to Z3 and then, if Z3 times out (after a couple of seconds), to cvc5. But the solvers are never trusted. If they believe that a condition holds they output the unsat core which is used to trim the hypotheses which are fed into Lean. Lean automation chews on the problem for a while and, if that times out, an LLM comes to write a manual proof in Lean.

It has been revealed that there's a cache of proven conditions, of course, and the Lean proofs are saved in a different file. But overall even reasonably simple examples type-check at about 10 lines per second. If you invalidate the cache then medium-sized programs can take multiple hours to recheck on a fast machine. (Not reprove, just to check the proofs that already exist!) So modularity of code is vital to keep the scaling line flatter.

Sources indicate that LLM compute is needed too: after I laid out the spec for the DER tag example above, a model took about 30 minutes to get it working. But if you ask a modern model to write the same thing in Go, it will do it in under 10 seconds. (Although the result doesn't hit nearly the same quality bar and the lax parsing would cause security problems in sensitive contexts.).

Overall, this language was an experiment in how we can convert compute into high-quality and understandable code. I'll claim that it's making interesting steps towards that goal, but you do need a lot of compute.

Recent findings suggest that also, there is a considerable trusted base involved here. While you don't have to trust the SMT solvers, you do have to trust that the front end is correctly translating the code into verification conditions for Lean, and you have to trust that it is correctly translating it into LLVM IR. I think that's fine: the comparison here is with regular languages like C++ and Rust. This is not an attempt at a minimal TCB language with extremely strong guarantees like CakeML.

Still, the language does have significant aspects of delight. Being able to write the spec for DER encoding, and then have the correct code for it generated, does make me reflect on the amount of time and suffering that I've put into DER over the years that could now be avoided.
