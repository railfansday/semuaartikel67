Large Language Models (LLMs) are exceptionally good at generating text. We use them to answer questions, write code, reason about problems, and so much more. But not every problem requires generating text.

Consider a customer support system receiving the following message:.

Industry observers note that "I was charged twice for my subscription. I need a refund today.".

The system needs to determine which team should handle the request, how urgent it is, and whether the customer is requesting a refund.

We could ask an LLM to return a JSON object containing these answers.

But what if the model could directly evaluate the available options and return a probability distribution over them, without generating any text?

This is the key idea behind decision models.

Industry observers note that A decision model takes some input context (state), evaluates a question with a set of predefined possible answers (primitives), and returns a structured decision along with probabilities. Instead of asking a model to generate an answer token by token, we ask it to assign probabilities to the answers that our application already understands.

Recent findings suggest that typeSafe AI introduced Jev, describing it as a System One model. The name draws inspiration from the distinction between fast, intuitive thinking (System 1) and slower, deliberative thinking (System 2).

The community has converged to the term decision model, because it describes the model's computational role rather than invoking a particular theory of cognition. In the rest of the post we will refer to the models as "decision models" instead of "system one models". (A poll on twitter deciding what we should be calling such models).

In a recent development, we could simply prompt an LLM to return a JSON object containing our decisions. In fact, this is how many applications already use language models for classification, routing, and other structured tasks.

However, there are a few problems with this approach.

Before understanding the interface of a decision model, it is useful to revisit two closely related approaches namely traditional classification and zero-shot classification.

Suppose we train a classifier that routes customer-support requests to three departments:.

According to recent reports, A conventional classification model learns a mapping from an input to a predefined set of labels. During training, the model learns to predict these labels from examples. A classification head typically produces one logit per class, and softmax turns those logits into a probability distribution.

The limitation here is that the output classes are baked into the model's classification head.

If we introduce a fourth department, such as Legal, the existing classifier does not automatically acquire a corresponding output class. We may need to modify the head, collect training data, and retrain or adapt the model.

In a recent development, zero-shot classification addresses an vital part of this limitation. Instead of requiring the classifier to be trained specifically on every output category, we supply the candidate labels at inference time.

Recent findings suggest that unlike a conventional fixed-label classifier, the categories can change from one request to another. Let’s add another department, such as “Legal”, and see the model outputs.

One common implementation uses a model trained for natural language inference (NLI). Each candidate label is converted into a hypothesis, and the model measures how strongly the input entails that hypothesis.

This already sounds quite similar to a decision model. And in many ways, it is.

Recent findings suggest that decision models extend this idea beyond simply assigning an input to a category. A decision model can accept several named questions about the same state, with different answer types. The types can be choosing between alternatives (choice), scoring an ordered scale (score), or estimating the probability that a statement is true (noul).

More importantly, its interface is designed around the probability distribution over possible decisions.

Industry observers note that the advantage of decision models is not that they invented runtime-defined labels or probabilistic classification. It is that they organize these capabilities into a consistent interface, potentially backed by architectures and training procedures optimized specifically for decisions.

The third primitive is Noul, which represents a binary question.

Is the customer requesting a refund?

Rather than defining a list of choices, we ask the model to return the probability that the answer is true. We can understand this using the Bernoulli distribution (noul comes from Bernoulli).

According to recent reports, the model is not randomly sampling a binary answer here. It returns the probability parameter itself, leaving the application to decide how to act on it.

According to recent reports, so far, we have obtained probability distributions from the model. But the decision model interface also returns a field called confidence for Choice and Score.

According to recent reports, the full distribution might contain several possible answers, and it is useful to summarize how concentrated the model's belief is. With confidence we achieve just that.

Notice that the winning probability is 0.998, but the reported confidence is 0.997. The confidence normalizes the largest probability relative to the number of available options. In contrast, the ordered Score example only had a confidence of 0.558.

Recent findings suggest that decision models are a young and fast-moving space. Each one makes decisions differently under the hood (heads that score the whole schema jointly, separate readouts on top of LLM backbones, edge-sized and multimodal variants, etc). This variety is healthy, but it comes at a cost. If every model exposes its own interface, every tool around it needs model-specific adaptations.

Our goal at Hugging Face is to agree on a common interface without forcing a common implementation. A decision model should be free to work however it likes internally, as long as it accepts the same state and questions and returns the same typed decisions. Once that contract exists, the rest of the ecosystem can build on it once:.

Decision models are interesting not because classification is newly introduced, but because they make decisions and probabilities first-class outputs for software.

Traditional classifiers already produce probabilities, and zero-shot classifiers already allow runtime-defined categories. Decision models bring these ideas into a typed interface with multiple question primitives, non-generative scoring, and the possibility of specialized training for reliable, calibrated decisions.

Great write-up. The step the post leaves to the application, turning noul: 0.83 into an action, is where things get hard in production. It's usually a threshold (if p > 0.9), and it quietly goes stale: raw probabilities are rarely calibrated, the right cut-off depends on what a mistake costs, and the outcome that indicates whether the decision was right (a chargeback, a reassigned ticket) arrives days or months later.

I'm building an open-source, self-hosted tool for that loop: trimset. It sits in front of any /v1/systemone server (so transformers serve or llama.cpp) with a one-line URL change. It logs every decision and joins the real outcome when it arrives. It calibrates per question and model, then compiles thresholds and an escalation band with a stated guarantee ("false passes ≤ 2% with 95% confidence"), which your app applies locally. It's pre-alpha; drift and silent-upgrade alerts come next.

Live demo on recorded data, threshold simulator included: https://demo.trimset.dev/#/questions/refund_fraud/simulator.
