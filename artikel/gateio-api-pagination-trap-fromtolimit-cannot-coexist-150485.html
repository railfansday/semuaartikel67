Recent findings suggest that if you've wired up Gate.io's futures candlestick endpoint, you've probably hit this: you build a request with a start time, an end time, and a page size, and the server replies HTTP 400. You strip out to, retry, and it works. You add it back, it breaks. The error message doesn't mention to at all — it usually complains about something generic like an invalid parameter or an empty result set, which sends you chasing the wrong thing for an hour.

It has been revealed that the rule the docs bury: from, to, and limit are mutually constrained. from+limit works. from+to works. to+limit works. All three together returns 400. And there's a second constraint that bites later: any single call returns at most the most recent 10,000 data points, regardless of how wide your range is.

The message varies and is never "you sent too many parameters." That's the trap: the API validates combinations, not individual fields, and the error text doesn't say which combination it rejected.

One more detail worth knowing: from and to are in seconds, but the timestamps inside the returned candle objects are also in seconds. Mixing in milliseconds (easy to do if you're used to other exchanges) silently produces empty arrays or absurd ranges rather than an error.

It has been revealed that the fix is to pick one paging axis and stick to it. from+limit is the most robust because it's forward-only: you always ask for "the next N candles starting at timestamp T," and you advance T using the data you got back.

Sources indicate that the rule: next page's from = last candle's timestamp + interval seconds. Not +1 second in general — +1 only works for the 1s interval. For 1m it's +60, for 1h it's +3600. If you use the interval length, you never re-request the boundary candle and you never skip one.

A few things this loop gets right that naive versions don't:.

The 10,000-point cap is per call, not per range, and it's applied to the most recent data in the window you asked for. This has a nasty consequence: if you request from = now - 30 days with limit = 1000 on 1m, you get the 1,000 most recent minutes of that window — not the first 1,000 minutes. Your pagination loop's first page is fine, but the semantics of "most recent within the window" mean that a naive loop which advances from will eventually get stuck asking for data older than what the server will serve in a single call.

The clean way to handle it is to split the overall range into windows of at most 10,000 intervals, and paginate inside each window. That way each from+limit call is guaranteed to fall inside the server's per-call ceiling.

Industry observers note that if you're pulling months of 1m data, this is dozens of HTTP round-trips. That's expected — there is no bulk export endpoint, and hammering the server with parallel requests will get you rate-limited. Serialize, add a small sleep between windows, and cache to disk.

The Gate.io case is one instance of a general problem: undocumented parameter interactions. When you hit a 400 and the message is unhelpful, don't guess — bisect.

The idea: start with a request you know works, then add parameters one at a time, and when it breaks, remove one at a time to confirm which combination is fatal. For a small parameter set this is a few requests.

Sources indicate that for three optional parameters this is at most 8 requests and it tells you definitively that {from, to, limit} is the failing triple and {from, limit} is the maximal working pair. That's far faster than reading docs that don't mention the rule.

According to recent reports, when the parameter space is larger — say, ten optional query params — exhaustive subsets are 1,024 requests, which is too many. Switch to a greedy bisection: add params one at a time in the order you suspect matters; when adding one breaks the request, mark it as conflicting with the current set and try it alone against the required params. That's O(n) in practice.

Run it, and you get a working parameter set plus the list of params that broke it. In the Gate.io case, rejected would contain whichever of from/to/limit was added third — which is exactly the information the error message withheld.

Industry observers note that the general lesson transfers: when an API's parameters interact, the docs often describe each field in isolation and leave the constraints implicit. Build a small probe harness once, and every new endpoint becomes a five-minute investigation instead of an afternoon of guessing.
