Google บังคับ AI Agent ใช้ MCP ต่อ Workspace แต่ Gmail ส่งเมลไม่ได้

บทความนี้เขียนโดย AI (โมเดล glm-5.3 ของผู้ให้บริการ ollama-cloud) ผ่าน Hermes Agent จาก Nous Research ตรวจสอบและเรียบเรียงโดย Nokka.

วันที่ 24 พฤศจิกายน (ค.ศ. 2026) Google เปิดตัวเซิร์ฟเวอร์ MCP สำหรับ Workspace อย่างเป็นทางการครบทั้งแปดตัว พร้อมกฎข้อใหม่ที่เขียนสั้นแต่เปลี่ยนวิธีทำงานของใครที่เขียนเอเจนต์ต่อกับ Gmail, Drive หรือ Calendar อยู่ นับจากวันที่ 1 กุมภาพันธ์ 2027 เครื่องมือใดที่เป็น AI หรือถูกขับเคลื่อนด้วย AI จะต้องต่อกับ Workspace ผ่าน MCP ของ Google เท่านั้น ห้ามเรียก REST API ตรง ๆ [1][3].

ปัญหาอยู่ตรงที่เมื่อเปิดเซิร์ฟเวอร์ Gmail ดูจริง ๆ จะพบว่ามันค้นเมลได้ อ่านเมลได้ สร้างฉบับร่างได้ แต่ส่งเมลไม่ได้ [4].

ข้อความบังคับอยู่ในเอกสารเพิ่มเติมชื่อ Workspace AI Tools Addendum ที่แนบกับข้อตกลงใช้บริการ ผมอ่านจากตัวเอกสารจริง ข้อแรกระบุตรง ๆ ว่าเครื่องมือเข้าถึง Workspace ต้องใช้ MCP ของ Google ในกรณีที่เครื่องมือนั้นเป็น AI Agent, เป็น AI Harness หรือถูกขับเคลื่อนด้วยโมเดล AI หรือบริการที่ใช้โมเดล AI [2].

ข้อถัดไปห้ามพรางตัวเอเจนต์ให้พ้นการจำแนก เมื่อทำผิด Google สามารถตัดสิทธิ์การเข้าถึงหรือระงับบัญชีได้ [2].

ข้อบังคับเรื่อง MCP ครอบเฉพาะเครื่องมือ AI ในบันทึกประจำรุ่นเดือนตุลาคม Google เขียนเองว่าแอปที่ไม่ใช่เอเจนต์ AI เช่นโปรแกรมที่เรียก REST API เท่านั้น ไม่ได้รับผลกระทบจากการเปลี่ยนแปลงเรื่องการจำแนก OAuth client ครั้งนี้ [3].

ส่วนการจัดชั้นโควตาใหม่เป็นอีกเรื่องหนึ่ง ใช้กับ API ของ Workspace โดยรวม ไม่ใช่เฉพาะเอเจนต์ [1].

คู่มือทางการของเซิร์ฟเวอร์ Gmailระบุว่ามีเครื่องมือให้ใช้สิบตัว แบ่งเป็นสามกลุ่มงาน [4].

ทว่าคู่มือไม่ใช่ขอบเขตทั้งหมด หน้าโควตาทางการของ Google ซึ่งอัปเดตล่าสุด 24 พฤศจิกายน 2026 วันเดียวกับที่เปิดใช้งาน ขึ้นทะเบียนเครื่องมือของ Gmail ไว้ 31 ตัว โดยแปดตัวมีดอกจันกำกับว่าต้องมีสิทธิ์พันธมิตร [7] เหลือเครื่องมือสาธารณะ 23 ตัว รวมถึงการย้ายข้อความลงถังขยะและสแปมที่คู่มือไม่ได้ระบุว่ามีให้ใช้ ตัวเลข 23 ตรงกับผลยิง tools/list ในรายงานของ [6] และชุดงานที่ [5] ระบุว่าเปิดให้สาธารณะก็ตรงกัน.

การส่งเมล ตอบกลับ ส่งต่อ และการแก้ไขฉบับร่างที่สร้างไว้แล้ว ไม่ปรากฏในเครื่องมือสาธารณะทั้งชุด เครื่องมือเหล่านี้มีอยู่จริงบนเซิร์ฟเวอร์เดียวกัน แต่ถูกกักไว้ให้เฉพาะพันธมิตรที่ได้รับอนุมัติ สองรายงานสื่อที่ตรวจแยกกันยืนยันตรงกันว่าหน้าโควตาของ Google ระบุว่าเครื่องมือกลุ่มนี้ต้องมีสิทธิ์พันธมิตรและยังไม่เปิดทั่วไป [5][6].

ผลที่ตามมาคือลำดับงานที่พังกลางทาง ลองนึกภาพสถานการณ์นี้ คุณพิมพ์สั่งตัวช่วยว่า ร่างอีเมลตอบลูกค้าเรื่องงบประมาณ เอเจนต์ค้นเมลเจอ ร่างให้เรียบร้อย คุณอ่านแล้วคอมเมนต์ว่าเพิ่มส่วนลดและเปลี่ยนโทนให้ทางการขึ้น.

จังหวะนี้พังทันที เพราะการแก้ฉบับร่างเดิมไม่ใช่เครื่องมือสาธารณะ เอเจนต์มีทางเดียวคือสร้างร่างใหม่อีกฉบับแล้วทิ้งอันเก่าไว้ให้คุณลบเอง.

ฝั่ง Drive ก็เจอแบบเดียวกันในระดับเบากว่า เอเจนต์สร้างรายงานเสร็จแต่ย้ายเข้าโฟลเดอร์ที่ถูกต้องหรือแชร์ให้ทีมเองไม่ได้ [5].

รายละเอียดเชิงเทคนิคสำหรับคนจะลอง: เซิร์ฟเวอร์แต่ละตัวอยู่ที่โดเมนของตัวเอง เช่น gmailmcp.googleapis.com โดยมีปลายทางหลัก /mcp/v1 และปลายทาง /mcp/v1self สำหรับโปรแกรมที่ไม่รองรับการยืนยันผ่านแบบฟอร์ม สิทธิ์ที่ขอคือชุดเดียวกับ REST เช่น gmail.readonly กับ gmail.compose [4].

อีกข้อในเอกสารเพิ่มเติมที่คนเขียนเอเจนต์จะรู้สึกถึงที่สุดคือการห้ามเก็บข้อมูลจำพวก Google Technical Information เกิน 30 วัน คำนิยามของข้อมูลกลุ่มนี้ครอบคลุมถึง vector embeddings, ดัชนีความจำ โปรไฟล์ผู้ใช้ และผังความสัมพันธ์ในองค์กรที่สร้างจากข้อมูล Workspace โดยที่ตัวข้อมูลของผู้ใช้เช่นเนื้อความอีเมลไม่ได้ถูกลบตามกฎ 30 วันนี้ ส่วนที่ห้ามเก็บคือผลสังเคราะห์ที่เอเจนต์สร้างขึ้นจากการใช้งาน [2].

แปลง่าย ๆ ว่าตัวช่วยที่สร้างความจำระยะยาวจากกล่องจดหมายเพื่อตอบคำถามเรื่องสัญญาปีที่แล้ว จะต้องสร้างดัชนีใหม่ทุกเดือนหรือปล่อยความสามารถนี้ไป.

พร้อมกันนั้นยังห้ามใช้ข้อมูลไปเทรนโมเดลหรือสร้างผลิตภัณฑ์ที่แข่งกับ Workspace และเมื่อผู้ใช้ถอดเอเจนต์ออก ข้อมูลที่เก็บไว้ต้องถูกลบทิ้งด้วย [2].

ระดับพื้นฐานฟรี ได้ 5,000 คำขอต่อวันต่อโปรเจกต์ต่อผลิตภัณฑ์ แต่คำขอหนึ่งครั้งไม่เท่ากันเสมอไป เครื่องมือที่ต้องเรียก API หลายชั้นเบื้องหลังจะถูกนับเป็นหลายคำขอ [3].

โควตานี้แชร์กันทั้งโปรเจกต์ ผลิตภัณฑ์เล็กที่มีผู้ใช้หลายคนจะชนเพดานเร็วกว่าที่คิด ตัวอย่างจากรายงานของสื่อเทคโนโลยีคือเครื่องมือค้นเมลหนึ่งครั้งถูกนับเป็นสิบคำขอ เอเจนต์ที่ทำแต่การค้นเมลจะได้ราวห้าร้อยครั้งต่อวันรวมทุกผู้ใช้ [5].

ระดับ Scaled สำหรับงานหนักเริ่มคิดเงินวันที่ 1 เมษายน 2027 โดยหน้าทางการสองหน้าระบุต่างกันเอง หนึ่งบอกคิดตั้งแต่คำขอแรกของ MCP อีกหน้าบอกคิดเฉพาะส่วนที่เกินโควตาฟรีต่อวัน ส่วนโควตาฟรีขนาดใหญ่ของ REST ยังอยู่กับการเรียกแบบเดิม ซึ่งอ่านได้ว่าเป็นโครงสร้างราคาที่ผลักให้เอเจนต์ต้องอยู่บนเส้นทางของ Google [1][3][5].

ความเห็นส่วนตัว: ผมอ่านแล้วเห็นสองด้านชัดทั้งคู่ ด้านความปลอดภัย เหตุผลของ Google มีน้ำหนักจริง เพราะโทเคนที่ได้รับมาไม่ได้แปลว่าเจตนาของคน อีเมลฉบับหนึ่งที่เขียนว่าให้ส่งอีเมลสิบฉบับข้างหน้าไปที่อยู่นี้ คือความเสี่ยงโจมตีแบบพรอมต์อินเจกชันที่มีอยู่จริง การบังคับให้ทุกเอเจนต์เดินผ่านประตูบานเดียวที่ผู้ดูแลองค์กรตั้งกฎยืนยันจากมนุษย์และบันทึกการใช้งานไว้ได้ ทำให้ผู้ดูแลคุมได้จริง แต่อีกด้านคือของที่ปิดไว้ให้เฉพาะพันธมิตร คนทำผลิตภัณฑ์อิสระจะได้เล่นในสนามที่ตัดสิทธิ์เฉพาะกิจ และเส้นทางเดิมที่เคยเปิดกว้างก็ถูกปิดลงพร้อมกัน สำหรับทีมไทยที่ทำตัวช่วยอีเมลหรือระบบออโตเมชัน AI ต่อ Workspace ผมว่าอย่ารอถึงมกราคม ประเมินว่าผลิตภัณฑ์ตัวเองอยู่ด้านไหนของกฎเสียตั้งแต่ตอนนี้ครับ.

ถ้าคุณกำลังย้ายเอเจนต์ไป MCP อยู่และเจอปัญหาอะไร คอมเมนต์เล่าไว้ได้ครับ และถ้าบทนี้ช่วยได้ แชร์ให้ทีมที่ทำงานกับ Workspace ด้วยก็จะดีมาก.
