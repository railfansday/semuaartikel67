Key domain provisioning on the tenant, upsert every intended MX record, and run verification as a separate convergent step. For a logistics tech giant pointing company mail at a provider, acceptance means agreement between the approved mail configuration and the published records. A successful worker attempt is only one piece of that evidence.

TL;DR: Persist the zone identifier on first success. Make each replay reconcile the current approved record set, then verify it. Use 4 checks before accepting the change: tenant identity, zone identity, record agreement, and verification against the same configuration revision.

The useful angle here is change acceptance: what evidence lets an operator close the onboarding task, and what evidence requires another reconciliation pass? That question determines the workflow more clearly than a list of DNS features.

In a recent development, retried onboarding is normal. Customers double-click, jobs get replayed, and deployments interrupt work. Consider an illustrative logistics tenant whose company-mail setup has already created a zone and written part of the desired MX configuration when its worker stops. The next attempt must recover that tenant's stored zone identity and finish reconciling the approved configuration. Treating the replay as a fresh onboarding request makes the wrong thing the unit of work.

An MX record existing is weaker evidence than an MX record matching the intended provider configuration. Compare the approved owner name, destination, and preference with what is published, using the mail provider's actual instructions. Don't substitute an example hostname or a remembered preference value. Another worker must be able to reach the same decision without interpreting an earlier worker's log messages.

Industry observers note that there are two duplicates to handle: a repeated delivery of the same job, and an old job arriving after an operator approves a newer mail configuration. Deduplicating delivery alone doesn't establish which configuration should win. As an application design rule, bind work to a configuration revision and check that revision before making changes. A stale job should trigger reconciliation of current intent rather than restore an obsolete mail destination.

Industry observers note that record whether identity recovery, record reconciliation, or verification remained incomplete. A generic onboarding failure hides the boundary that the next attempt must cross.

Industry observers note that keep a durable tenant-level provisioning record containing the approved domain, the saved zone identifier, the desired MX configuration, and its revision. These are proposed application fields, not a vendor request schema. Store the zone identifier on first success so retries don't re-derive it. The identity should survive a worker restart and remain available to a later delivery.

Upsert every record in the approved configuration. Upsert removes the failure class in which a second attempt errors merely because the record already exists. It does not, by itself, answer whether an obsolete record should be removed or whether a competing worker still holds an older configuration. Define record ownership and serialize changes for a tenant, or enforce an equivalent revision guard, before enabling automatic removal. Otherwise cleanup can fight the next reconciliation attempt.

For company mail, make the intended MX set reviewable and identify which records this workflow owns. Leave unrelated DNS changes outside that scope. If a provider migration requires removing an earlier MX destination, make removal an explicit part of the approved change. Repeatedly upserting newly introduced entries doesn't prove the old entries have disappeared.

Keep verification separate from writes. Verification is convergent: running it again on a verified domain is harmless. However, an earlier verification result should not approve a later configuration revision. Associate the result with the revision being accepted, and keep the task pending when the evidence describes a different state.

Back off on rate limits, honor Retry-After when supplied, and surface an exhausted attempt as pending reconciliation with its reason. A retry budget belongs in the worker policy. Indefinite retries without an actionable status turn a visible change into a forgotten background task.

Sources indicate that choose a DNS control surface by inspecting how it fits the existing authoritative zone and how much reconciliation your application must own. These are alternatives to evaluate, not a claim that their write operations share one upsert or retry contract. Establish those contracts from the linked product documentation before implementation.

According to recent reports, existing operational ownership is a concrete difference between these choices. Moving a zone solely to simplify an onboarding worker adds another change to review. Keeping the current DNS service can be the better decision even if the integration requires more application logic. Conversely, an existing account isn't sufficient evidence that a particular record-write strategy is safe to replay. Test that boundary.

If the current hosted zone and its operational controls already meet the team's needs, prefer retaining that provider over introducing another integration just for onboarding. Choose the interface whose semantics the team can explain in its runbook. None of these product names establishes that company mail is ready.

Use the same acceptance checks after a normal attempt and after a replay. These are proposed operational gates, not measured service guarantees.

A longer requested wait ends this attempt without retrying early. A GET requires no write-deduplication key. Provisioning writes need their own stable operation identity and reconciliation logic.

Exercise interruption boundaries before relying on the workflow: after zone creation, after partial record reconciliation, and before verification is recorded. These are test scenarios, not reported incidents. For each, inspect the final published state and the durable provisioning record. Counting successful requests is inadequate because the requirement is convergence after the interruption.

Also replay an older job after approving a newer configuration. If it can restore the previous mail destination, the workflow lacks an effective revision boundary even if every individual request is idempotent.

In a recent development, keep the claim narrow. Matching MX records and completing domain verification are evidence for this provisioning task. DMARC addresses a separate mail-authentication concern, described in RFC 7489; an MX reconciliation result should not be presented as proof of that separate configuration.

Before a mail-provider change, retain the approved previous MX configuration and the ownership scope of this workflow. If the change needs to be reversed, approve that configuration as a new revision, reconcile it against the same saved zone identity, and repeat the acceptance checks. Don't replay an old job as a rollback command: that bypasses the revision boundary established to keep stale deliveries from winning.

Record which revision is now intended, what remains different in the published records, and whether verification has completed for that revision. Keep the task open while those disagree. A rollback request is another desired-state change; it needs the same evidence as the initial cutover.
