If you want to remove vocals from a song, isolate drums, or export several instrument tracks, sending audio to a third-party API is not your only option. Stem Separator is an open-source, self-hosted web application that runs the separation pipeline on your own machine, homelab, or NAS.

This tutorial uses the project's stable v1.0.0 release and Docker Compose. You will start the CPU version, verify its health endpoint, upload a supported audio file through the browser, and understand when the NVIDIA GPU configuration is appropriate.

Recent findings suggest that clone the repository, start the default Compose service, open http://localhost:7860, and upload an MP3, WAV, FLAC, M4A, AAC, OGG, or OPUS file. The default mode separates vocals and music. Stem Separator stores model weights in a named Docker volume and writes job output to ./data/output.

Recent findings suggest that the key boundary is that this is local processing, not an anonymous public service. The application does not include built-in authentication or rate limiting, so keep it on localhost or a trusted LAN unless you add an authenticated reverse proxy.

The CPU deployment includes FFmpeg in the image. You do not need to install Python, PyTorch, or FFmpeg on the host for this path.

Industry observers note that the repository is MIT licensed and the stable release used here is v1.0.0. The project README is the source for the commands and configuration discussed below: paladini/stem-separator.

According to recent reports, the default Compose file maps the host directory ./data/output to /data/output in the container. That directory holds job state and exported tracks, so the results remain available when the container restarts. Model weights use the named volume stem-separator-models, which prevents a model from being downloaded again after every container recreation.

The default Compose configuration is intentionally conservative:.

These settings cap upload size and duration, reject jobs when disk space is too low, limit concurrent processing to one job, and bound the waiting queue. Completed or failed job folders are retained for 24 hours by default.

Sources indicate that the default model is a practical CPU starting point. The repository also documents a BS-Roformer model of about 610 MB, recommended for an NVIDIA GPU because CPU processing can be slow. Model file size is not the same as runtime memory, so treat the RAM and VRAM guidance as a baseline, not a guarantee.

The project provides a separate Compose override for NVIDIA CUDA. The host needs an updated NVIDIA driver and the NVIDIA Container Toolkit installation. Verify that Docker can see the GPU before starting Stem Separator:.

Then start the GPU image with both Compose files:.

The override replaces the CPU image, requests all GPUs, and keeps the same port and mounts. Do not run both stacks in the same checkout because both publish port 7860.

The Docker configuration supports CPU and NVIDIA CUDA deployments. The README does not claim verified Docker acceleration for Apple Silicon MPS/CoreML, AMD ROCm, Intel graphics, or Windows DirectML. If you need those paths, evaluate the native Python setup separately instead of assuming the Docker image will pass through the host accelerator.

It has been revealed that stem Separator places a small web application in front of python-audio-separator. Its catalog maps friendly goals such as Vocals & Music to a verified model and a set of output tracks. The job manager validates the input, creates an isolated job directory, runs the engine, and exposes status and download endpoints.

That separation is useful operationally. A malformed filename or unsupported extension can be rejected before inference, and a low-disk condition can stop a job before it consumes more storage. Engine failures can return as actionable application errors rather than unfiltered stack traces.

Check the logs and verify that the container has its bundled FFmpeg available. For a native Python installation, install FFmpeg and confirm that both ffmpeg and ffprobe are on PATH. A degraded health response is a signal to fix the media dependency before submitting a job.

The first use of a model downloads its weights. Watch docker compose logs -f, check available disk space, and remember that the model cache is mounted at /data/models. Deleting the named volume forces the downloads again.

It has been revealed that start with the default Vocals & Music model, reduce concurrency if you changed it, or choose the Force CPU option exposed by the application. The larger studio model and multi-instrument modes need more memory. A GPU does not remove the need to size the host and its VRAM correctly.

Sources indicate that run docker compose ps and inspect the port mapping. If another application owns port 7860, change the host side of the mapping in a local Compose override, then use the matching browser URL. Keep the container port at 7860 unless you also change the health check and application configuration consistently.

The README documents local processing, filename sanitization, isolated UUID job directories, and path-containment checks for downloads. These safeguards are not a complete deployment security model.

There is no built-in authentication or per-IP rate limiting. Do not expose this service directly to the public internet. If remote access is necessary, put it behind a reverse proxy with HTTPS, authentication, request-size limits, and rate limits. Also review the licenses and usage rights for the audio files and model weights you process.
