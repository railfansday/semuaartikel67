PDF to Text in Your Browser: pdf-lib Can't Extract Text, but pdf.js Can

If you want the words out of a PDF without uploading the file anywhere, the answer is one function: page.getTextContent() from Mozilla's pdf.js. And if you already build PDF tools with pdf-lib — the library from my merging post — here is the thing nobody tells you until you waste an afternoon on it: pdf-lib cannot extract text at all. Both "do PDFs in JavaScript", but they do opposite halves of the job, and picking the wrong one is the most common dead end in browser PDF work.

Below: what pdf.js does, the exact code already running in one of my production tools, and a real test on two real PDFs.

Sources indicate that pdf-lib 1.17.1 exposes 46 methods on PDFDocument.prototype, and not one of them mentions text or extraction. It can load a document, copy pages between documents, draw newly introduced text onto a page, and save the result. Reading the text already in a page is simply not in its vocabulary. That is a design boundary, not a missing feature: pdf-lib is a document builder, and extraction belongs to a document reader.

A PDF does not store text the way a .txt file does. It stores positioned fragments — a string here, a string there, each with coordinates — and the order those fragments sit in the file is not necessarily the order a person reads them. pdf.js, Mozilla's open-source PDF parser, parses that structure and hands you the fragments per page:.

getTextContent() returns one entry per text fragment, each with a str property. Join them and you have the page's words — the entire extraction step. Everything else in a real tool is interface: file picker, progress label, copy button, download-as-.txt button.

In a recent development, two things worth knowing before you trust the output blindly. First, the join matters: the example joins fragments with a space, which is what my link extractor does. Nutrient's guide improves on this by checking each item's hasEOL flag and inserting a newline where the PDF ends a line — better for prose, where a space-join can glue a heading to the next paragraph. Second, pdf.js reads the text layer. A scanned PDF is pictures, not text, and getTextContent() will honestly return nothing for those pages. That is the boundary between extraction and OCR — a different tool (Tesseract.js) for a different problem.

Two honest notes. The 184 ms includes the library warming up — the second file took 15 ms, the honest per-file cost once loaded. Node also printed warnings about missing standard font data; they did not affect the output, and they are a Node-only artifact. The point is not the milliseconds: a four-page PDF gives up its text in well under a second, with no server, on a library version already proven in production.

In a recent development, scanned PDFs return nothing. If the page is a photograph of a page, there is no text layer, and getTextContent() returns an empty list. Say so in your UI — "no text found, this looks like a scanned document" — instead of showing a blank box and letting the user assume the tool is broken.

Industry observers note that reading order is not guaranteed. pdf.js returns fragments in the order they sit in the file, which for multi-column layouts can mean the left column's second paragraph arrives after the right column's first. Single-column documents read correctly, as the two test files show. For two-column papers, expect interleaving — sort fragments by coordinates before joining.

The worker setup has two silent failure modes. If you forget to set workerSrc, pdf.js falls back to a "fake worker" on the main thread — extraction still works, but a 50-page PDF freezes the page while it parses. And if the worker version does not match the main library version, loading hangs with no error at all. Both are documented in the w3tweaks guide on PDF.js extraction — pin both scripts to one version string, as the production code does.

Recent findings suggest that can pdf-lib extract text from a PDF? No. I verified it directly: pdf-lib 1.17.1's PDFDocument has 46 prototype methods and none of them reads text. pdf-lib builds and modifies PDFs; extraction is pdf.js's job.

Does this work on scanned PDFs? No — a scan has no text layer to read, so getTextContent() returns nothing for those pages. Scanned documents need OCR (Tesseract.js runs in the browser). Check whether you can select text in your PDF reader first: if you can select it, pdf.js can extract it.

In a recent development, how large a PDF can the browser handle? No hard limit, but the whole file sits in memory, and a 5 MB PDF can expand well beyond its file size once parsed. Ordinary documents run in milliseconds, as the test above reveals.

Is my file uploaded anywhere? No. The file is read with file.arrayBuffer(), parsed by pdf.js in a Web Worker, and the text is produced in your tab. There is no server endpoint involved at all — the entire reason to build it this way.

In a recent development, PDF to text in the browser is a solved problem, but only if you pick the reading library: pdf.js, getDocument() then getTextContent() per page, worker pinned to the same version. pdf-lib is the wrong tool for this half of the job — and knowing that saves you the afternoon I spent learning it.

ToolNest's PDF link extractor already runs this exact code in production — it reads the same text layer to find URLs — and the PDF merger from my earlier post covers the other half with pdf-lib. Between the two libraries, the browser does the whole job, and your file never leaves your machine.
