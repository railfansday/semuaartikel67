According to recent reports, databricks has added PostgreSQL 19 to Lakebase and Neon, giving teams a way to try the open-source database’s newly introduced maintenance, query planning and replication tools on managed infrastructure. Databricks claims both services had support on the day the PostgreSQL project released the new version. PostgreSQL’s own announcement dates the community release to November 19, 2026.

The update is relevant to teams building AI applications, even though it does not introduce a latest AI model or vector index. Operational databases often sit behind the user-facing parts of these systems. They store conversation history, track jobs and permissions, record application events and serve calls that need predictable response times. A database upgrade that makes this infrastructure easier to maintain can matter more to those teams than a new feature in the application layer.

Recent findings suggest that one of the main additions in the PostgreSQL 19 release is REPACK, a command that rebuilds a table to reclaim unused space and can optionally reorder the data to match an index. PostgreSQL creates a new row version when data changes. Routine vacuuming makes old space available for reuse, but that does not always shrink the underlying table on disk. A table that stores frequently updated jobs or messages can keep occupying more space than its remaining live rows need.

An option lets ordinary reads and writes continue through most of the rebuild. That does not make the operation free of disruption. As Neon’s release notes explain, PostgreSQL still needs an exclusive lock to finish swapping the rebuilt files into place. Teams should test the operation under a representative write load rather than assume the final lock is negligible on a busy table.

The release also adds pg_plan_advice, an extension for testing and stabilizing execution prepares, and a companion pg_stash_advice extension that can apply stored advice to a matching query. The planner ordinarily chooses how to execute a query based on the data and statistics available. When that choice changes, an operation that used to be fast can suddenly become slow. The fresh tools give operators a way to investigate or mitigate that regression without immediately rewriting application code. Any saved advice should be revisited as the data and workload evolve.

Recent findings suggest that postgreSQL 19 also adds WAIT FOR LSN, which lets an application wait for a database replica to reach a specified position in the write-ahead log. With asynchronous replication, a write can succeed on the primary database before a replica has applied it. A user or agent that immediately reads from that replica may otherwise see an earlier state.

In a recent development, that lag matters if, for example, an application records approval for a task and immediately asks another service to read it from a replica. Waiting for the relevant log position can let that read see the approval. It trades some waiting time for freshness when the workflow needs it, rather than assuming all replica reads are current.

Industry observers note that databricks’ supported-versions documentation lists PostgreSQL 19 for Lakebase, and Neon’s announcement explains how to choose it for a fresh project. Neither announcement indicates that all existing databases were automatically upgraded. Databricks also says Lakebase engineers contributed to the upstream release, including work on query-plan advice, shared memory and release management.

In a recent development, for teams considering a migration, version availability is a starting point. A useful test is to run representative queries, confirm extension compatibility, measure replica lag and rehearse the maintenance operations that prompted the upgrade. Teams can then compare those results with the behavior of their current database before switching production traffic.
