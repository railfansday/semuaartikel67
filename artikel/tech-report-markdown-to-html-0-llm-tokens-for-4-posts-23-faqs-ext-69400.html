We needed to publish four manuscripts (43,699 bytes in total) that another project had handed over, and the obvious move was to ask an LLM to turn the markdown into HTML. We wrote a deterministic converter instead. It used zero LLM tokens, extracted 23 FAQ questions automatically, and all four posts passed its built-in checks. The reason is not cost. The manuscripts already contained values that had been cross-checked by hand, such as notice numbers and page numbers, so changing a single character during formatting would itself be a defect.

This post covers the rule we use to decide between a script and an LLM, what the converter actually does, and the two publishing traps it closed without anyone having to remember them.

Ask these about the step you are about to automate. A single "yes" means use a script.

Our conversion answered yes to all three. The manuscripts already followed a fixed layout (title, three-line summary, tables, a Q/A list), the rules for turning that layout into tags were unambiguous, and compliance could be checked with plain string searches. Work that needs judgment, such as summarizing, restructuring, or adjusting tone, belongs to the LLM. Moving a fixed format into fixed tags does not. The short version: if judgment is needed, use an LLM; if there is a rule, use a script.

In a recent development, there is a cost argument too, but it is the weakest of the three. A few posts are cheap either way, yet an LLM step also gives you a different output on each run and a chance to quietly touch a number. Those two problems are what actually hurt.

The script takes one markdown file and produces body HTML plus a metadata JSON. If it finds a spec violation it exits with code 1.

According to recent reports, (The full manuscript and converter output checklists are in the original post.) Two numbers catch most formatting accidents. If faq_count differs from what you expect, the Q/A format in the manuscript drifted. If html_len is far smaller than the source, part of the body was not parsed.

The converter also removes the H1 from the body and uses the first summary item as the excerpt. Our platform renders the title separately, so leaving the H1 in the body would show it twice.

It has been revealed that FAQ entries are pulled only from the FAQ section of the body. That keeps the structured data from containing questions the page never demonstrates, which search engines flag as a mismatch. A runnable version of the idea looks like this:.

Industry observers note that the regular expression enforces the format. If the section heading differs, the question line is styled differently, or an answer does not begin with A., that pair is simply not captured. In other words, the manuscript format becomes the parser's input specification. On these four posts the approach extracted 23 questions with no manual step.

The last block of the converter counts the things that must not ship: a leftover style block, a leftover h1 tag, a leftover TODO marker, a leftover emoji, or a missing title. Any hit makes the process exit with 1.

According to recent reports, with an LLM you would have to write "do not include a style block" into the prompt every time and then eyeball the result. A script holds the rule in code, so it does not forget, and a pipeline only has to look at whether the exit code is 0. All four posts passed.

Sources indicate that the first trap is CSS leaking across the whole site. Our blog renderer lifts style definitions found inside a post body up into the page-level head, so CSS written for one post can change others. The converter never emits a style block. It keeps a per-tag style dictionary and injects the styles inline:.

Tables are wrapped in an overflow-x:auto container in the same pass, so a wide table scrolls instead of pushing the whole page sideways on mobile.

The second trap was duplicated JSON-LD, and it came from the handoff document, not from the script. The spec stated to put a BlogPosting block in the body. The front end already generates BlogPosting in the head, so following the spec literally would have produced duplicate structured data. Reading the receiving code while building the converter highlighted that only a FAQPage block belonged in the body.

The lesson is about order, not about this spec: read the receiving code before executing a handoff document. A spec is true as of the day it was written, and the system on the other side may have changed since.

Recent findings suggest that A deterministic converter is only deterministic if the input follows the spec. Otherwise it silently drops things.

Some limits are worth stating plainly. This converter is built for our blog platform. The per-tag inline styles and the "no style block" rule exist because our renderer hoists styles globally, and another platform may not have that constraint. Markdown parsing relies on an external library and its extensions (tables, sane_lists, nl2br), so a version change can alter the output. And the approach only fits steps that need no judgment: writing the manuscript is still the LLM's job. Split a publishing pipeline along that line, with evidence gathering, machine verification, and layout in scripts and first drafts from the LLM.
