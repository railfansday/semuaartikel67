Fig and Elastic partner to help security teams prevent silent gaps in detection coverage

In a recent development, security teams rely on detection rules to identify suspicious activity across increasingly complex technology environments. But even when those rules remain active, changes to the underlying data can quietly undermine their effectiveness. A vendor updating its log format, a new data source entering the environment or a pipeline modification can leave detection logic without the information it needs to identify threats.

Recent findings suggest that addressing this challenge, Fig has confirmed an integration partnership with Elastic designed to help security teams maintain detection coverage as their environments evolve. The integration combines Elastic Security’s open, agentic security operations platform with Fig’s capabilities for mapping detection dependencies, identifying breaks and validating changes before they reach production.

The partnership aims to give security operations teams greater visibility into the relationship between their data infrastructure and the detection rules that depend on it.

Detection engineering involves more than creating rules that identify suspicious behavior. Those rules depend on data arriving in specific structures, containing particular fields and values that allow security teams to recognize potentially malicious activity.

When those dependencies change, detection coverage can deteriorate without producing an obvious warning. Data may continue flowing, and detection rules may remain enabled, even though the information required to identify an attack is no longer available.

In a recent development, these changes are not necessarily caused by mistakes. Organizations regularly modify their data pipelines to improve performance, introduce upcoming vendors or accommodate evolving infrastructure requirements. However, changes made outside security teams’ direct control can have downstream consequences for detection engineering.

Recent findings suggest that this is where Fig’s integration with Elastic is designed to help. Rather than treating data infrastructure and detection rules as separate components, the integration connects changes upstream to the detections that depend on them.

According to recent reports, fig connects to an Elastic environment through a read-only API key and retrieves its configuration. Its deterministic Security Data Lineage then maps the relationships between data sources, pipelines, mappings, fields and detection rules.

Industry observers note that this creates a dependency map that allows engineers to understand what each detection rule requires before making changes to the environment. When a source, pipeline or mapping changes, Fig identifies the affected detections and pinpoints where the data flow has broken.

The platform also recommends fixes, giving engineers information they can use to investigate the underlying glitch and evaluate potential repairs.

For Gal Shafir, Co-Founder and CEO of Fig, the partnership addresses two complementary areas of security engineering.

Recent findings suggest that “Elastic gives security teams control over their data, and Fig gives them control over the engineering around it,” said Shafir. “Teams can see how every source connects to every detection, test each change against their own environment and ship it as code. That lets them move rapidly without losing sight of their coverage.”.

The distinction is notable as organizations introduce latest data sources and continuously adjust the infrastructure supporting their security operations.

In a recent development, elastic provides prebuilt integrations and research-backed detection rules to help organizations establish security coverage from the beginning. Its Automatic Import and AI Agent capabilities also help teams develop newly introduced integrations and custom rules as their requirements expand.

Fig complements these capabilities by allowing engineers to test changes against their organization’s actual data and environment context before deploying them.

Once changes have been validated, teams can ship them as code through continuous integration and continuous delivery workflows. Version control and one-click rollback provide additional control over deployment.

Jamie Hynds, Director of Product at Elastic, highlighted the importance of maintaining visibility as security environments change.

Industry observers note that “Environments never stop changing, from vendor schemas and APIs to ETL tools and pipelines. Fig traces those changes to the detection rules that depend on them, so SecOps teams can adapt promptly and maintain detection coverage with Elastic Security,” noted Hynds.

Sources indicate that the integration also addresses organizations migrating from another security information and event management platform. Elastic’s Automatic Migration translates existing detection rules, while Fig checks those translated rules against the data available in Elastic before cutover.

The process identifies rules that require rework and recommends fixes, helping engineering teams align detection logic with the destination environment before completing the transition.

The Fig and Elastic integration is now available. Security teams can book a demonstration through fig.security to see how Fig maps their Elastic environment.

In a recent development, as security environments continue to evolve, maintaining effective detection coverage requires more than keeping rules active. It also requires understanding the data dependencies behind them and validating changes before they affect production.
