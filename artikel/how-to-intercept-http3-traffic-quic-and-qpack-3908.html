How to Intercept HTTP/3 Traffic: QUIC and Qpack

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

It has been revealed that short answer: HTTP/3 does not go through an HTTP proxy, because it runs over QUIC, and QUIC runs over UDP. Most HTTP proxies, such as Burp Suite, are built on HTTP over TCP, so they never see it. To intercept HTTP/3 you need a proxy that can relay UDP and can act as a man in the middle for QUIC. After that, the work is about streams and header compression: the request is not text any more, it is bytes on a QUIC stream, compressed with QPACK.

It has been revealed that in this post we intercept real HTTP/3 traffic from curl and from Microsoft Edge. Then we use a small lab server to look at every byte, so the QUIC and QPACK parts are easy to follow.

Recent findings suggest that this post uses InterceptSuite, so you should know what it is and what it is not. It is not built for HTTP. It is built for raw network traffic: TCP, TLS, UDP, DTLS and QUIC. Because it can intercept UDP and QUIC, it can handle HTTP/3 too. But it does not come with an HTTP parser, and that is also true for HTTP/3. The core shows raw bytes.

To read and edit those bytes as HTTP, InterceptSuite has an extension API, and there is an official, open source HTTP/3 extension that decodes the QUIC stream and QPACK headers into text. You can read the code, change it, or send a fix. The decoding in the screenshots below comes from that extension, not from the core.

If you have only used HTTP/1.1 or HTTP/2, three things are different.

According to recent reports, 1. It runs on QUIC, not TCP. HTTP/3 (RFC 9114) is HTTP carried over QUIC (RFC 9000). QUIC packets travel inside UDP datagrams. TLS 1.3 is part of the QUIC handshake (RFC 9001), so there is no separate "TCP then TLS" step.

In a recent development, 2. The client has to learn that the server speaks HTTP/3. The ALPN name for HTTP/3 is h3. A server can advertise it with an Alt-Svc response header, and a DNS HTTPS record can advertise it too (RFC 9460). So a browser often makes its first request over TCP, then moves to QUIC.

According to recent reports, 3. Everything is a stream. A QUIC connection carries many streams. The two lowest bits of a stream ID tell you what it is (RFC 9000, section 2.1):.

In a recent development, in HTTP/3, every client-started two-way stream is one request and its response (stream 0, 4, 8 and so on). The one-way streams are for housekeeping: a control stream, and two QPACK streams. Their type is the first byte on the stream: 0x00 control, 0x02 QPACK encoder, 0x03 QPACK decoder (RFC 9114, section 6.2 and RFC 9204, section 4.2).

It has been revealed that one more detail that matters for interception. The first packets of a QUIC connection (the Initial packets) are protected with keys that anyone can calculate from the connection ID, so they have no real secrecy (RFC 9001, section 5). That is why a passive observer can still see things like the server name in the handshake. Everything after the handshake is encrypted with keys from the TLS 1.3 exchange. You cannot read it without being one of the two ends. A proxy that wants to read HTTP/3 has to be one of the two ends.

Recent findings suggest that HTTP proxies use CONNECT to open a tunnel. In HTTP/3, CONNECT still builds a tunnel to a TCP connection (RFC 9114, section 4.4). To tunnel UDP over HTTP there is a different method, CONNECT-UDP (RFC 9298), and most tools and apps do not use it.

According to recent reports, SOCKS5 can relay UDP. The command is UDP ASSOCIATE (RFC 1928). But many clients never use it. For example, the Chromium network docs say that in Chrome, SOCKSv5 is only used to proxy TCP-based requests and cannot relay UDP (Chromium proxy docs). So pointing a browser at a SOCKS5 proxy does not send its QUIC traffic through that proxy, and you are not testing the QUIC path.

According to recent reports, where are the entries? In the 114-byte entry on the encoder stream. Its first bytes are C0 88 9D 95 E8 1C 6B A4 A8 4F, which is "insert :authority, with a Huffman-coded value" (the value decodes to h3.lab.test). The client sent the long header values once, and every later request only sends numbers. This is a good design. It is also what makes interception harder.

There is one more thing to see here. In the capture, the 13-byte request (row 30) arrived before the 114-byte encoder stream entry (row 31). That is allowed by design. QPACK lets a request stream wait ("block") until the inserts it needs have arrived. The server confirmed it could keep up to 16 blocked streams (the QPACK_BLOCKED_STREAMS setting we saw above). Later a single byte 88 comes back from the server on its decoder stream. That is a Section Acknowledgment for stream 8, which was the third request: the decoder tells the encoder it processed a header block that needed the table (RFC 9204, section 4.4.1).

If the edited text leaves a broken header block, Replay sends only a few bytes (25 here) and the server closes the connection:.

Sources indicate that 0x106 is H3_FRAME_ERROR. RFC 9114 notes that if a stream ends and the last frame on it is cut short, the receiver must treat it as a connection error of this type (RFC 9114, section 7.1). In plain words: the frame header promised more bytes than the stream delivered. If you hand-craft HTTP/3 bytes in the Raw or Hex tab, this is the error you will meet first. It means your frame length does not match your data.
