What is gradient checkpointing, and when should you use it?

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Gradient checkpointing, also called activation checkpointing, saves GPU memory in training by keeping only a few activations from the forward pass and recomputing the rest during the backward pass. Nodus turns it on by default in its sft fine-tuning runtime: in our Qwen3-8B estimate it cuts activation memory more than 10x, and published measurements put the cost at 20 to 36% more step time. Use it when activations are what overflow your GPU, and leave it off when the model already fits with a batch size that keeps the GPU busy.

No, and the shared word causes real confusion. Gradient checkpointing is a memory trick inside one training step. Nothing is written to disk, and nothing survives a crash.

A training checkpoint is a saved copy of the weights, optimizer state and data position, written every few hundred steps so a run can resume after a failure. If that is what you are looking for, read our guide to automatic checkpointing and resume.

The two often sit side by side in one config. The Nodus sft runtime has gradientCheckpointing, default true, described as "recompute activations to save GPU memory". It also has saveSteps, default 200, the number of steps between recovery checkpoints. One saves memory, the other saves progress.

Recent findings suggest that gradient checkpointing and activation checkpointing are the same technique. PyTorch's torch.utils.checkpoint docs call it activation checkpointing, and recent Hugging Face Transformers releases have renamed their methods to match.

Sources indicate that it throws away most of what the forward pass would normally keep. In ordinary training, every intermediate tensor a layer produces stays in memory until the backward pass uses it to compute gradients. With checkpointing, only the input to each checkpointed block is kept. When the backward pass reaches that block, it runs the block's forward again to rebuild what it needs.

In a recent development, the idea comes from Chen et al.'s 2016 paper, Training Deep Nets with Sublinear Memory Cost. Split an n-layer network into about sqrt(n) segments and keep only the segment boundaries. Memory then grows with sqrt(n) instead of n, for "the computational cost of an extra forward pass per mini-batch". The paper reports a 1,000-layer residual network going from 48 GB to 7 GB with 30% more running time.

The extra time has a simple ceiling. Korthikanti et al. at NVIDIA note in Reducing Activation Recomputation in Large Transformer Models that the backward pass needs about twice the FLOPs of the forward pass. A normal step is therefore 1 forward plus 2 forward-equivalents of backward, or 3 units. Recomputing everything adds 1 more, so 4 / 3 = 1.33, at most about 33% more compute.

On a transformer, often 90% or more of the activation memory. We worked it out for Qwen3-8B, using the per-layer formulas from Korthikanti et al. Their formulas are for GPT-style layers, so treat the results as estimates for Qwen3's gated MLP and grouped-query attention.

The inputs are from the Qwen3-8B config: hidden size h = 4,096 and L = 36 layers. We assume one 8,192-token sequence (s = 8,192, b = 1) in 16-bit precision, with a fused attention kernel. One unit of s x b x h bytes is then 8,192 x 4,096 = 33,554,432 bytes, about 33.6 MB.

In a recent development, korthikanti et al. put the stored input of a checkpointed layer at 2 x s x b x h bytes, against 34 x s x b x h for a full layer. When we count peak memory, we add the activations of the block being recomputed: 34 units for one layer, 6 x 34 for a 6-layer segment. Every layer works out to 2.4 GB of stored inputs plus 1.1 GB for the layer being rebuilt.

Checkpointing every layer cuts this example's activations from 41.1 GB to 3.6 GB.

The table holds a detail the sqrt(n) rule hides. Chen's rule assumes the cost of storing a segment boundary is about the same as the cost inside a layer. In a transformer, a layer's input is 2 units and its insides are 34, about 17x more.

The best number of segments is then near sqrt(17 x 36), about 25, not 6. In practice, checkpointing every layer (3.6 GB) or segments of 2 layers (18 segments, about 3.5 GB) is close to the minimum. That is why Hugging Face checkpoints every decoder layer by default rather than using sqrt(n) segments.

Wrap each block's call in torch.utils.checkpoint.checkpoint and pass use_reentrant=False. The PyTorch docs recommend the non-reentrant variant and warn that a future release will raise an error when use_reentrant is not passed explicitly.

In a recent development, for an nn.Sequential model, checkpoint_sequential(model, segments, x, use_reentrant=False) splits it into segments for you. We ran both forms on PyTorch 2.15 on CPU with a 12-block MLP stack. The gradients matched the plain version exactly, with a maximum difference of 0.0. That checks correctness, not speed or memory, which you should measure on your own GPU with torch.cuda.max_memory_allocated().

According to recent reports, the non-reentrant variant also avoids an old trap. The docs say the reentrant variant needs at least one input and output with requires_grad=True, or the checkpointed part gets no gradients. That bites LoRA runs, where the frozen base model's inputs do not require gradients. The non-reentrant version has no such requirement.

Keep the recomputed forward identical to the first one. The docs warn that if a global variable or other state changes between the two calls, you can get an error or silently wrong gradients. Dropout is handled for you, because preserve_rng_state defaults to True.

Recent findings suggest that one call on the model, or one flag on the trainer. In the Transformers v5.24.1 model docs, the method is activation_checkpointing_enable(). The old gradient_checkpointing_enable() still works as a deprecated alias until v6, and older releases only have the old name.

In a recent development, the upcoming method takes every_n_layers, which checkpoints only every n-th decoder layer and lets the rest keep their activations. That is the 22.9 GB row in our table, with roughly half the recompute cost. It also takes offload, which holds the saved inputs in pinned CPU memory and makes each step slower.

On Nodus, the sft runtime sets gradientCheckpointing: true for you. You only touch it to turn it off:.

According to recent reports, expect 20 to 36% longer steps with every layer checkpointed. The Hugging Face GPU training guide quotes about 20%. Chen et al. measured 30% on their residual network. Korthikanti et al. write that full recomputation can add as much as 30 to 40% to compute time, and they measured 36% on their largest models.

Most measurements land near the 33% ceiling that one extra forward pass implies.

Measured overheads can sit below 33% because the non-reentrant variant stops recomputing once it has what it needs, and because some step time is not compute.

In a recent development, yes. Sharding splits weights, gradients and optimizer state across GPUs, while checkpointing shrinks activations on each GPU, so the two stack. Use sharding when model state is too big and checkpointing when activations are.

It is the middle ground from Korthikanti et al.: recompute only the attention parts that are cheap to rebuild but large to store. With sequence parallelism, they cut recomputation overhead by over 90%. Fused attention kernels such as FlashAttention already avoid storing the attention score matrix, which gives a similar saving.
