Embedded SQL in RPG is the default way to access Db2 for i in newly introduced code. It is also where I most often see sloppy code: no status checks, SELECT *, and cursors left open. This article gives a pattern you can paste into a real program.

SQL statements start with exec sql and end with a semicolon, and can span lines. The source member type is SQLRPGLE.

Same program in fixed format (what you will meet in most shops):.

Fixed format has no exec sql ...; one-liner: the statement sits between C/EXEC SQL and C/END-EXEC on C+ lines (/ in column 7, EXEC SQL in columns 8-16). SET OPTION goes there like any other statement.

SET OPTION is not executable; the precompiler reads it. IBM requires it to precede every other SQL statement in the source, and you can code only one, so put all options in that one statement. It lets the source carry its own compile options.

If no row matches you get SQLSTATE 02000 (SQLCODE 100). If more than one matches, you get an error (SQLSTATE 21000, SQLCODE -811) unless you add fetch first row only. Decide which you mean. A null in a column needs a null-indicator variable (:cust.balance :balInd) or you get SQLCODE -305.

According to recent reports, the precompiler gives you sqlstate and sqlcode automatically. Check after every statement. SQLSTATE is the portable value; SQLCODE is Db2-specific but handy.

Same program in fixed format (what you will meet in most shops):.

DSPLY needs a variable in fixed format, hence MSG. DSPLY also cuts the message at 52 characters, so keep it short. If CHECKSQL is called earlier in the same source, add a D CHECKSQL PR N prototype first.

Sources indicate that warnings start with 01, not found is 02, and 00 is success. Anything else (class 22, 23, 42 and so on) is an error you must handle. For details use GET DIAGNOSTICS CONDITION 1 :msg = MESSAGE_TEXT (the CONDITION 1 is required for condition items like MESSAGE_TEXT, RETURNED_SQLSTATE and DB2_MESSAGE_ID). Capture sqlstate into a variable before you run it, or any other statement, because every later SQL statement can overwrite what you were about to test.

Use a cursor when you expect many rows: declare, open, fetch in a loop, close.

Same program in fixed format (what you will meet in most shops):.

Sources indicate that DECLARE is not executable, but it must appear in the source before the OPEN that uses it, and the host variables it references must be declared before it. closqlcsr(*endmod) closes cursors when the module ends. The ILE default is *ENDACTGRP, so a cursor you forget to close stays open until the activation group ends, and the next call's OPEN fails with SQLSTATE 24502 (already open). Close cursors yourself anyway.

Fetching a block of rows in one call reduces overhead. Use an array data structure.

Same program in fixed format (what you will meet in most shops):.

SQLERRD(3) (short name SQLER3) holds the number of rows fetched. The last block is usually short: Db2 then returns SQLSTATE 02000 (SQLCODE 100) and the rows it did find, so process SQLERRD(3) rows first and stop afterwards. Reading it straight after the FETCH needs no extra statement; GET DIAGNOSTICS :fetched = ROW_COUNT gives the same count but is one more statement to get wrong.

When the statement text is built at run time, use PREPARE and EXECUTE. Use parameter markers (?), never concatenated user input, to avoid SQL injection.

The statement literal is split with + because a single literal would run past column 80.

Recent findings suggest that for a one-off statement without parameters, EXECUTE IMMEDIATE :stmt is enough. A dynamic SELECT is prepared, then used with DECLARE CURSOR FOR s1 and OPEN c USING :value.

With COMMIT(*NONE) every statement is permanent immediately. With COMMIT(*CHG) (or *CS, *ALL) changes are held until you matter COMMIT or ROLLBACK.

Same program in fixed format (what you will meet in most shops):.

Tables must be journaled to be used under commitment control; otherwise the statement fails at runtime (SQLCODE -7008, SQLSTATE 55019). The CRTSQLRPGI default is COMMIT(*CHG), so a program you compile without thinking about it hits this on any unjournaled file. On PUB400 a latest SQL schema is journaled automatically, but tables created with CRTPF (see DDS to SQL DDL migration) in a plain library are not.

Industry observers note that the precompiler produces a temporary source and then calls the RPG compiler. COMMIT(*NONE) is right for batch utilities (wrap the call in CL and use SBMJOB) and read-only programs; choose *CHG for transactional programs. The SET OPTION line in the source carries the same options with the member.

According to recent reports, the samples use mylib.customer. With OPTION(*SQL) an unqualified name goes to the default schema instead of the library list.
