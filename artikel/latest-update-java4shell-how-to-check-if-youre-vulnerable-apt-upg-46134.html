📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Industry observers note that you ran apt upgrade openjdk-17-jdk, java -version printed a fresh build, and you went to lunch. Your Keycloak container still runs its own JRE, your Jenkins agent image is pinned to last month's Temurin, and the vendor appliance in the corner has a JVM you have never seen a version string for.

According to recent reports, java4Shell (CVE-2026-114938) is a heap overflow in HotSpot's AVX-512 Base64 decoder. Calif, who found it, rates it 9.2 under CVSS 4.0 and lists Keycloak, Jira, Confluence, Artifactory, Jenkins and PingFederate as pre-auth RCE in default configs. Oracle scores it 8.1 under CVSS 3.1, citing high attack complexity (Aikido). Patches shipped November 17, 2026.

Below: which Java 17, 21, 25 and 27 builds are affected, which are fixed, and four commands that find every JVM on a host or in a container image, including the ones java -version never sees.

Not in how easy it is to exploit. Log4Shell was one string in a User-Agent header. Here the overwritten bytes are a fixed pattern derived from the decoder, not attacker-chosen, and the Harness team didn't get code execution in their lab. With the default heap the write was silent across thousands of triggers; only after shrinking TLABs (-XX:TLABSize=2048 -XX:-ResizeTLAB) did they get a SIGSEGV in G1. Calif's own exploit is spray-and-retry heap grooming, and they say it is sensitive to RTT and jitter. On Lobsters someone called it "a nothingburger" next to Log4Shell, and the EPSS score quoted there was 0.00734.

I still think it's the worst JVM bug since Log4Shell, for two reasons.

First, the preconditions are boring. As a Lobsters commenter pointed out, Traefik, Envoy and HAProxy don't buffer requests by default, and Zen 4 shipped in 2022. And Base64 from strangers arrives before login all the time. Harness lists HTTP Basic headers, JWT segments decoded before the signature check, and SASL exchanges like Kafka SCRAM.

Recent findings suggest that second, and this is the Log4Shell part, the fix lives in every copy of the runtime. Log4Shell at least came down to one dependency in a pom.xml. Here you have to hunt down every JVM you ship, and most teams have no list of those.

Calif also claims finding the bug took about an hour and the first working exploit two more, for under $200 in token costs. They're holding back the per-product chains until people have upgraded. Aikido had seen no confirmed exploitation in the wild as of November 18. I wouldn't bet on that lasting.

In a recent development, ARM64 is not affected. Graviton fleets can relax. EPYC Naples, Rome and Milan are AVX2-only, as one HN commenter noted, so older boxes are out of scope too.

According to Aikido, standard Java 8 and 11 are not affected, with one exception: Oracle lists its Java SE 8 Enterprise Performance Pack build (8u511-perf) as vulnerable.

Fixed builds, from Aikido's roundup:.

According to recent reports, EOL lines are affected and don't get their own fix. Move 18-20 to 21, 22-24 to 25, and 26 to 27. Red Hat is expediting RHEL 8, 9 and 10 builds. Zulu and Microsoft number their builds differently, Aikido has no fixed build numbers for Liberica yet, and distro packages carry their own versioning, so check each vendor's advisory and don't eyeball it against Oracle's table.

Sources indicate that one Temurin gotcha: Adoptium publishes the binaries per platform as testing finishes, and the Docker Hub images only follow once every binary for that version is out. Your FROM eclipse-temurin:17-jre rebuild may pull the old JRE for a while.

All four flags need to show up. If any are missing, this host can't hit the vulnerable path. But your autoscaling group can land the same image on a Sapphire Rapids node tomorrow, so don't treat a clean dev box as proof about production.

Every JDK, JRE and jlink-built runtime has a release file at its root. Reading those files covers bundled runtimes without executing anything:.

This is where the surprises turn up: /opt//jre, jpackage'd desktop tools, an IDE's bundled runtime, the copy your monitoring agent brought along.

According to recent reports, the binary on disk doesn't matter if the process still has the old one loaded. Harness's advice is to check the running process rather than trust the image tag. Finding processes by name misses custom launchers, so match on libjvm.so instead:.

For each hit, jcmd VM.version tells you the build, and jcmd VM.flags -all | grep -E 'UseBASE64Intrinsics|UseAVX' tells you whether the fast path is on. To see what a particular binary defaults to on this CPU:.

UseBASE64Intrinsics true and UseAVX at 3 on a VBMI-capable host means you're exposed until you patch.

Distroless images don't have a shell or find, so don't bother with docker exec. Export the filesystem and read the release file out of the tarball:.

For Kubernetes, kubectl get pods -A -o jsonpath='{..image}' | tr ' ' '\n' | sort -u gives you the image list to feed into the same loop.

Harness also published a runtime checker script that compares local JDKs against the advisory builds and checks the CPU and flags; exit code 2 means a JDK is still exposed. Their post indicates it as curl | bash. Read it before you pipe it into a root shell on prod.

Calif lists both of these flags as workarounds and still tells everyone to patch right away.

Strict Base64 validation in front of the decoder (length a multiple of 4, alphabet only, padding only at the end) is a backstop. Harness notes that a loose character-class check doesn't catch the inputs that overflow.

Switching to ZGC isn't a fix either. The only exploit discussed so far targets G1, but as one Lobsters commenter pointed out, the bug isn't in G1 and can still be used for denial of service under ZGC.

My order would be: internet-facing services that decode Base64 before auth (SSO, CI, artifact repos) first, then image rebuilds, then the appliances you'll have to open vendor tickets for.
