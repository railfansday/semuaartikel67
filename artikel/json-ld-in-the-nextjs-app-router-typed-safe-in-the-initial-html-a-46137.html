Structured data is one of the few SEO tasks that lands squarely on the developer's desk. Marketing asks for "schema", someone pastes a JSON-LD snippet from a generator into the layout, and a year later the price in the markup no longer matches the price on the page.

Here is a setup for the App Router that avoids the usual problems: the markup is typed, rendered on the server, escaped correctly, built from the same data as the visible page, and tested.

Sources indicate that structured data doesn't improve rankings by itself. It makes pages eligible for rich results such as product price and availability, breadcrumbs or article details, and it helps search engines understand the entities on a page. Google requires the markup to describe content that is visible on the page; markup that contradicts the page can cost eligibility.

That last rule is the technical requirement hiding in an SEO guideline: the JSON-LD and the rendered page must come from the same source of truth.

In a recent development, in the App Router, the simplest correct approach is a plain , it ends the tag early and whatever follows is parsed as HTML. Replacing < with its Unicode escape keeps the JSON valid and the document intact. The Next.js documentation recommends the same.

The schema-dts package provides TypeScript types for the Schema.org vocabulary. It catches misspelled properties and wrong value types at build time. It does not know Google's rich result requirements, which are stricter per feature; a perfectly typed Product can still lack what Google needs for a product snippet. Types prevent typos, validators check eligibility.

Site-wide entities like your organization and website belong in the root layout, and page-level entities can reference them instead of repeating them:.

An article page can then set publisher: { "@id": "https://example.com/#organization" }. Stable @id values turn several disconnected blocks into one graph, which is easier to maintain and easier for consumers to interpret.

Industry observers note that validators are manual tools. A small check against a preview deployment catches the regressions that matter: markup that disappeared, no longer parses, or lost a required field.

In a recent development, run it against one URL per template. JSON.parse failing is a test failure too, which is exactly what you want.

Recent findings suggest that run Google's Rich Results Test on a sample of each template after changes to the markup, and the Schema Markup Validator if you also care about general Schema.org validity. Then watch Search Console's enhancement reports for latest errors.

Samples miss the errors that only occur on some products or categories, so a full crawl helps periodically.
