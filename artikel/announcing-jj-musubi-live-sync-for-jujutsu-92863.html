Announcing jj-musubi: live sync for Jujutsu

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

In a recent development, I’m pleased to announce a newly introduced source control tool, jj-musubi, that live-syncs copies of a Jujutsu (jj) repository across multiple machines. Every time jj snapshots my work, jj-musubi syncs it to every machine in moments, and also commits, rebases, fetches, and so on.

This simple capability is surprisingly powerful.

jj-musubi makes repos on multiple machines feel like jj workspaces (worktrees if you speak git).

It’s intended for use by one person who works across several machines, so it has no security model (or rather, that is the extent of its security model).

Jujutsu already treats the working copy as a commit. Running jj status records a snapshot of my edits in that commit, which jj-musubi then syncs to my other machines. I like to have my shell prompt run jj status, so in practice I rarely have to think about snapshots.

It has been revealed that jj-musubi does not write to the working copy. Each machine has its own working copy and workspaces as usual, so syncs of commits, snapshots, and rewrites can bring in newly introduced history while a build is running, without changing the files under it. On a laptop, I can work offline, and my machine will sync when I’m back on the network.

This has also proven handy when I have agents working on several machines. I can give each agent its own jj workspace on different systems, then run jj diff -r devbox/agent-1@ on the laptop to see what one of them has done so far. If one finds a bug that another needs to fix, they can coordinate and see each other’s work without overhead.

jj-musubi refers to a collection of copies of a repo as a hive.

In a recent development, I often run agents in temporary disposable VMs. jj-musubi supports this by allowing an agent to lease its repo’s membership in the hive: if it doesn’t renew that lease in time, its repo gets forgotten about, so temporary repos or vanished containers can’t just stack up and clutter things.

According to recent reports, back when I was at Meta, I kicked off the project that became Sapling and Mononoke. Sapling’s Commit Cloud gives engineers there a similar way to move work between machines, and Google engineers have something similar with an internal jj server.

Sources indicate that since then, I’d missed that everyday convenience for the machines I already use, and felt like I could get it without massive infrastructure or hosting. With jj-musubi, one machine runs a hub, and daemons exchange jj history with it over SSH. That’s almost as lightweight as you can get.

What’s tricky is getting concurrent work right. That’s already hard in any distributed source control system, and when syncs are live and we strategy for disconnected work in an unreliable network, the difficulty goes way up.

Industry observers note that as a user, I shouldn’t have to care about when exactly I can safely close my laptop after finishing an edit; all of my changes should make it through either just before I close it, or right after I reopen. No work should get lost or corrupted in the presence of interrupts, resends, delays, or machines sleeping, and the system should stay reliable even when machines go offline forever.

According to recent reports, I used Lean to prove key properties of jj-musubi’s network protocol, and tests compare the Rust code against that model. An extensive body of other tests run real jj repositories through concurrent edits, interrupted syncs, hub restarts, and a myriad of other nasty situations. Mutation and adversarial testing ensure that when bugs are injected, sensible things happen. The safety guide details all the checks (and the parts I don’t yet cover).

According to recent reports, it might sound spooky or dangerous to be able to see in-progress work on one machine from another. How can that be safe?

If you use jj in multiple workspaces, you’re already used to the novelty of being able to check out the same change in two workspaces and modify it. jj simply marks the change as divergent, but it won’t update either working copy with changes from the other until you decide to, e.g. by calling jj workspace update-stale. In jj, dealing with divergent versions of a change is similar to any other kind of conflicted merge.

jj-musubi uses jj’s existing workspace machinery, so everything will feel familiar. The only difference is that when you run jj-musubi, a workspace’s name is prefixed with the name of the machine it lives on.

In a recent development, start with e.g. a laptop and another machine that’s always on (let’s call it devbox), with a copy of a jj repo on each. On each machine, download the binary or build it yourself:.

Run musubi hub on devbox; it will keep your sync data in ~/musubi-hub. In the laptop’s repo, run musubi create --hub devbox. In devbox’s repo, run musubi join.

I provide builds for Linux, macOS and Windows, and the quick start walks through setup and the first sync. If you try it and something surprises you, I’d like to hear about it.
