An AI-managed VPS isn’t the same as a traditional managed VPS. You still get a self-managed server with full root access, but Hostinger Agent does the work you’d normally do yourself. Agent (previously called Kodee) is an MCP-powered assistant that lives in the dashboard and beside the AI web terminal, and it’s included at no extra cost. You can also connect Claude or Cursor to your server through Hostinger’s MCP server.

I gave it three tasks in plain English.

My prompt: “Check that Docker is installed, then set up a reverse proxy with a free SSL certificate so my demo-app container (port 3000) is served at https://srvXXXXXXX.hstgr.cloud.”.

In a recent development, it started by looking around: the Docker and Compose versions, which ports were in use, whether a web server was already running, and the OS release. Then it installed Caddy from Caddy’s official repository, configured the proxy and made sure ufw allowed web traffic.

Industry observers note that it read Caddy’s logs to confirm the Let’s Encrypt certificate, which arrived in about 6 seconds. Finally it tested its own work: HTTPS returned 200, and plain HTTP returned a 308 redirect. The whole task took about two minutes.

To give it a real fault, I ran docker stop demo-app and reloaded the site. Then I asked why it was returning a 502 and to fix it.

Industry observers note that in a single command, it checked the container state (Exited (137)) and searched Caddy’s logs, where it found connect: connection refused on port 3000. It restarted the container, confirmed /health and HTTPS were back, and even pointed to my docker stop in the terminal history. It also explained that --restart unless-stopped covers crashes and reboots, but not a manual stop.

A tip it didn’t mention: exit code 137 means Docker had to force-kill the container, because Node running as PID 1 ignores SIGTERM. Add --init to docker run for clean, instant shutdowns.

In a recent development, this was the most impressive answer. ufw already allowed only those three ports, but Agent noticed port 3000 was still reachable from the internet, because Docker-published ports bypass ufw rules.

Recent findings suggest that it recreated the container bound to 127.0.0.1:3000, so the app is only reachable through Caddy, and confirmed with an external port check. It left DNS, time sync and Caddy’s local admin port running, explaining that stopping them would break DNS and time sync.

Then I asked it to reboot the server. First it checked that Docker and Caddy start on boot and that the container’s restart policy was set, then it rebooted. The site came back over HTTPS without any help from me.

Nothing I asked for was destructive, so Agent just got on with it: the firewall change, the container rebuild and the reboot all ran without a confirmation prompt.

Sources indicate that the Agent panel says so upfront, noting that terminal commands can run without one. For destructive actions such as reinstalling the OS or restoring a backup, Hostinger’s FAQ says Agent always asks for confirmation first.

One thing worth knowing: to close port 3000, Agent removed and recreated my container. That was harmless for a stateless demo, but a container that keeps data without a volume would lose it. Take a snapshot before big jobs, and keep the panel in view.
