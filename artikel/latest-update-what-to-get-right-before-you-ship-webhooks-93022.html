OpenAI, Anthropic, Gemini, and Cursor are all sending webhooks now, and all four built them on Standard Webhooks, the open spec written by Svix. Downloads of the spec's npm package went from 1.7 million a month in September 2025 to 220 million a month presently.

This may be boring to hear for the nth time, but the reason is agents. An individual person checks on a running job a few times. An agent told to watch for changes checks every resource, every minute, for as long as it runs, and almost every one of those requests comes back with nothing upcoming. An agent that starts a job, polls until it finishes, and then starts the next one spends most of its time waiting: six steps with 15 seconds of polling each add 90 seconds, even when every operation is fast. Polling more often adds load, and polling less often adds delay, so there's not really a sweet spot.

According to recent reports, an event-driven API gets rid of that trade-off. It tells consumers when something changed or finished, so they stop asking. That matters most for work that runs for minutes or hours, like batch inference, fine-tuning, and video generation, and many APIs still don't offer it. Of the 57 AI APIs with long-running jobs that Svix reviewed for its State of Webhooks 2027 report, 19 make you poll for the result.

Webhooks are how most APIs push those events, and you can get a v1 out pretty fast. Making it dependable is an infrastructure problem, which is a class of problem that requires more time by default. Before you ship webhooks, you need an append-only event log behind every delivery, a fixed event format, signed payloads, retries with backoff, event IDs receivers can deduplicate on, per-endpoint isolation, and delivery logs your customers can read. If you skip one of these things, a customer is just going to bring it up later.

Each section below covers one of them with adaptable code, and Standard Webhooks works with existing verification libraries in most languages.

Recent findings suggest that if the request handler that changes the data also sends the webhook, a crash between the commit and the HTTP call loses the event, and nothing records that it should have gone out. A customer whose endpoint was down for longer than your retry window has no way to find out what they missed.

In a recent development, both problems go away if you write each event to an append-only table, scoped per customer, in the same transaction as the change. Webhooks are delivered from that table, and the same table backs an HTTP endpoint customers can read from a cursor. Svix calls this design POKE (Publish Once, Kickoff Everywhere). Build the log first: a consumer who misses a webhook needs somewhere to resume from.

Recent findings suggest that the advisory lock prevents a subtler bug. Postgres assigns sequence values at insert time, but rows only become visible at commit. With two concurrent writers, a reader can see ID 102, store it as its cursor, and then never see ID 101 when the slower transaction commits. Holding a per-customer lock until commit makes each customer's events visible in ID order.

A customer who was offline for a week asks for events after their last cursor and gets everything they missed, in order. Publish your retention period, since it limits how far back that works. The same log can also serve synthetic created events for existing records when a newly introduced integration needs to load its initial state.

Customers write handlers against your payloads, so you'll be supporting every field you ship.

Recent findings suggest that give each event an id, type, timestamp, and data. Use the log row's ID as the event ID so webhooks and the pull endpoint agree. Name types as a resource plus a past-tense action, like invoice.paid, and publish a catalog with an example payload for each type.

Emit an event for each state change a consumer would otherwise poll for. Deletions are the ones teams forget most. Long-running jobs need completion and failure events, such as export.completed and export.failed.

Adding a field is safe. Removing or renaming one breaks handlers, so ship a new type such as invoice.paid.v2 and keep sending the old one until customers have moved over.

Anyone who finds a customer's webhook URL can POST a fake invoice.paid to it. A signature lets the receiver confirm the request came from you, wasn't modified in transit, and isn't an old request being replayed.

Retries mean some events arrive twice. Usually the receiver processed the event but timed out before you saw its response, so you sent it again. Senders accept this at-least-once behavior because the alternative is dropping events, and receivers handle the duplicates.

According to recent reports, put this pattern in your docs with a note about ordering. Events in the log have a fixed order, but webhook deliveries don't always arrive in it. A retried invoice.created can land after invoice.paid. Receivers should keep whichever event has the newer updated_at, or read the pull endpoint when they need strict ordering.

Industry observers note that with a shared worker pool, one customer's hanging endpoint can tie up every worker for the full timeout while other customers' events wait. Limit concurrent deliveries per endpoint, and slow down delivery to endpoints that keep failing.
