Recent findings suggest that you can build an AI agent in an afternoon now. Pick a model, write a loop, hand it a few tools and watch it book a meeting or open a pull request. The demo works, and everyone in the room is impressed.

Then it meets a real system with real permissions and real customers, and things get quiet. Gartner has predicted that over 40% of agentic AI projects will be canceled by the end of 2027, citing rising costs, unclear business value and inadequate risk controls. Its analyst Anushree Verma described most current projects as early-stage experiments that are driven by hype and often misapplied. A forecast is not a measurement, but the pattern it describes matches what many teams report: the agent is rarely what breaks. The workflow around it is.

A year or two ago the model was often the differentiator. Today many teams can reach the same frontier models through the same kinds of APIs, so if the intelligence is similar, the advantage has to come from somewhere else.

Anthropic’s guide to building effective agents reached a similar conclusion after working with teams building agents. It reports that the most successful implementations were not using complex frameworks or specialized libraries, and were building with simple, composable patterns instead. It also separates workflows, where code paths are predefined, from agents, where the model chooses its own steps, and advises using the simplest approach that works and adding complexity only when measurement shows it helps.

That should change where developers spend their time. Frameworks matter, but three less glamorous questions matter more: what can the agent touch, when does it stop, and who checks its work?

Industry observers note that the OWASP guidance on Excessive Agency names what goes wrong here. It covers agents that can do more than they need to, and it traces the problem to three root causes: excessive functionality, excessive permissions and excessive autonomy.

According to recent reports, in practice this looks familiar. An agent that only needs to read tickets is given a token that can also close them. A summarization tool connects with an admin account because that was quicker to set up. A generic “run shell command” tool is exposed when the agent only ever needs to write one file.

It has been revealed that the fix is ordinary engineering discipline applied to a new kind of caller. OWASP’s recommendations include giving each tool only the functions and permissions it needs, preferring narrow tools over open-ended ones, running actions under the user’s own scoped identity, requiring human approval for high-impact actions and enforcing authorization in the downstream system rather than letting the model decide. The last point is the key one: a model can be talked out of a rule written in a prompt, but an API that checks scopes cannot.

According to recent reports, the Model Context Protocol has become a common way to connect agents to tools. Anthropic donated MCP to the Agentic AI Foundation, a directed fund under the Linux Foundation, in December 2025. Block contributed goose and OpenAI contributed AGENTS.md as founding projects, which shows how central the ecosystem has become.

A standard protocol is good news. It also means you can install a tool server in minutes and expose every endpoint of your glitch tracker, repository or CRM to your agent, whether it needs them or not. Easy connection quietly pushes more power to the agent.

Recent findings suggest that the protocol’s own security best practices document covers several relevant risks, including confused deputy problems in proxy servers, token passthrough, local server compromise and scope minimization. For scopes, it recommends starting with a minimal set and elevating only when a privileged operation is first attempted, and it lists wildcard or omnibus scopes as a common mistake.

Industry observers note that A sensible rule is to treat every tool server like a third-party dependency running with production credentials. Review the tools it exposes, switch off the ones the workflow does not use, pin versions and log every call. If you would not let a newly introduced contractor do it on day one, the agent should not do it either.

Human-in-the-loop design is often implemented as “approve everything”. That fails in a predictable way: people click approve forty times a day and stop reading by lunchtime.

According to recent reports, A better rule is to gate on reversibility. Reads run freely, reversible writes run and get logged, and irreversible actions such as sending, paying or deleting wait for a person. Everything leaves a trace that a developer can replay when something looks odd. The gate above implements exactly this split.

Some teams build these pieces themselves, and others buy them. Elsewhen, a London-based consultancy that works on agentic operations for enterprise teams, describes its own service in similar terms. Its page lists approval gates where people sign off consequential decisions, an audit trail of what each agent read and which systems it touched, and a shared layer of permissions and guardrails that is reused across workflows. Elsewhen also claims its Planet Agent report found that agents tend to start at the edges of an organization, where tasks are repeatable and mistakes are cheap, and then move toward the core. Treat that as the vendor’s own finding, and ask for the underlying evidence before relying on it.

According to recent reports, the same logic applies outside engineering. The first question worth asking any AI partner is what they have actually put into production, and developers can ask the same of their own work.
