In a recent development, OAuth consent phishing never asks for a password. The attacker registers a multi-tenant application, sends the victim a link to the real login.microsoftonline.com authorize URL, and waits for the user to click Accept. Every step the victim sees is genuine, including MFA, which is why this attack class keeps working against organisations that think they are covered by phishing-resistant authentication. What matters is not who the user is, but what they just authorised an unknown app to do.

According to recent reports, this guide covers how the attack works at the protocol level, the Entra ID consent settings that close it, a KQL detection you can deploy today, and the exact commands to clean up after a successful grant. For the related token-theft pattern that abuses RFC 8628 instead of the authorization code flow, see OAuth Device Code Flow Security.

This is the same refresh-token persistence problem seen in MFA bypass attacks, except here Microsoft itself issued the token to the attacker's client at the user's request.

Microsoft documents three user consent settings in Entra ID: do not allow user consent, allow consent only for apps from verified publishers requesting low-impact permissions, or let Microsoft manage your consent settings (the default for newly introduced tenants, backed by the microsoft-user-default-recommended policy). Check which one your tenant is on before assuming you are protected.

Sources indicate that if this returns ManagePermissionGrantsForSelf.microsoft-user-default-legacy, users can consent to almost anything that does not require admin consent. Move to a stricter setting.

This is the strongest control and fits regulated tenants. Pair it with the admin consent workflow below, otherwise users hit a dead end and look for workarounds.

Note the weakness: it depends on the verified-publisher signal, and the permission classification (which scopes count as low impact) is something you must review rather than assume. Mail.Read should never be classified low-impact in a tenant that cares about mailbox confidentiality.

In the Entra admin center go to Enterprise applications > Consent and permissions > Admin consent settings and set Consumers can request admin consent to apps they are unable to consent to to Yes, then pick reviewers. Users get a request button on the consent prompt instead of a block, and reviewers see the app, publisher and exact scopes before approving. Make sure reviewers know to decline anything requesting offline_access plus mail or file scopes from an unverified publisher.

Microsoft's risk-based step-up consent turns a user consent request that Microsoft flags as risky into a requirement for admin consent. It only changes behaviour when user consent is enabled, and the BlockUserConsentForRiskyApps setting is controlled through the Graph PowerShell beta module with the Privileged Role Administrator role. Treat it as a useful extra layer, not a substitute for restricting consent: the flag is advisory and attackers iterate until their app is not flagged.

Sources indicate that consent phishing succeeds because identity teams spend their effort on authentication strength and treat authorisation as a user decision. Passkeys and number matching do nothing here: the user authenticated correctly and then authorised the wrong party. The durable fix is making consent an administrative decision for anything beyond trivial scopes, and watching the audit log for the exceptions. If your org also exposes OAuth-based integrations to AI agents, the same principle applies to what those agents may be granted; see MCP OAuth 2.1 authentication and the OAuth 2.1 security best practices guide.
