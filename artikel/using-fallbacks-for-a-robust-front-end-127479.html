Using Fallbacks for a Robust Front-End

Anyone who has been working in web development for a while will be familiar with this now-legendary meme from xkcd. It illustrates just how fragile the technical infrastructure of a website or app can be.

That’s why it’s important to use fallbacks to build a robust front end, either to quietly and discreetly avoid the error or to communicate it to our consumers.

According to recent reports, the issue of robustness is so vital that it is actually one of the four principles of the Web Content Accessibility Guidelines (WCAG)! So how can we provide a modern front end without excluding people who use browsers and hardware that are only partially compatible or not compatible at all?

The answer lies in implementing multiple safety nets in HTML, CSS, and JavaScript, so that we are prepared for the worst-case scenario and can provide our owners with the best possible experience.

The main difference between the use of fallbacks and progressive enhancement lies in the directions in which the two approaches aim.

While progressive enhancement is about automatically making certain features available as long as they are supported (forward), fallbacks are about what happens when something is not available or accessible (backward).

Recent findings suggest that for example, we can offer a shiny fresh CSS feature that makes interacting with our website even more enjoyable. But if this feature isn’t available in some browsers, no one will notice, because a version that’s supported by older browsers is available instead. Progressive enhancement in action!

Another example: If JavaScript cannot be loaded for a critical application, we provide a fallback that either offers basic functionality or, at the very least, displays a message explaining what the problem is.

While one doesn’t necessarily exclude the other, their approaches are quite different. My personal recommendation is to always work with progressive enhancement as a guiding principle and to consider fallbacks whenever possible.

To evaluate new features intended for production, we must first determine the extent to which a feature is supported.

Sources indicate that since 2023, the Interop project has been in place, in which major browser vendors collaborate to release fresh features for the web platform more or less simultaneously. This serves as a general overview.

Related to this is the Baseline project, which shows, for specific features, the extent to which they are supported and how long they have been available. However, it is extremely important to note that it does not track browser support for accessibility features built into the web platform!

Another vital resource for checking compatibility is Can I Use. Here, you can get a quick overview of browser support for various features.

Industry observers note that let’s start with the foundation of the World Wide Web: HTML. Modern tech stacks place a strong emphasis on client-side rendered JavaScript, which can offer many benefits to users in more complex applications. However, there can be just as many reasons why JavaScript might fail to load, so we need a strategy to address this.

It has been revealed that in the event of a total failure, we should redirect users to an appropriate error page where they receive information about what went wrong and what not only they, but also we, can do to prevent this in the future. My experience so far at various companies has been that the topics of fallbacks and robustness haven’t played as prominent a role as they really should have.

This is surprising, because as we’ve learned, it doesn’t take much to implement various safety nets on the front end, as long as you think ahead about what (shouldn’t) happen if something goes wrong.

HTML, CSS, and JavaScript provide us with specific elements and functions to ship robust code and thus avoid upsetting our users and, in the worst case, causing them to turn away from us.
