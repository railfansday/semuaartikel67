Java4Shell is a reason to use Java

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

It has been revealed that we're less than a day into dealing with "Java4Shell", an issue stemming from how the Java Virtual Machine intrinsifies Base64 encoding code. If you have a Java deployment you haven't updated yet, add -XX:-UseBASE64Intrinsics to the VM flags. Then upgrade your VM to a version where the issue is patched when you can.

Industry observers note that this is just one in a string of high profile outages and vulnerabilities. AI is a good fuzzer, people are finding latent problems with much lower effort than the past. People are pretty worried about this because we're all pretty sure there are more latent problems to find.

Vulnerabilities tend to be bigger problems when they stem from native code, and they tend to be widespread problems when they come from dependencies many people share.

Recent findings suggest that java4Shell is both of these things. A lot of people use Java and the problem stems from a handwritten assembly intrinsic. Fun times.

It has been revealed that but, for a moment, lets say we trust the VM. It is a significant dependency, but it is only one dependency. We can all agree to audit it more closely, reduce the amount of native code in it, proactively run AIs against it, etc. Of course.

Normal Java programs are memory safe. If you use a library which wants to call native code you will get a warning, later a hard error, unless you the person using the library adds --enable-native-access=the.specific.library to their command-line options. This means even with a sprawling dependency tree, which is a problem for all programming language ecosystems, you can know your exact exposure to native code and what dependencies you need to audit more closely.

It has been revealed that compare that to C#, which lets any dependency write assembly inline. Python, JavaScript, Go - everything speaks C and lets any one of your dependencies bring along native code. As we are all learning the hard way, this carries risk.

It has been revealed that not only are Java programs memory safe. They are also fast. The exact mechanism which caused Java4Shell (the ability for the VM to swap out normal Java code for native code) combined with JIT compilation can make the actual performance of a Java program competitive with C. Sometimes a Java program can even be faster. A JIT compiler knows what code paths are actually taken and can optimize around them. They can even refocus what is optimized if the workload changes. It is pretty cool!

Somewhat recently I went through the raytracing in a weekend book with Java.

Benchmarks can be problematic, I know. What I want you to take away is that the JVM makes your code fast enough that most people don't need native code. Unlike, to take a potshot, CPython. There everything is slow as molasses unless you make it a native extension.

So if you are worried AI is going to find security problems with your code, use Java. The problems are likely to be less severe.

Or use Kotlin, Clojure, JRuby, etc. Whatever. Most of what I talked about applies to all of them. Its only what I didn't talk about (the module system) that is Java specific.
