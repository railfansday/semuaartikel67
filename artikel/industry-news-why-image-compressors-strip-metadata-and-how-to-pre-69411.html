If you have ever run images through a compression pipeline and discovered the EXIF data came out empty, the explanation is usually straightforward: the compressor never handled the metadata in the first place.

Image compression operates on pixel data. Metadata — EXIF, IPTC, XMP, GPS coordinates — is stored in structurally separate sections of the file. Whether those sections survive compression is entirely a function of how the tool is built.

Recent findings suggest that JPEG files use marker segments to organize data. The pixel stream starts at the SOS (Start of Scan) marker. Metadata lives in application markers:.

Low-level libraries like libjpeg and libjpeg-turbo process only the pixel buffer. They do not automatically parse or carry over APPn markers. To preserve metadata, the developer must explicitly intercept markers during reading (via jpeg_save_markers()) and reinject them during writing (via jpeg_write_marker()).

Sources indicate that metadata behavior varies by library and configuration. Some image libraries strip metadata by default, while others can preserve it when explicitly configured. For example, Sharp removes metadata by default unless preservation options such as keepMetadata(), keepExif(), or keepXmp() are used.

PNG files store metadata in ancillary chunks:.

Recent findings suggest that PNG compression itself is lossless — optimizers like OxiPNG reorganize the pixel data more efficiently without changing it. But whether the metadata chunks are preserved depends on the optimizer's implementation.

WebP uses a RIFF container with dedicated chunks:.

Sources indicate that IPTC is not part of the WebP specification. When converting from JPEG to WebP, EXIF and XMP can be carried over, but IPTC fields have no standard container in WebP.

The compression library does not handle it — if the tool wraps libjpeg without marker handling or uses HTMLCanvasElement.toBlob() without separately preserving and reattaching source metadata, the output file will have no metadata regardless of the input.

Deliberate size optimization — some tools strip metadata to save a few kilobytes per file.

Format conversion side effects — converting between formats (JPEG → WebP, TIFF → JPEG) can drop metadata fields that the target format does not support.

Canvas-based workflows operate on decoded pixel data rather than the original file container. Exporting with canvas.toBlob() or canvas.toDataURL() creates a newly encoded image and does not automatically carry over the source file's EXIF, IPTC, or XMP metadata. Applications that need metadata preservation must handle and reattach that metadata separately.

Recent findings suggest that tools that use WebAssembly-based encoders (MozJPEG, libwebp, OxiPNG) can produce better compression results and can handle metadata if the implementation explicitly copies the relevant sections. The GeoImageTagger Image Compressor uses WASM encoders for compression and is designed to preserve supported metadata as a separate step, including post-compression verification.

Recent findings suggest that before compression — inspect the original file's metadata. The Metadata Viewer reveals EXIF, IPTC, XMP, and GPS fields for any supported image.

It has been revealed that if fields are missing — use a metadata editor to restore them, or switch to a compressor that preserves metadata. The Metadata Editor handles writing EXIF, IPTC, and XMP fields.

Metadata preservation is not always the right choice. Personal photos shared publicly may contain GPS coordinates and device information. For privacy-sensitive images, deliberately removing metadata is the correct approach. The EXIF Remover handles selective removal without re-encoding pixels.
