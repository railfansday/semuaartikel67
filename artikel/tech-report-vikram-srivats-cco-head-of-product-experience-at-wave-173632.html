Industry observers note that vikram Srivats is Chief Commercial Officer and Head of Product Experience at WaveMaker. His career spans handheld computing, wireless technology, IoT, and enterprise software. He focuses on the architectural and organizational requirements that turn emerging technologies into maintainable applications at enterprise scale, with an emphasis on code ownership, design consistency, and engineering discipline.

Recent findings suggest that waveMaker provides an agentic application-generation platform for enterprise development teams. Its two-pass approach separates AI-assisted interpretation of design intent from deterministic code generation, using a structured intermediate representation. The platform combines agent, visual, and code-editor workflows with reusable components and integrations designed to fit existing development practices.

In a recent development, your career has taken you from handheld computing and wireless technology at Mindtree to IoT, enterprise software, and now AI-driven application development. How has that progression shaped your view of what it takes for an emerging technology to become genuinely useful at enterprise scale?

According to recent reports, every wave I’ve watched from up close — handheld computing, wireless, IoT, cloud applications — seems to follow the same pattern. The technology does something impressive in a controlled setting. Then it hits enterprise scale, and the gap becomes visible: what it does in a pilot versus what it does reliably in production at a massive user scale, under stringent security audit, integrated with systems built a decade ago, and maintained by engineers who weren’t associated with the tech development itself.

The companies who survive (and thrive) solve the hard architectural problems, not just the interesting, shiny ones. Enterprise scale punishes pure optimism and speed, and rewards discipline and rigor. A technology earns the right to be called enterprise-grade when it performs consistently, survives review, and can be changed by someone who didn’t build it.

According to recent reports, AI coding tools can generate functional applications remarkably quickly. Where do you see the biggest gap today between code that works in a demo and software that is actually ready for production?

Recent findings suggest that the gap is structural. Watching an AI tool generate a working UI in thirty seconds, you’re seeing the easy part: assembling recognizable patterns into something that renders. You’re not seeing consistent adherence to your design system, correct authentication and authorization flows, proper error handling across edge cases, clean integration with your existing APIs, code your security team can audit, or output another developer can modify six months from now without the original author present.

The data backs this up. CodeRabbit’s analysis of production pull requests found AI-generated code introduces 1.7 times more problems than human-written code. Veracode’s testing found security vulnerabilities in roughly 45% of AI-generated output. Google’s DORA research highlighted a 7.2% drop in delivery stability among teams using AI coding tools. The fix is the right architecture around AI that can actually guarantee quality and cost with speed.

According to recent reports, prompt-driven development has made software creation much faster and more accessible. What are the limitations of relying primarily on prompts once applications become larger, more complex, and business-critical?

Prompt-driven development is single-pass: describe intent, the model generates output, you hope it matches requirements. That works for self-contained tasks. It breaks down as complexity grows.

According to recent reports, the core problem is that prompts carry no persistent context about your organization’s standards. An LLM has no memory of the architectural decision your team made many sprints ago — every prompt starts fresh. You get stylistic inconsistency across components, duplicated logic, security configurations that drift from established patterns, and a codebase that gets harder to reason about with each addition. Enterprise applications are living systems built on years of accumulated decisions. Prompts generate for the moment, not the long term, and that mismatch leads to architectural drift or worse, no architecture at all. If you were building a skyscraper, would you skip architecture and planning?

Industry observers note that generative AI is inherently non-deterministic, while enterprises generally want predictable and repeatable software. How significant is that tension, and what approaches can development teams use to control it?

The tension is real. Non-determinism in a creative tool is a feature. In a compiler, it is almost a fatal flaw. Applying LLM-based generation directly to production code treats a creative tool as a compiler, and the results are predictably unpredictable.

The architectural fixes: give the model a narrower, well-defined output space instead of letting it generate arbitrary code. Use an intermediate representation that validates intent before code gets emitted. Build guardrails that encode your organization’s standards so the model operates inside them. Non-determinism is valuable in the reasoning phase, figuring out what to build, and destructive in the generation phase, actually building it. Separating those two phases matters.

It has been revealed that waveMaker uses an intermediate representation and a two-pass approach rather than generating production code directly from prompts. Why do you believe separating AI reasoning from deterministic code generation can produce more reliable applications?

According to recent reports, the two-pass compiler is one of the foundational breakthroughs in software engineering. Early compilers were single-pass: read source, emit machine code, hope for the best. They were fast but fragile. They couldn’t reason about the whole program before committing to output. The move to two-pass — separating analysis from synthesis — is what gave us the reliability and optimization that made modern software possible.

Industry observers note that AI code generation repeated the single-pass mistake. WaveMaker applies the same historical fix. In the first pass, AI agents constrained by a Model Context Protocol (MCP, trained on a decade of production application patterns) convert design intent and natural language into WaveMaker Markup Language (WML): a compact, structured, language-agnostic intermediate representation that captures what the application should do without committing to how it gets implemented. In the second pass, a deterministic, template-based code generator converts WML into production-ready Angular, React or React Native code. Same WML in, same code out, every time. No hallucinations, no phantom dependencies.

It has been revealed that the AI does what it does well: understand intent. The deterministic engine does what it does well: execute reliably. Neither phase carries the full burden of correctness alone. InfoWorld’s published analysis of this lays out the full technical case.

How should AI-generated applications incorporate an organization’s existing design systems, architectural standards, APIs, and reusable components rather than creating something fresh with every prompt?

Every time a tool generates a slightly different button style, skips your established component library, or builds a newly introduced API integration pattern instead of reusing an existing one, it adds technical debt that takes engineers months to reconcile.

The fix is encoding organizational standards as hard constraints, not prompt suggestions. WaveMaker’s component library propagates design tokens from Figma directly, so your design system isn’t something you describe to the AI: it’s actually the space the AI operates in. API integrations via OpenAPI and Swagger get registered once and reused consistently. Security configurations — RBAC, SSO, OAuth, MFA — are set once and applied deterministically across every generated application. Your standards become the rails the system runs on.

In a recent development, security, testing, version control, and CI/CD are already deeply embedded in enterprise development. How should AI application-generation tools fit into these workflows without creating an entirely separate development process?

They shouldn’t create a parallel workflow. The moment an AI tool requires a separate repository, a separate deployment pipeline, or a separate security review process, it adds complexity instead of removing it. Enterprise teams have spent years building the practices around Git, CI/CD, and security scanning that make delivery reliable. Any AI layer that disrupts those workflows gets rejected, correctly.

Industry observers note that instead, AI generated code should live in your Git repository, run through your existing CI/CD pipelines, and get reviewed by your security teams using the tools they already use. There should be no proprietary runtime, no vendor-managed deployment, no lock-in that requires staying on the platform to keep applications running. The generated code should be yours: readable, auditable, maintainable by any engineer who knows the open standards framework.

Industry observers note that one concern with AI-generated software is the technical debt that may emerge months or years later. What needs to happen at the generation stage to ensure that developers can understand, modify, and maintain the resulting code over time?

In a recent development, yes, technical debt from AI generation doesn’t surface immediately. This can be in the form of inconsistent patterns, undocumented assumptions, duplicated logic with subtle variations, and dependencies nobody can explain.

It has been revealed that what has to happen at generation time is disciplined structure. Generated code should follow consistent, recognizable patterns, because consistency is what lets someone who wasn’t there at creation understand it. It should use your established components. And if you have an intermediate representation, that itself is a readable artifact that an engineer who needs to understand why an application behaves a certain way can inspect and trace the reasoning back to the original design intent. That traceability is what separates maintainable generated code from a black box.

Most AI coding assistants have initially focused on making individual developers more productive. What changes when AI development systems are designed for entire engineering teams, including architects, designers, security teams, and developers?

Recent findings suggest that almost everything changes. Individual productivity tools optimize for one loop: one developer, one task, fast feedback. Team-scale systems solve a different problem. How do you maintain consistency across dozens of developers working in parallel? How do an architect’s decisions propagate to every component, not just the ones they personally touch? How do designers get a voice in the output without writing code? How do security teams set standards once and have them enforced automatically across everything generated?

That change from tools that assist to platforms that constrain productively, is the real design challenge. Architects, designers, developers, and security teams need different interfaces to the same underlying system. Architects define structural patterns. Designers watch their design tokens carry through every generated component. Security teams configure authentication once. Developers move between agent mode, visual mode, and code editor mode depending on the task. Everyone operates in the same system, on the same codebase, with the same standards enforced. Scale only happens because the platform was designed for teams, not individuals.

As agentic development matures, which parts of the software development lifecycle do you expect AI agents to take greater ownership of, and which decisions will continue to require human engineering judgment?

According to recent reports, agents will take increasing ownership of the translation layer: converting human intent into structured artifacts. Figma designs into component specifications. Business requirements into data models. API contracts into integration stubs. These are tasks where the input is well-defined, the output space is constrained, and correctness can be verified. Agents will also get better at producing a starting point that’s 80% correct and needs human refinement — faster and better than a blank page.

What will remain with human engineers is anything involving competing values. Should this feature prioritize accessibility or performance when you can’t have both? Should this architecture optimize for extensibility or simplicity given where the product is likely to go? Should this security trade-off get made given the organization’s risk appetite? Agents can inform those decisions. They can’t make them. The most dangerous outcome of agentic AI is assuming that because an agent can make a decision, it should. The best engineering organizations will use AI to move faster on what can be specified, and preserve human judgment for what requires it.
