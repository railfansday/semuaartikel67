It has been revealed that this attack uses WebRTC, the technology that allows you to make video calls in your web browser. WebRTC lets a web page open its own channel to another party and pass data (e.g. audio/video packets) over it. It has likely been used (both to load the skimmer and to send the stolen card details out) because security rules and monitoring tools often do not watch this communications channel as closely. For example, Meta briefly used WebRTC in a creative way in 2025, according to researchers looking at the technology as a compromise vector. This form of attack appears to target mobile devices, and we only saw the server enable the skimmer on checkout pages, so desktop checks and homepage scans would likely not see it. The skimmer's traffic appeared to run through Cloudflare's relay, so it would blend in with the WebRTC traffic and hide its true endpoint.

Recent findings suggest that how the kit is designed to work on a store page, in 7 steps. Only step 4 is an ordinary web request, which a connect-src rule can block; steps 5 to 7 run over the WebRTC data channel, outside connect-src.

The loader gets onto the page through a consent-banner setting, a retailer CDN file, a shared marketing pixel or the store's own HTML.

It loads Insds.js or gtage.js from an Amazon S3 bucket.

It runs only on small or touch screens. The Samsonite version runs on /checkout only.

GET /_cf/ice fetches the relay details, and POST /_cf/rel sends the WebRTC offer, to a brand-named northbridgeads[.]com host.

Every exchange that returned relay details used turn.cloudflare.com. The malefactor's answers listed only Cloudflare relay addresses; through that relay it sends code and receives data.

The skimmer arrives in chunks over the channel, is checked against a SHA-256 digest, then run with eval.

We saw the skimmer delivered in three different ways across five websites run by different companies, and all of them appear to rely on the same attacker infrastructure. That makes it likely that other sites are affected too, so we encourage online retailers to check their own sites for the signs below.

This attack takes advantage of a few critical design decisions in websites that, if improperly configured, allow malicious actors to broadly deploy and trigger exploits across the open web.

According to recent reports, loading third-party tracking pixels on checkout, payment and login pages is far too common a practice today. Each pixel can run whatever code its vendor's file holds, including a skimmer, and whoever controls that file can change it without the site noticing. Every site should review which tracking pixels load on pages that take payment or sign-in details, who can change those files, and whether they need to be there at all.

A similar weakness was exploited at scale on 16 November 2026. An attacker reportedly used a flaw in Optimizely's Web Experimentation product to add malicious code to customers' projects, and Optimizely's own servers delivered it to visitors of 178 organizations' sites, including Zoom, the BBC and CNN, with no change to those sites' own code.
