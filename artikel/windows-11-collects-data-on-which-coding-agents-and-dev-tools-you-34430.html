Windows 11 collects data on which coding agents and dev tools you use

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Industry observers note that I recently asked AI to help me look through the latest Windows binaries for undocumented features and functionality. Among the leads it turned up, one list immediately caught my attention: coding agents such as codex.exe, claude.exe, copilot.exe, and cursor.exe, alongside familiar developer tools such as python.exe, dotnet.exe, gcc.exe, and code.exe.

Why would a Windows system DLL need a list of coding agents and developer tools?

In a recent development, the names were in MissionControlAggregator.dll. I asked the agent to follow the references and dig into what the DLL actually does. That led from a handful of string comparisons to a running Windows component that records which coding agents and developer tools have been used, saves that information locally, and reports it to Windows Diagnostics. And unless you have opted out of the “optional” diagnostic data (which is enabled by default), the data is uploaded to Microsoft.

I shared the initial finding on X. This post includes more details about the investigation behind it.

Opening the DLL in Binary Ninja made the first lead easy to see. These were explicit executable names embedded in a Windows component:.

Following the references demonstrated that the names were used in comparisons. There are four CLI-agent slots checking copilot.exe, claude.exe, codex.exe, and agy.exe, with extensionless equivalents on the WSL route. Five desktop-agent slots check github.exe, claude.exe, codex.exe, cursor.exe, and antigravity.exe.

The compiler-generated C++ names are unwieldy, so I will call these functions executable-name matchers. For reference, one related matcher is std::_Func_impl_no_alloc<, bool, std::basic_string_view> const&, Microsoft::Diagnostics::MissionControlAggregator::Utils::AppType>::_Do_call. The screenshot shows another lambda instantiation performing the same kind of name comparison.

The feature guarding the upcoming agent checks has a particularly direct name: CLICodingAgentUsage, feature ID 62580080.

In a recent development, and the list extends beyond AI agents. The same component checks for node.exe, python.exe, dotnet.exe, gcc.exe, clang.exe, gdb.exe, javac.exe, devenv.exe, and code.exe, among others. Those checks feed broader developer-tool categories. Some of these checks also verify the publisher: the Node.js slot expects Node.js Foundation, Python expects Python Software Foundation, and the .NET and Visual Studio slots expect Microsoft Corporation. The compiler/debugger group containing GCC and Clang has no additional publisher check in this path.

Sources indicate that for Windows programs, it consumes KernelProcess.AppStateChangeSummary and Win32kTraceLogging.AppInteractivitySummary. These provide application identities that its handlers parse and pass to the matchers. For WSL, it consumes Microsoft.Windows.Lxss.Manager.Exec and ExecCritical, using the imageName field. A regular Windows codex.exe can therefore reach the CLI-agent checks through the app-state summary route; this is not limited to Linux programs running inside WSL.

The relevant flow looks like this:.

A successful match sets a slot in the aggregator’s state. Later, ReportCohorts<12,4,5> turns those slots into bitsets and emits a report named Segments.SubCohorts. The numbers correspond to twelve broader tool categories, four CLI agents, and five desktop agents.

Recent findings suggest that ETW (Event Tracing for Windows) is the mechanism carrying that report. In this case, it is a self-describing TraceLogging event. Rather than writing the executable names into every report, the component assigns each category a bit. A set Codex bit means the matching tool was observed during the reporting window.

In a recent development, the source events also include runtime, time in focus, interaction counters, and resource usage. This component appears to discard those details and record only a bitmap of which agents were observed. The report’s timestamps describe the collection window, not how long each agent was used.

Although I found no prompt text or source code in this report, collecting which agents and developer tools someone uses already has significant privacy implications.

Recent findings suggest that strings and code are a useful lead, but I wanted to see the component running. I checked my Parallels Windows 11 ARM64 VM, build 26200.9974. Its MissionControlAggregator.dll was version 10.0.26100.9818, and CLICodingAgentUsage was already enabled as a service experiment. I had not manually enabled the feature.

DiagTrack, the Connected User Experiences and Telemetry service, was also already running with its startup type set to Automatic. It starts a separate AggregatorHost.exe process, and that process loads the DLL. The following administrative PowerShell commands show the service, its child process, and the loaded module:.

The process IDs connect the pieces: DiagTrack runs in process 10148, which is the parent of AggregatorHost.exe, process 1500; the module listing places MissionControlAggregator.dll inside that child.

It has been revealed that to test the finding in practice, I copied cmd.exe to a file named codex.exe and ran it in the interactive Windows session. The name alone was enough for the component to recognize it as Codex.

I captured an AppStateChangeSummary for the running process from the KernelProcess provider ({2839ff94-8f12-4e1b-82e3-af7af77a450f}), with LaunchCount=1 and TerminateCount=0. The aggregator’s saved state contained the value 2 in CLI slot 2, the Codex slot. A separate run without an additional ETW trace also set that slot, confirming that detection worked through Windows’ existing diagnostic collection.

The report normally follows a roughly daily boundary. To capture it immediately, I temporarily moved the saved reporting-window start 25 hours into the past and restarted DiagTrack with a trace listening for the aggregator. The resulting Segments.SubCohorts event contained:.

Industry observers note that the value 4 is 1 << 2: the Codex CLI bit. The name had made it through the input summary, the matcher, the persisted state, and the emitted report.

Recent findings suggest that I also tested the developer-tool path separately, using a copy of cmd.exe named gcc.exe. It set developer-tool slot 3. With optional diagnostic data allowed, I found the resulting Segments.SubCohorts event in DiagTrack’s upload queue with SubCohorts: [8] (1 << 3). This is the compiler/debugger category shared by GCC, Clang, and related tools, rather than a separate bit for each executable.

It has been revealed that an ETW event by itself would not establish that anything leaves the machine. ETW is used for plenty of local diagnostics. The more revealing question was who was listening to this particular report.

The first subscription, for KernelProcess, had MatchAnyKeyword=0x400000000002, which includes the summary’s 0x400000000000 keyword. The second, for Microsoft.Windows.MissionControlAggregator, had MatchAnyKeyword=0xe00000000000, which includes the report’s 0x800000000000 keyword. Both had level 255.

Sources indicate that the subscription showed where the report could go. To check whether Windows actually queued it for transmission, I inspected DiagTrack’s EventStore.db and decompressed the JSON batches in its AsimovEvents table. This revealed an important condition: the agent-usage report is treated as optional diagnostic data.

When optional diagnostic data is allowed (enabled by default in the US setup I tested), Windows queues the coding-agent usage report for upload to Microsoft. I verified this by finding the agent event itself in DiagTrack’s upload queue:.

I checked this with a clean installation of Windows 11 Home ARM64 using the latest official ISO, with the region set to the United States. Before changing any privacy settings, the Diagnostic data toggle was already enabled and labeled Include Optional. After completing setup with those defaults, AllowTelemetry was 3, confirming that optional diagnostic data was enabled.

Sources indicate that optional diagnostic data is therefore enabled by default, at least in the US setup I tested. If you did not opt out of it during installation or disable optional diagnostic data later, it is still enabled and your coding agent usage data is being uploaded. You can decline optional diagnostics during setup or turn off Send optional diagnostic data later under Settings → Privacy & security → Diagnostics & feedback. Microsoft’s diagnostics and privacy guide explains how to change it.
