According to recent reports, A few years ago, CUB3D demonstrated unsigned code execution on the iPod nano 6G and 7G through ipod_sun, a font-based exploit. Whether the same approach would work on the 5G was still an open question.

I wanted to get Rockbox running on the nano 5G, so I set out to adapt the exploit. My motivation was simple: an up-to-date music player without an internet connection. I built a fully untethered boot chain that loads Rockbox from the nano 5Gâs NAND, with no computer or button sequence needed after installation. I also found a way to make the existing exploit fully untethered on the nano 7G, and likely the 6G too.

In a recent development, existing DFU exploits, including q3kâs wInd3x, provide code execution on the nano 5G, but booting custom code this way requires a computer each time. I used wInd3x to explore the device and develop a convenient, fully untethered exploit. The firmware details below refer to the latest nano 5G firmware, 1.0.2 (34A20020).

The nano 5Gâs NAND flash appears through a flash translation layer (FTL) as a logical disk with 4 KiB sectors. Its partition table separates a small private area for persistent device state, a firmware partition containing boot programs and resources, and a data volume for user files. The firmware partition has a directory of named images; the fonts live inside rsrc, a resource volume formatted as FAT16.

The original ipod_sun chain combines a resource-validation bypass with a font-parser vulnerability. Appleâs firmware directory identifies the normal operating system as osos, the disk-mode program as disk, and the resource image containing fonts as rsrc. The disk-mode boot path does not request the resource signature check used by normal OS boot.

In a recent development, swapping the disk and osos directory entries exploits that difference: selecting disk mode now releases Appleâs regular OS under the disk-mode policy. The OS still reads its fonts, but the bootloader has not required a valid signature for the modified resource image.

It has been revealed that the font then triggers CVE-2010-1797, the FreeType CFF stack-overflow vulnerability also known through the star exploit. A malformed font program corrupts the parserâs stack and redirects execution. My 5G port adapts that technique to the deviceâs font and execution context.

Recent findings suggest that the swapped images remain on disk, but each restart still requires choosing disk mode with the deviceâs buttons. A normal boot selects the other entry. I wanted a better experience, with the modified font loading through the normal OS path.

It has been revealed that the private-status tool verifies the existing header and tag, constructs the updated record, and obtains its upcoming tag from the device. It rechecks the partition table and header before writing, then flushes the write and reads it back. The tool writes a complete 4 KiB logical sector even though the bootloader only consumes the smaller header. This works on nano 5G hardware.

Recent findings suggest that once the private record and modified font are installed, they remain in NAND across restarts. emCORE and the host computer are needed for the installation workflow, not for each subsequent boot.

According to recent reports, reaching the font parser automatically solved persistence. The next constraint was fitting something useful inside the font. I wanted it to load Rockbox from storage, so the payload needed a NAND driver, a flash translation layer, a filesystem reader, and enough startup code to hand off reliably.

To fit, I compiled with size and link-time optimizations and had the linker remove unused sections. The Rockbox kernel is stored on the deviceâs FAT32 partition and can be easily updated.

It has been revealed that code execution initially arrives in a damaged FreeType call frame. The stack has been corrupted, and Appleâs OS has left interrupts, DMA controllers, timers, caches, and address translation configured for its own use. Jumping straight into a large C program would carry that state into storage initialization.

I split the bootstrap into two images. The first is the 808-byte assembly stub at 0x22050000. Its job is to leave the parser context: mask IRQs and FIQs, switch to a private stack, stop inherited timer activity, quiesce DMA and clock domains, and clean up caches and the MMU before entering the main payload. It replaces the damaged stack and then jumps to the Rockbox kernel loader.

It has been revealed that the second image is the main loader at 0x22060000. Its entry code disables the watchdog before starting the NAND scan, installs its own stack, and clears the uninitialized-data area before calling C. The watchdog matters because reconstructing the logical flash mapping can take several seconds; a reset in the middle would stop the boot before it ever found Rockbox.

Industry observers note that this separation keeps the most fragile stage small. The assembly stub establishes a controlled execution environment; the main payload can then do the more substantial storage work in freestanding C.

On my nano 5G, the result is a cold, battery-powered boot straight into Rockbox, with no USB connection and no disk-mode button sequence. The PRVD partition setting skips rsrc validation and, when combined with the star exploit, enables untethered boot straight into Rockbox.
