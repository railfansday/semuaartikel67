Or rather, I vibe-coded an FPGA into running an LLM. And it… just worked.

According to recent reports, one of the more entertaining things about programming recently is that coding agents let me work in entirely new domains by giving me access to new programming languages and paradigms. Lately, that has meant hacking on hardware, now that writing low-level software is much easier. So, in this blog post, I’m going to try to recount the experience of vibe coding an FPGA, going through a series of “oh shit” moments several times, and giving myself a new appreciation for what’s possible if you have a large token budget (thanks YC) and interesting problems to point the models at.

I overheard some founders recently talk about how FPGAs work. I’ll admit I was relatively naive about them. I’d never really experimented with them in my startup or in college, so I knew little about them before. The basic idea I was familiar with: you can program a circuit into a reprogrammable chip. So rather than having a general purpose computing architecture (like a CPU) you can have a reprogrammable one, i.e. the configuration loaded onto the chip determines how its logic and routing are connected, and that (in theory) enables performance advantages. I also know that it took a mountain of C++ to write and involved manually analyzing waveforms for simulation and verification. I had never done this before though and it seemed cumbersome.

That’s about what I knew going into this.

Naturally, my ML brain thought “could we use these for AI inference”. I’m not the first to think this — there are a few repos attempting to port ML models to FPGAs on Github. But I hadn’t actually seen a writeup on whether coding agents are good at writing the low level C++ and Verilog code to program them and verifying the outputs so that they actually run accurately. (Spoiler alert, they are incredible at programming them.).

So I decided I needed to get my hands on one. AWS has F2 instances with FPGA hardware, and that seemed easier than going and buying physical hardware, so I asked Codex to spin up a reservation and got cooking. It had a relatively limited memory of 16 GB of FPGA HBM. Around the same time, I was working with the DeepGrove founders who were discussing their new ternary weight architecture that is well suited for memory limited cases. It’s SOTA on Mac hardware with actual agentic tool calling, so I figured why not, let’s see if I can get this working on an FPGA and fast enough to be useful.

What followed was a cloud agent running in Conductor for several days with me mostly just encouraging it periodically while it both (1) got a model fully running and (2) increased its speed by 33× from the first full-model bit-exact baseline to get it to a real-time relevant speed. It was one of the most mind blowing autoresearch loops I’ve run, ultimately writing roughly 3M lines across the experiment history and parsing 30M lines of output files, burning only $10,000 in Claude and OpenAI tokens to run hundreds of experiments. Most of the code is C++ and some Verilog. It’s been probably a decade since the last time I wrote any serious amount of C++ and I’ve never written Verilog. I honestly don’t know the first thing about Verilog. Most of my prompts were not particularly clever: they consisted mostly of me saying things like “you’re a superintelligent model, time to be more creative” and “let’s go for 2x faster, you got this”. Sometimes I brought some ML knowhow like “hey it’s time to consider speculative decoding” or “why is that running on CPU, you should port it”. But for the most part, it was just vibes and I’m pretty sure that with enough time the model would have figured out those things. Also, it seemed that both Astra and Opus (fresh Fable wasn’t out yet) were pretty capable at this and I could use them interchangeably. I’m sure someone has a good benchmark for which is smarter but both passed my smart-enough threshold.

According to recent reports, at one point, around when it got to 10 TPS, I messaged the DeepGrove founders about this, and they replied surprised that it was working so easily, saying they had tried this a few months back and the models were not quite good enough to be particularly effective. They sent me a prompt that summarizes some of their lessons and I copy-pasted it into my session to see if it’d matter. It was essentially the most significant piece of actual guidance I added to this session. The prompt is reproduced below.

Industry observers note that here is what someone else did for a dense bs=1 decode optimized fpga implementation for a dense qwen style model with ternary weights. you should take this with a grain of salt and pick things that you believe are acutally useful to add to your initiative. Please also dont do things if you dont think is useful that take a lot of times like runnning really long test of a cycle accurate simulation etc or like physical design since those can take like hours. here are some ideas please pick and choose use this as context and not somehting that you shoudl be strictly guided by somethings that could help. prioritiize speed of like getting this up and running though..

The coding agent diligently considered these asks, but it didn’t seem to make all that much of a difference qualitatively. Indeed, when I asked it later to read all of the logs and determine which of these instructions it actually used, it remarked:.

According to recent reports, its biggest design ideas were already in my blueprint before you pasted it. You pasted it on Oct 29 at 21:50 UTC: 4,741 characters describing what someone else did for a dense, batch-1, ternary FPGA decoder. Within 70 seconds I had sorted it into ten ideas to adopt and five to reject, and written that into every design agent’s brief. The shorter remark from your friend Edward, about using lookup tables as logic gates, came 24 minutes earlier and left nothing on the speed line.

Design ideas I adopted: mostly confirmation.

Already planned: streaming weights straight into the compute lanes, running rows in parallel, and reading the attention cache in bursts were all in the design brief I’d released 35–40 minutes earlier.

Ideas I rejected: all five numerics shortcuts. Lower-precision activations, a deferred norm, an 8-bit KV cache, online softmax and 16-bit probabilities each change the output bits. That is where their design got its efficiency, and your bit-exact rule ruled it out.

Process advice: this changed things right away.

What you asked: not to do things that take hours.

What I stopped: a simulation that had run for about 24 hours, and two 250 MHz builds.

What I switched to: a short loop of C tests, synthesis and a logic-depth check, with one place-and-route per integration.

Likely gain: it got hardware results sooner.

Possible cost, which I can’t prove: two hangs that only RTL simulation could show reached the board the next day, and the big integration lost 38 hours to them.

One real find it triggered. While checking their memory ideas, I found AWS’s own reference memory design, which reaches 426 GB/s across all 32 memory channels. The memory subsystem was built from it.

Sources indicate that in other words, for most of the actual design ideas it is unclear but there is good reason to believe the model would have figured them out, especially because it came up with them many cycles later after several compaction cycles. But the process advice was useful immediately for getting to hardware results sooner and increasing iteration speed. In other words, the humans are still useful at defining how to iterate fast and what correctness looks like, and the agents are great to manage the exploration.

Industry observers note that here are the changes the autoresearch loop found. Interestingly, it’s mostly a series of modest improvements that compound 1.5x ish every time, rather than one or two giant ones.

Baseline: the first full-model bit-exact FPGA image (R8), served with host-side prefix caching.

Host software only: per-command overhead fell from ~10 ms to 0.9 ms (persistent register mapping, streaming reads, no per-command SDK calls or fsyncs).

1.25× this step · 1.25× from baseline.

A 128-lane attention engine that reads the KV cache in bursts instead of a word at a time, keeping the reference's exact summation order.

1.74× this step · 2.18× from baseline.

A parallel MoE router with an exact GCC-sort tie-breaker plus a streaming output head with built-in argmax; moderate-effort routing let it run at 250 MHz.

1.46× this step · 3.19× from baseline.

A glue engine that parallelizes norms, RoPE, quantization and copies between engines in certified exact orders.

1.47× this step · 4.70× from baseline.

The full newly introduced pipeline (streaming ternary projection lanes + a new sequencer replacing R8's control path), after fixing two hangs that only appeared in hardware.

1.63× this step · 7.65× from baseline.

Exact speculative decoding: the host drafts tokens by prompt lookup and the FPGA verifies several in one pass.

1.04× this step · 7.97× from baseline.

Fixed a relay that moved router weights between dies at 1/6 speed: router stall per layer 43,862 → 12,292 cycles.

1.14× this step · 9.08× from baseline.

Head shadow v2 (start the next token on a provisional guess; catch misses early) plus cross-die timing fixes, enabling 237.5 MHz kernel / 450 MHz memory.

1.62× this step · 14.68× from baseline.

Exact speculative decoding with a real draft model: a cut-down Maple on the F2's host CPUs drafts ahead, and the FPGA verifies every token.

1.12× this step · 16.42× from baseline.

Doubled the memory ports from 4 to 8 (two projection lanes, output head striped across banks): 1.39× per clock, but congestion cut the clock to 181/375 MHz.

1.03× this step · 16.91× from baseline.

Hid the attention engine's KV fetches behind its compute, and replaced the router's 2,048-step serial sum with an exact order-independent one (12,292 → 2,338 cycles per layer).

1.24× this step · 20.98× from baseline.

Lossless 5-trit weight packing (−20% weight bytes), shorter serial steps, and moving the output head to the far die, which relieved congestion and allowed 225/400 MHz.

1.27× this step · 26.63× from baseline.

Re-speculation after head-shadow misses, speculative MoE expert prefill during the router, and a die rebalance (without the unused DDR controller) that ran 231.25/450 MHz on both boots.

1.08× this step · 28.63× from baseline.

A head loader that reads both of its memory banks at once (+17.3%, measured on and off on one image), a runtime expert-prefetch policy, and the router-job timing fix; run one clock step lower (225/425 MHz) after a soak test found random faults at 231.25.

1.16× this step · 33.13× from baseline.

Recent findings suggest that this was a fun project. I’m not sure I’m ever going to use this specific chip architecture in this specific way, and I’m certainly not claiming that an 8,192-token-context model running on an FPGA is the way I’d recommend anyone use something like this in production. But it’s pretty epic that this just works. Capability like this completely shifts the overton window for what a committed team of engineers can work on. It should mean that entirely newly introduced types of ideas (scientific discoveries, products, startups) are possible if you can point the models in the right direction. I’m excited to see what everyone builds.
