I have been using the community fork of Maiao for a little while now, and it is excellent. For anyone who prefers working with stacked diffs, but needs to interact with a more traditional forge such as GitHub, try using Maiao for a bit. It just does the right thing in almost every situation. It’s cut my frustration with GitHub at least in half, if not more.

For the small group of readers who are stoked about stacked diffs, that’s probably enough of a pitch. For the rest of the world, let’s back up a little.

Sources indicate that on traditional forge platforms11 Like GitHub, Codeberg, GitLab, BitBucket, etc., pre-commit22 Pre-commit because it’s the review that happens before the code is merged (“committed”) to the upstream branch, in contrast to e.g. audits which are a kind of post-commit review. code review happens on pull requests (sometimes called merge requests), where each pull request is created from a git branch.

Industry observers note that users that are new to git can then think of a branch as one development effort toward a small goal. They keep adding commits to that branch as long as its tip does not represent the goal state. At the end, when everything looks right and the change is approved, they perform an explicit merge. This means they create a merge commit on the upstream branch that references both the old upstream and the branch they worked on.

Recent findings suggest that this lets beginners work in smaller increments while not dealing with the intricacies of rewriting git history33 Sometimes the beginner is instructed to perform a squash merge instead, which typically means the forge platform creates a single, regular commit on the upstream branch, referencing only the old upstream, and containing all the changes implied by the tip of the development branch. Although it sounds like this rewrites history, it doesn’t really – the old development branch is still exactly the same as it was before. The difference is that the changes implied by it were copied over to the upstream branch without reference to the development branch.; the workflow lowers the barrier to collaborating with others using git, which is nice.

It also means the reviewing interface in a traditional forge doesn’t have to deal with the intricacies of rewriting git history. This means the reviewing ui typically only shows the differences between commits still on the development branch, and not what changed between two versions of “the same” commit, when one of them is no longer on the branch.

We don’t have to use git that way. We can instead choose to have only one development branch. I call it something generic like dev. On that branch, each goal state is represented by one commit. So instead of multiple branches (one for each goal) with multiple commits on them (steps toward the implementation), there is just one branch (a generic development branch) with multiple commits on it (one for each goal).

With that workflow, if we discover one of the commits don’t represent the goal state of that change, we edit that commit55 Technically speaking, git doesn’t let owners edit commits. What happens under the hood is the commit is replaced with a latest one. But with a change id in the commit message, we can still tell that they represent the same atomic change. instead of adding more commits.66 What if we need to revert to an old commit? Fortunately, git maintains a reflog with old commits. Those stick around until git decides to garbage collect dangling refs. Then each atomic change in progress is implemented in exactly one commit, all on one development branch. The dev branch may have many commits, but they represent different atomic changes, not progress toward one goal state.

It has been revealed that this way of working is also known as making stacked diffs, and I find it easier and faster than having a separate branch for each atomic change. Many experienced software engineers agree.77 I should say I disagree with Gergely Orosz when he notes it’s impossible to make a pull request that depends on changes in an earlier, unmerged pull request. It’s possible (and even easy in most forges) but it’s a lot of extra work to juggle the branches and merge targets. Fundamentally, there’s no deep incompatibility between pull requests and stacked diffs. The reason people prefer tooling made for stacked diffs is that there’s less paperwork needed to satisfy git when working with those tools.

Industry observers note that the way stacked diffs are merged is ideally by copying them over to the upstream branch, either through cherry-picking, or by choosing the rebase and fast-forward merge type in the forge ui. This produces a history of the upstream branch that very clearly lists each atomic change in the order it occurred, without the false steps and mistakes along the way.

Industry observers note that beginners may think this is dishonest. The the point is not to hide one’s mistakes, but to present a history that another developer can read and follow along with three years into the future, when they want to understand how the project ended up in the state it is in. For that purpose, only what eventually went into the upstream branch matters.

The same process happened for the flaky test fix a little later. Once those commits are approved and have passed through ci, they will get copied to the upstream branch, like the ones before them.

All of these commits needed amendment just as many times as in the previous graph, only we do it by replacing the commits instead of adding more commits.

This is what people mean when they talk about how “one atomic change is one commit, and one commit is one atomic change”.

In a recent development, there is one unfortunate consequence of the stacked diffs workflow: when all commits are in one branch, they look like they depend on each other in the order they exist on the branch, even if they actually contain independent changes. When all commits are on one branch, there’s no way to see which commits are independent without (a) reading the code, and (b) trying to cherry-pick one of the changes.88 Both are needed, because cherry-picking or rebasing can conflict in git even though changes are independent (when they happen to appear close to each other in the source code), and dependent changes can generate a clean cherry-pick as far as git is concerned, even if it breaks the code (when the changes happen in different locations in the code, but one of them assumes the other has happened already).

If it’s notable to document to ourselves that we have two parallel workstreams that are indepedent, we can use two local generic development branches (I call mine dev and, imaginatively, dev2). Each branch is still treated as a stack of diffs, i.e. each commit represents one atomic change, but now it’s abundantly clear that commits cannot depend on each other across the two branches.

Sources indicate that at this point, you can probably guess why the pull request workflow of traditional forges is annoying. The pull request assumes we have one branch for each atomic change, but with stacked diffs, we only have the one branch, where we want each commit to become a separate pull request, building on the one before it.

Industry observers note that this is a lot of work.99 Still less work in total than having a branch per atomic change, but just barely! Maiao solves that.

Industry observers note that these days, when I feel ready to create pull requests for my commits, I trigger the git review command. Maiao then automatically does all of the things I did manually before, better than I could. It fetches the latest upstream, rebases the current branch onto it, creates disposable branches for each commit, pushes them, opens up a pull request with the right merge target for each disposable branch through the GitHub api, and turns them into a native GitHub stack of pull requests, meaning they get merged in the right order, and can be merged all at once when they are ready.

If code review or the ci build uncovers things I need to change, I do what I always did: I replace the commit that needs changing. Then I run git review again, and Maiao just does the right thing: it rebases onto the latest upstream again, it moves the disposable branches to the fresh commits, force-pushes them, updates the pull request descriptions with any changes to the commit messages, updates any merge targets that have changed, etc.

It has been revealed that maiao is one command (git review). When run, it makes the GitHub pull request stack match our local development branch. That’s all it does, and that’s all it needs to do.

In cases where we have multiple local development branches (because the work is independent and parallel), git review can be run on either or both of them independently of the other, and Maiao will create one stack for each branch, as one would expect.

In a recent development, note also that Maiao doesn’t have to create pull requests for the entire development branch. Maybe we’re still working on the top few commits. Then we can create a temporary branch pointing to the topmost of the commits we do want pull requests for. When we run git review with that branch checked out, Maiao makes pull requests only out of the commits included in that branch. Then when we finish those top commits, we can run git review on the development branch, and Maiao understands that the topmost commits build on the commits that already have pull requests, so it stacks new pull requests for the new commits on top of the pull requests that already existed for the prior commits.

Industry observers note that all of the above to say Maiao doesn’t care about how you branch locally. A decent mental model is that it creates and updates pull requests for each of the commits between head and the master branch so the stack on the forge matches the local commits. That’s all.
