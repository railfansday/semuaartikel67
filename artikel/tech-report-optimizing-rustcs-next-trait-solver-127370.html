Industry observers note that the next rust trait solver, a large subsystem of the rust compiler that we've been trying to replace, will finally land in rust 1.102.0. In the last stages, before stabilizing it, its performance was a major blocker. But what is "a trait solver"? And why is its performance a problem? My goal for this blog post is to answer those questions in a way where you don't need any prior knowledge. I think discussions of the trait solver can quickly become quite involved, and daunting. So today, we'll start from the very basics!

According to recent reports, on the 15th of May, 2015, Rust reached a major milestone. The very first stable version of rust was released. Version 1.0.0. Just 72 days later, on the 24th of July, work started on a new trait solver. Or well, that's when the Chalk project got its first commit. It seems the initial goal was to formalize the trait system so we could prove its correctness. One reason that didn't work well is because the trait system wasn't very correct at all.

Sources indicate that chalk is, according to its github description, "An implementation and definition of the Rust trait system using a PROLOG-like logic solver". The fact that it's "PROLOG-like" we'll come back to in a few paragraphs, it's quite interesting! However, Chalk isn't around anymore. Its README.md states it has been "sunset in favor of the newer next-generation trait solver". In October 2022, this project was officially started to turn the lessons learned from Chalk, into an actual latest subsystem of the rust compiler, that, once finished, could replace the code of the old trait solver.

In a recent development, the goal of the newly introduced trait solver is to make sure we wouldn't have as many correctness bugs in the trait system. We now call this project "project zero", referring to the number of soundness bugs we'd ideally like to have in our type system. There have been several very long standing bugs in Rust's (old) trait solver. Like this one, that has been open since May 28, 2015 (just 13 days after Rust 1.0!). It abuses something called "implied bounds" to convince the Rust compiler to turn a short lifetime 'a into a 'static lifetime, allowing you to use a reference after its already freed. Some of these bugs were fundamentally impossible to fix with the way the old trait solver worked.

Note: Chalk and the fresh trait solver aren't the same thing. Chalk came first, and learned a lot of lessons incorporated in the new solver.

But what is a trait system? And how does a trait solver solve it?

Industry observers note that the first place to look for documentation about the Rust compiler is the "rustc dev guide". It says "The goal of the trait system is to check whether a given trait bound is satisfied. Most notably when typechecking the body of - potentially generic - functions.". But I promised I'd start at absolute zero, so what's a trait?

In a recent development, some types act in similar ways. They share certain properties. For example, a lot of different types can be cloned, or copared for equality. To codify these properties, we can use traits. In other words, a trait is a property of a type.

Industry observers note that notably, you can associate behaviors with these properties. The standard library's definition of Clone also includes two methods that can be called to perform this cloning operation.

Industry observers note that to check whether the code you wrote is correct, the Rust compiler sometimes has to check that these properties hold. If you're trying to clone a value, the compiler has to check whether that value can be cloned.

Prolog is a cool programming language that works and looks very differently to what you may be used to. However, it is just as powerful (i.e. turing complete) as any other. The way it works has strong parallels to our trait system, let me show you. Here's an example:.

A Prolog program consists of a set of statements, called "facts", as well as relationships between facts. In the above program, there are two facts: u64 has the property Copy, String has the property Clone, And there's also a relationship between these two properties. If some variable x has the Copy property, it also has the Clone property.

Industry observers note that finally, we can ask the prolog program some questions. For example, Does the type u64 have the Clone property? To answer that question, the runtime of a prolog program has to analyze all the known facts and relations. In this program we haven't said that u64 has the Clone property. However, we have said that it has the Copy property. And by using the relationship between Copy and Clone, the solver can derive that both questions (starting with ?-) are true!

It has been revealed that in the example code, one place where the trait solver comes into effect is when we call weird_add. On the function there's a where bound. A where bound is a requirement that the Rust compiler must check before allowing a call to that function. In this case, Rust has to make sure that i32 (a type we found through type inference) implements the Add trait. To do that, the solver can use one of a couple of strategies, and we'll look at each. In this case, we'll be looking for an impl block that mentions the i32 type, and we'll find one of those in the standard library!

Once the trait solver finds this impl block, it acts as an answer to the question "does i32 implement Add?". We somtimes refer to this answer as a a proof that the statement holds.

Industry observers note that the example code contains several more calls to the trait solver. One you may not have thought about is that all local variables in Rust have to implement the Sized trait to be allowed on the stack. The Sized trait codifies that the compiler knows how many bytes of memory the value takes up, so it can be allocated on the stack. So, there will also be a query to the trait solver asking "does i32 implement Sized?".

The proof for this statement doesn't come from an impl block though. I did say that the compiler has several stratagies to derive proofs. In this case, the fact that some primitive types implement Sized is built-in to the compiler. i32 is inherently Sized, and there is no impl block anywhere that says so.

It has been revealed that answering Sized queries in general turns out to be quite hard because of the shear volume at which it occurs. To compile rust's standard library, we'll ask "does type implement Sized?" about 800 000 times! Additionally, answering it isn't always this simple. Let's take a slightly more involved example:.

To prove Kitten: Sized, a recursive process takes place. Both fields have to implement Sized too. So in the process of answering this question, the trait solver will produce more questions to be answered. Kitten: Sized leads to String: Sized & f64: Sized. f64 luckily is trivial again, and built into the compiler. String isn't though, and we go one more layer deeper to Vec: Sized, etcetera.

Sources indicate that in Rust, generic functions can be type checked standalone. The example using weird_add doesn't need a main function to be checked, and may emit its own type errors.

This is where the trait solver actually does the most work. For example, to type check weird_add, we have to prove that a + b is valid. a + b desugars to a.add(b), and when finding the method add the trait solver gets invoked, since the add method comes from the Add trait.

Previously, proof candidates came either from impl blocks or they were built into the compiler. Not here though! A new proof strategy is used here instead. When calling weird_add we saw that a where bound acts as a requirement that has to be checked before calling, but that means that inside weird_add we can assume that where bound holds and thus it acts as a proof strategy. Concretely, we know a has the type T, and to answer the question "does T implement Add" we find a where bound that says so.

Again we have to look for candidates, and there's no built in one for generic types T, nor is there an impl block, nor a where bound that mentions Sized. So how does that work? Sources indicate that what this all means, is that while answering a question, the trait solver emits more questions. These subquestions get added to an internal queue in the trait solver, and this queue of questions will be proven one after the other. Like this, some questions can turn into several subquestions, which can even have their own subquestions again.

Hold on! impl blocks can define inputs they act on, like impl Foo for i32 applies when the input is i32. It can make these inputs variables, like impl Foo for T. And impl blocks can also define outputs thrugh associated types.

Recent findings suggest that what we've done here, is make impl blocks powerful enough to act as functions, with inputs and outputs. And Alonzo Church proved that a language with only pure functions is in fact turing complete.

This is why Prolog is a fully-fledged turing complete programming language, and so is Rust's type system. People have defined numbers completely in Rust's type system in a crate called typenum, and have gone even further by implementing a chess engine inside the type system.

Recent findings suggest that this ends up replacing the trait solver more complicated than you might think. People have already written many programs using the old solver, and because the latest solver internally makes different assumptions (sometimes in the name of soundness, remember the old solver has many bugs), we end up having programs that take both longer and shorter to compile. Sometimes with a polynomial factor, sometimes even with an exponential factor.

For example, the crate unic-ucd contains code along the lines of:.

It lists a whole bunch of unicode characters, and each constant inside these slices are themselves string literals. That means each of them has an associated lifetime variable, that at some point gets inferred to 'static since we're assigning to a const. Now the newly introduced trait solver, in some cases where the old solver did not, reasons about lifetimes.

In a recent development, now sometimes, the rust compiler attempts see if two types are equal. This process may have side effects, in that it may make some progress towards inferring other types in the program. Because these side effects are sometimes undesireable, we have a system to "attempt" to unify types, and then roll back the results. To be able to do rollbacks we sometimes keep a trace of all operations we perform, so we can run them in reverse to get back to where we started. However, sometimes this tracking is more expensive than simply making a copy of the state and putting that copy back.

In a recent development, in this case, during borrow checking, we call into the the trait solver and end up unifying two "lifetime variables", which we roll back. This specific rollback involves a copy, though there was a shortcut. We keep track of a single boolean: "was any lifetime variable modified". If none were, the rollback can be skipped. The old solver wouldn't do such unifications, so the rollback could always be skipped, while in the new solver we couldn't do so.

According to recent reports, often, there are very few lifetime variables in scope, so doing a rollback isn't so bad. However, the example above lists every unicode character in existence, so the list is rather long. And for every item in the list, we'd do such a rollback, that copied all lifetime variables (for which there is one per element in the list). So N undos copying a list of N lifetime variables, that's a quadratic factor! So this crate would compile just fine with the old solver, and be 200 times slower with the latest solver. Oops!

It has been revealed that there are two important strategies we use to make the trait solver faster. First of all, there's caching, and a lot of it. For example, in the following example we prove that i32: Sized three times:.

We'd like to make it so we only need to figure out whether a specific type is Sized once, and so we cache the result.

Sources indicate that the second optimization we use a lot is not caching funnily enough. Accessing the cache can be rather expensive (we'll get to why). So in this case, since i32 is trivially Sized, we can answer the question faster by never looking in the cache. For more complicated types this is not true.

According to recent reports, A naive cache would be a mapping from questions asked to the trait solver, to answers (errors or proofs). So, something like HashMap, but this wouldn't perform so well. Let's look at this example:.

Here we've renamed the variables T and U between foo and bar. We'll prove two question, that T: Into and later U: Into. Because of the renamings these two proofs are the same, but the questions are technically different. If we don't do something about variable renaming, we'd have cache misses all the time.

Another problem is that this cache wouldn't even work. By now, we've learned that candidates for proofs can come from three sources:.

The first two play nicely, because the same impl blocks and compiler built-ins are around for all questions submitted to the trait solver. Howver, where bounds are different for every function, and thus a proof that a type implements a trait inside of one function, may not be reusable inside another function.

According to recent reports, in the example above, we prove that T: Into twice. Inside foo that's ok, but not inside of bar. So if we naively cached that T: Into we wouldn't notice that bar is incorrect.

According to recent reports, we call the set of bounds that are in-scope during trait solving the ParamEnv (parameter environment), and so the cache would really have to look like HashMap<(ParamEnv, Question), Answer>. Since for every function, the ParamEnv is different, we'd have even more cache misses.

Recent findings suggest that to improve our chances of a cache hit, we perform a process called "Canonicalization". During canonicalization, we do two things. First we'll rename all variables with numbers. So, T: Into will become ?0: Into (variable 0 implements Into variable 1). Since this process is consistent, another renamed input like U: Into also gets this numbering and is compatible.

According to recent reports, in addition, we'll try very hard to figure out which where bounds in the ParamEnv actually matter. If there are bounds that won't affect the result of the query, we can avoid putting them in the cache key, making cache hits more likely.

So, in the rust compiler, the cache really looks more like a HashMap<(Paramenv, CanonicalQuestion), CanonicalAnswer> Note that the answer of every query now has to be de-canonicalized. We call this "instantiation". When we turn T: Into into ?0: Into, and cache its result, and we later look for U: Into, we have to turn the answer (that mentions variables 0 and 1) into U and T respectively. In other words, by canonicalizing we make cache hits much more likely, but the process isn't free. Hence not caching is sometimes worth it for simple questions.

Sources indicate that the problem was that there's one more property that has to be part of the cache key: which opaque types are in scope. An opaque type is a type you write as a "return position impl trait". For example:.

foo returns impl IntoIterator. By doing so, callers of this function don't get to know what specific type is returned. Only that they can iterate over whatever they get back. Inside of this function foo, the trait solver will infer which specific type gets returned (a Vec), but in other functions calling foo, this information is not available. So, this is another piece of information that may affect answers from function to function, just like the ParamEnv.

So, the real cache has one more input: HashMap<(ParamEnv, OpaqueTypes, CanonicalQuestion), CanonicalAnswer>. What that really means is that the following two functions both submit the question i32: Clone to the trait solver, but cannot reuse the cache entry:.

Sources indicate that this ends up mattering a lot in async code, or code like parser-generators that tend to return -> impl Parser from functions. That's unfortunate, because the fact that opaque types are different ends up almost never affecting the outcome of a question. Sure, we can come up with examples where it does, but in practice it almost never does.

Recent findings suggest that so, the fix here is to remove opaque types from the cache key to the cached value like so: HashMap<(ParamEnv, CanonicalQuestion), (CanonicalAnswer, OpaqueTypeState)>. Then, every time we answer a question that may be different because of opaque types, we record in the opaque type state under what condition it may affect the answer, and continue assuming the answer is unaffected (this is often the case). Then, when we get a cached answer in a specific environment, we look at the opaque type state, to see whether the answer might be affected by current context. It almost never is, but if it ends up mattering, we retry the question but now no longer assuming opaque types don't matter.

It has been revealed that this sometimes makes performance worse (we sometimes do double work), but since its so rare, we get an improvement over all by having more cache hits. In the graph from above, there are two bars for wg-grammar. One where the hit rate is 73% and one where the hit rate is 79%. This 6% difference translates to some the wg-grammar crate first taking 28 seconds to compile, and afterwards only 14 seconds. That's 2x faster!

This, and more optimizations meant that wg-grammar used to take almost 200 Billion cpu cycles to compile, and now only about 7 Billion.
