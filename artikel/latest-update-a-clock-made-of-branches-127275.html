In a recent development, what is time inside a machine you want to replay? 🧘.

Industry observers note that when building Rewind, a deterministic VM, you come face-to-face with the idea of how to represent time very rapidly. You need a way to measure time inside the guest so that on subsequent replays, the guest sees the same time and makes the same decisions. Time is the ultimate variable.

You can’t simply record the wall-clock time of the host because time spent between two interception points depends on things outside the guest, like host load, CPU frequency, caches and other processes. Therefore the same guest work can take a different amount of time on the host.

Sources indicate that in dafuq is a deterministic VM? I explained how the clock inside Rewind VM moves 5 microseconds per step. More specifically, that clock, exit time, moves only when the guest exits such as from a syscall. It treats everything the program does between two exits as instant. Therefore a program that is CPU bound such as doing nothing but math for a full second between two system calls, sees only 5µs go by. 🤦🏻‍♂️.

Industry observers note that rewind has a second clock mode as well, counter time, that tries to account for the work. The clock advances one nanosecond for every conditional branch the guest retired.11This is the same approach popularized by the rr debugger. The rr paper calls it deterministic time.

Aside: New to Rewind? Start with a flaky build you only catch once and dafuq is a deterministic VM?

Still confused about what I mean by “free” and “branches”? Let’s look at a simple example to distinguish between the two clocks.

The counter time tries to account for the work whereas the exit time only advanced the clock on exits.22The 5µs was my guess at a reasonable cost of a system call and context switch on current hardware. The 1ns is roughly what a conditional branch costs on a current core.

We already understand that we cannot rely on the wall-clock time of the host. We need something to measure that is the same for every run of the same program so that we can equate it to time spent.

In a recent development, the guest’s instruction stream! The CPU is a deterministic machine: the same input, the same registers, the same memory, and the same instructions produce the same next state.

Sources indicate that we can measure time by measuring progress through the instruction stream. 💡.

Recent findings suggest that turns out that CPU manufacturers even ship a hardware counter for exactly that. Is it reliable? Let’s see. 🧐.

Sources indicate that the same program and input gives the same conditional branch count, but the instruction count is off by a thousand or so. Why?

According to recent reports, although this loop is CPU bound and only decrements a register, it is still not isolated from the effects of the outside world. Timers tick, network packets arrive, other cores send inter-processor interrupts (IPIs). The program can’t see any of that, but the instruction counter we are probing can.

I pinned the loop to a single CPU and counted how many interrupts that CPU took during each run, from /proc/interrupts.

The dashed line is one extra count per interrupt, and the instruction counter is almost perfectly on it.33The fit is 0.94 rather than 1 because /proc/interrupts also catches the interrupts that land while perf and taskset start up and tear down, before and after the loop runs. The conditional branch counter on the other hand, stays at zero no matter how many interrupts land.

Sources indicate that interrupts from the outside-world are not the only thing that can skew the instruction count. The program can also page fault, which is an interrupt too. The instruction counter sees the kernel’s detour to handle the fault, but the program does not.

Tip Out of the box, AMD Zen also overcounts conditional branches, a few in tens of millions, from a speculation optimization known as SpecLockMap. The fix is to set a particular bit in the PMU MSR, which Rewind does automatically as does rr#2034.

In order to rewind history, we need a measurement of time that is reliable and deterministic. Our traditional wall-clock time is unreliable due to the effects of the outside world but we do have a reliable measurement of progress through the instruction stream: the conditional branch counter.

Using the conditional branch counter as a proxy for time turns out to be a relatively decent approximation.

Why do we care about having a “realistic” representation of time?

In a recent development, plenty of programs read the clock and make decisions with it, so the guest’s clock has to be at least somewhat realistic. Under exit time, computing is “free”. A test that checks some work “finishes within 1 s” always passes. If the bug you’re chasing is a timeout, exit time will never reproduce it. 🙃.

Races get skewed too with an unrealistic clock. With exit time, a whole burst of work lands in the same instant, which crowds the threads together, so a race can fire far more often in the VM than it ever would on real hardware.

The closer we can emulate the real world, the more likely we are to reproduce a bug that only happens in the real world. Counter time is a better approximation of the real world than exit time, and it is deterministic, so it is the default clock in Rewind.

Some say time is an illusion. I say it’s a jnz counter.
