According to recent reports, modifiers have been with us for a long time, often with modifier classes, but also with attribute selectors. Some common examples are things like different versions of alerts and buttons.

For a lot of use cases, either of those approaches work great, but when it comes to layout, a lot of the time we want the context of where the element is being used to control things.

A card is a nice example of this, where we might have several versions.

In a recent development, the issue here is, if I’m using .card--compact, I probably want to do that for all the cards within a section. That can be annoying to apply to each card, but that’s rendered moot since most people are doing some sort of looping in a template like this these days.

And this works great, as long as we always want the cards to be compact.

However, you might put this together and send it off to the design team for approval, only for them not to like that when the compact cards are lower down the page, the smaller padding isn’t needed to create visual separation between the two sections. Instead of helping with the hierarchy, it’s simply creating a strange visual inconsistency.

We could use something like a resize observer to try and deal with this, but we have a better tool at our disposal: Container Style Queries, which are now Baseline Newly Available.

While they all start with container, for the rest of this article I interchangeable use container query or size query for a container size query, and style query for what we’re talking about here.

Before we get into the good stuff, a quick look at the basics of style queries.

It has been revealed that you’re probably familiar with size queries, which work similar to @media but look at the size of a container, rather than the viewport. Container style queries use the same @container at-rule as container size queries, but instead of looking at a size, they look at the value of a custom property.

This reads as, “if the nearest container has --theme: high-contrast, style the .card like this.”.

if() is also on the way, and allows for style queries as well, but if() is able to see the value of custom properties on the element it’s being used. The big difference is it can only be used for a single property, while style queries can be used for rules with multiple properties.

In a recent development, the split section isn’t styling the overflow grid directly, which is possible, but always awkard, and leads to fragile code bases. Instead, we created some configurable settings on that grid, and simply adjusted them as needed.

Industry observers note that I don’t think style queries mean it’s time to throw out modifier classes (or data modifiers). They still work great, especially since a style query can’t look at the element it’s styling. If I simply want my button to be an accent button, or a pill shape, then a modifier makes a lot of sense.

On top of that, a regular media query or container query, or even an intrinsic pattern might get the job done, and that’s great too.

Sources indicate that where style queries shine is when the condition and the styles need to live in different places, or when one condition needs to affect several things at once, like the split above. Instead of a layout reaching in and styling its children, it changes a few settings, and each component decides how to respond.

That’s a big part of what I think of as writing resilient CSS: components that keep working, and adapt sensibly, no matter where they end up.
