According to recent reports, here's a setup we see a lot. A claims team at an insurer has a working prototype on the OpenAI SDK that writes a short summary of each claim file. Then legal asks who else can see the claim text while the model is running. For any hosted API, the honest answer is the provider and whoever operates the GPUs, at least technically. The contract and the retention policy say they won't look. You have no way to check.

This post demonstrates how to move that prototype to Confidential Router with almost no code changes, and how to verify where your data is going before every request.

Router speaks the standard OpenAI API. In Python you change base_url:.

Notice the URL points to localhost, not to our servers. That's Gatekeeper, a small local process that checks the remote endpoint first and only then lets traffic through. Streaming, tool calling and /v1/embeddings (on models that support it) work the way you'd expect.

It's a single static binary with no dependencies, for Linux, macOS and Windows:.

According to recent reports, trust add pins one specific deployment. It writes that deployment's evidenceDigest to your config: a SHA-256 over a snapshot of everything deployed, with container images pinned by digest. If we ship a new version, Gatekeeper stops forwarding requests until you approve the new digest yourself. In a regulated environment that's the behavior you want: a change to how your data is processed goes through you.

In a recent development, before the first request, and every five minutes after that, Gatekeeper runs six stages: fetch, cert-chain, untrusted-root, jws, tls-fingerprint, policy. Two of them do most of the work.

It has been revealed that the root of the certificate chain. The root CA runs inside a confidential VM on AMD SEV-SNP or Intel TDX. Gatekeeper checks that:.

According to recent reports, the last check is there because without it, any other tenant on the same hardware would pass. All of this runs offline.

In a recent development, the TLS binding. The signed evidence bundle includes the fingerprint of the endpoint's TLS certificate. Gatekeeper compares it with the certificate it actually saw on the same connection. If something sits between you and the server, the fingerprints won't match.

Industry observers note that if any stage fails, your app gets a 503 with an OpenAI-shaped error object and a stage field, and the request goes nowhere. Handle that case on its own instead of blindly retrying:.

Industry observers note that on successful responses Gatekeeper adds an X-Gatekeeper-Verdict: allow header. Log it next to the request ID in your audit trail.

The evidence bundle is public and needs no key: https://api.router.superprotocol.com/.well-known/swarm-evidence. The simplest thing you can verify by hand is the TLS fingerprint:.

Industry observers note that when we ran this from our own build environment, the fingerprints didn't match. All outbound traffic there goes through a TLS-inspecting proxy, so the script saw the proxy's certificate. The bundle itself was intact: the hash of its embedded tlsLeaf matched the claimed fingerprint. If your corporate network does SSL inspection, Gatekeeper will deny at the tls-fingerprint stage. Add the router host to your proxy's bypass list; don't loosen the check.

The script is weaker than Gatekeeper: it opens two separate connections and doesn't verify the signature or the root. Use it to understand the mechanics and debug your network, not in production.

Gatekeeper proves three things: which code is running, that it's running on genuine TEE hardware, and that you're connected to it. It doesn't right now verify GPU attestation. The docs list that as out of scope, even though inference itself runs on GPUs in confidential mode. If you call https://api.router.superprotocol.com/v1 directly and skip Gatekeeper, nothing is verified. For tools that only accept https endpoints that's the only option, so know what you're giving up.

Recent findings suggest that the operator sees billing metadata only: model, token counts, timing. Each generation record (GET /v1/generation) carries the evidence_digest of the deployment that served it, and never any content.

Now the answer to legal's question isn't a pointer to the contract. The claim text is decrypted only inside an attested environment. Before every request, a process we run ourselves confirms it's the deployment we approved, and blocks the request if anything changed. The hash of that deployment sits in our log next to each call.
