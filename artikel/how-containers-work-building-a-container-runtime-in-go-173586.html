In a recent development, when we run docker run alpine sh, it feels like we just booted a tiny virtual machine. We get a newly introduced hostname, a new filesystem, our shell is PID 1, and the rest of the system seems to have disappeared.

But there's no virtual machine here. The shell is just a regular process on the host, started with a few Linux kernel features that limit what it can see and how much it can use. Docker, containerd, and runc are all tooling built around those features, and underneath it all, it's just a handful of system calls.

Sources indicate that in this article, we will build our own container runtime using those system calls in about 250 lines of Go. Along the way, we'll look at namespaces, pivot_root, overlay filesystems, cgroups, and what Docker adds on top.

From the host's point of view, a container is a process like any other. If we start one with our runtime and look at it from the outside:.

Recent findings suggest that process 40 is the "container". The host sees it, can signal it, and can read everything about it in /proc/40. What makes it a container is what the process itself sees, and three kernel features control that:.

Namespaces give the process its own view of a global resource: its own process IDs, hostname, mounts, and network interfaces.

A different root filesystem makes / inside the process point at a directory of files we chose, usually an image.

Control groups (cgroups) cap how much memory, CPU, and how many processes it can use.

Everything else in a container runtime is plumbing around these three.

It then starts a copy of itself, box child, inside new namespaces. The child finishes the setup that has to happen inside, switches to the new root filesystem, and replaces itself with the user's command.

The exit code handling copies a shell convention: a process killed by a signal reports 128 plus the signal number. That's why a container killed by the out-of-memory killer exits with 137, which is 128 + 9 for SIGKILL, in Docker and in box alike.

Industry observers note that the run function returns an exit code instead of calling os.Exit itself, so the deferred cleanups always run. A runtime that leaks a mount or a cgroup every time something fails gets messy quickly.

Next, the child sets the hostname, makes its mounts private, switches root, and then replaces itself with the user's command:.

It has been revealed that sethostname only affects the fresh UTS namespace, so the host keeps its own name. The MS_PRIVATE remount keeps the container's mounts to itself. A new mount namespace starts as a copy of the parent's, and on most systems those mounts are shared, meaning mount events propagate between namespaces. Without making them private, the container's /proc mount could show up on the host.

syscall.Exec doesn't start a fresh process. It replaces the current one, so the user's command inherits the child's PID, which is 1 in the new PID namespace. There's no box process left inside the container.

The shell is PID 1 and sees only its own processes. On the host, the same shell has an ordinary PID like 40. A process in a PID namespace has one ID per namespace it's visible in.

Recent findings suggest that the network namespace starts with a loopback interface that's down and nothing else, so the container has no network at all. Docker's default bridge network is built on top of this, and we'll touch on it in What Docker Adds.

According to recent reports, the child is started as /proc/self/exe child ..., which is a fresh copy of the same binary. It would be simpler to call the namespace system calls directly in the parent, but Go makes that hard.

The Go runtime starts several OS threads before main runs, and some namespace changes only apply to the calling thread. Others, like a newly introduced PID namespace, only apply to processes created afterward. Doing it in a running Go program means fighting the scheduler for control of which thread does what.

Passing the flags to clone sidesteps that: the kernel creates the child already inside the new namespaces, and the child is a brand new Go program that starts up there. runc solves the same problem a different way, with a small piece of C that runs before the Go runtime starts.

Fresh namespaces alone don't change the filesystem. The child can still see the host's entire /. To look like an Alpine container, it needs Alpine's files as its root.

A container image is a directory tree of files plus some metadata. The easiest way to get one is to ask Docker to export a container's filesystem as a tar archive:.

Recent findings suggest that that directory now holds /bin, /etc, /lib, and everything else in Alpine, about 9 MB. box treats it as a read-only image.

Sources indicate that the classic way to change a process's root is chroot, but it's not a security boundary. A process with root privileges inside a chroot can escape it with a few well-known tricks, because the old root is still mounted and reachable.

Sources indicate that container runtimes use pivot_root instead. It moves the old root filesystem to a directory under the newly introduced one, after which the runtime unmounts it entirely:.

Recent findings suggest that the bind mount of the fresh root onto itself looks redundant, but pivot_root refuses to pivot to a directory that isn't a mount point. Once the old root is unmounted, the host's filesystem is gone from this mount namespace. There's no path left to reach it.

In a recent development, this all happens in the child's private mount namespace. The host's mounts are untouched.

According to recent reports, /proc is how tools like ps find processes. Mounting a fresh proc filesystem inside the fresh PID namespace makes it list only the container's processes. Without the new mount, ps would either fail or show the host's processes.

A device file is just a name pointing at a driver, identified by a major and minor number. /dev/null is character device 1:3 on every Linux system, so creating a file with that number gives the container a working /dev/null without exposing anything else.

If the container used the image directory directly, anything it wrote would change the image for every container after it. Running rm -rf / inside would destroy the image.

Docker avoids this with an overlay filesystem, which stacks directories on top of each other and presents them as one:.

The lower directory is the image, and it's never written to.

The upper directory starts empty and receives every write.

The merged directory is the combined view, and it's what the container uses as its root.

Sources indicate that reading a file returns the upper copy if one exists, otherwise the lower one. Writing a file from the lower layer copies it up first. Deleting one creates a marker in the upper layer that hides it. A real Docker image has many lower layers, one per build step, stacked the same way.

According to recent reports, the work directory is scratch space the kernel needs to make copy-up operations atomic. The cleanup deletes the upper layer, which makes every container start from the clean image, the same as docker run --rm.

It has been revealed that namespaces control what a container can see. Control groups control how much it can use. On cgroup v2, every cgroup is a directory under /sys/fs/cgroup, and we set its limits by writing to files in it:.

mkdir creates the cgroup, and the kernel fills the directory with control files. cpu.max of 50000 100000 lets the cgroup's processes run for 50 ms in every 100 ms period, which is half a CPU. memory.swap.max of 0 stops the container from escaping its memory limit by swapping.

Industry observers note that the usual way to put a process in a cgroup is to write its PID to the cgroup's cgroup.procs file after it starts. That leaves a window where the process is running without limits. run avoids it with UseCgroupFD, which passes the open cgroup directory to clone, so the kernel creates the child already inside the cgroup. Our box runtime has the core pieces, but it's missing almost everything that makes Docker safe and convenient to use:.

Networking: Docker creates a virtual Ethernet pair for each container, puts one end in the container's network namespace and the other on a bridge on the host, and uses NAT so containers can reach the outside world. box containers have no network at all.

It has been revealed that dropping privileges: the shell in box runs as full root. Docker drops most of root's capabilities, applies a seccomp profile that blocks more than 40 of the 300-plus system calls, and can map container root to an unprivileged host user with a user namespace.

Images: box uses a directory someone else unpacked. Docker pulls layered images from registries, verifies them by content hash, and stacks the layers with overlayfs.

Lifecycle: Docker runs containers in the background, keeps their logs, restarts them, and lets us exec into a running one, which joins its existing namespaces with the setns system call.

Docker's own architecture splits this work into layers. The docker CLI talks to dockerd, which hands containers to containerd, which manages their lifecycle and images. To actually start a container, containerd calls runc, which reads a JSON description of the container defined by the OCI runtime spec and does what box does: clone with namespace flags, pivot_root, mounts, cgroups, and finally exec.

runc is written in Go too, and now that we know these system calls, its source code is a great next read.

In this article, we learned that a container is just a Linux process, and built a small container runtime in Go using namespaces, pivot_root, overlay filesystems, and cgroups.

These pieces also explain a lot of everyday container behavior: why a container's PID 1 needs to handle signals, why exit code 137 means out of memory, why a container can't see host devices, and why changes inside a container disappear when it's removed.
