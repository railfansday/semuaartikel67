It has been revealed that your accessibility check in CI is green. axe-core ran, zero violations, and the badge in the README looks great. Your site can still fail WCAG 2.2.

Recent findings suggest that that isn't a bug in axe. WCAG 2.2 became a W3C Recommendation in October 2023. It added nine success criteria and dropped one (4.1.1 Parsing), and most of the latest ones can't be judged by reading the DOM. Deque mentioned as much when it shipped the first WCAG 2.2 support in axe-core 4.5: the target-size rule would probably be the only new-criterion rule they added, because the others can't be automated without a lot of false positives.

Sources indicate that so the rest is on you. This article covers the one criterion axe can check and three it can't (focus not obscured, dragging movements, accessible authentication), with Playwright tests you can drop into a project. I ran all of them against a small test page that fails every criterion on purpose, and against a fixed version of the same page. If you want a plain-language rundown of every change first, WCAG 2.2 vs 2.1 goes through them. Here I only care about what you can put in a pipeline.

Level A and AA are what most contracts and laws point at, so those are the ones that matter first. The AAA criteria are still worth knowing about.

Sources indicate that that's four AA criteria with something you can script, one of which axe already handles. The rest of this article goes through those four.

The AA rule is smaller than most people expect: a pointer target should be at least 24 by 24 CSS pixels, or sit far enough from its neighbours that a 24px circle centred on it wouldn't overlap another target or that target's own circle. There are exceptions, including inline links in a sentence, and targets whose size the browser controls.

Recent findings suggest that axe-core has a target-size rule for this. One catch: it isn't part of a default run. In my setup (axe-core 4.14.1 through @axe-core/playwright 4.14.0), a plain analyze() on the broken page reported nothing at all. The rule only indicated up once I asked for it:.

In a recent development, some context on how common the problem is. In the scan data behind my last SitePoint article, 34.5% of the 1,025 sites had controls below a stricter 44px threshold. That is a tougher standard than the 24px that AA asks for, so don't read it as "a third of sites fail 2.5.8". Plenty of those would pass. But it does show how many production sites ship tiny controls.
