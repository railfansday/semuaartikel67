In a recent development, you have a robot, a folder of demonstration data on the Hugging Face Hub, and a new task you want it to learn. Today that takes five separate tools: one to record new demonstrations, another to train, a third to test in simulation, custom code to deploy on hardware, and yet another to coordinate when you have more than one robot. The pieces work on their own. They don't talk to each other.

According to recent reports, strands Robots is an open source SDK from AWS (Apache 2.0) that gives you a robot, its simulation, and the LeRobot stack behind agent tools that you hand to a single Strands agent. The integration is deliberately thin: LeRobot's own scripts handle hardware recording and calibration, and Strands Robots comes in for the parts an agent actually orchestrates. A robot in simulation records LeRobotDatasets with LeRobot's own writer, in the same format LeRobot writes on hardware. A Policy loads LeRobot checkpoints in-process behind one interface, including ACT, SmolVLA, pi0, GR00T and MolmoAct2. A peer mesh fans the agent out to remote robots. The dataset format stays exactly as LeRobot wrote it; the agent loop is the glue.

This post walks you through five steps inside a single agent: build the agent over the robot's tools, record a demonstration as a LeRobotDataset in simulation, run a policy from the Hub on the same robot, deploy the same agent code to a physical SO-101 with one keyword argument change, and reach the robot over the Zenoh mesh. At the end, you can clone the working sample from GitHub and run it on your laptop in simulation. No hardware, no GPU, no Hugging Face credentials needed for the default path. The runnable companion to this post is the notebook notebooks/11_hub_to_hardware.ipynb.

It has been revealed that two design choices make this work. First, Robot("so101") is a robot in a simulated world by default (no hardware, no risk), and Robot("so101", port=...) is the same class driving a physical arm. The agent code is identical across both, and every command from the agent passes the robot's safety chain: a target outside a joint's range is refused, never clipped. Second, recording goes through LeRobot's own dataset writer on both the simulation path and hardware, so a dataset captured in MuJoCo and one captured from a physical SO-101 are in the same format.

Industry observers note that with the dataset on the Hub, the next step is to run a policy. A Hub repo id is a policy: Policy("/") loads a LeRobot checkpoint in-process with LeRobot's own loader. You hand it to the robot's tool by name, and the agent runs it the same way it would run any other policy:.

Industry observers note that under the hood, the agent calls the robot tool's run action with policy="act". The robot steps the simulation with the policy's action chunks, and every action passes the same safety chain as a command from the agent. norm= states the units the checkpoint was trained in, and the library checks it against the checkpoint's saved statistics before the first step, naming the joint and the fix if they disagree. The chain applies to the policy too: in one of our runs it stopped the checkpoint after 1.3 seconds, when it asked for the gripper 0.0002 rad past its range, and the robot refused the step instead of clipping it. To run inference on a separate GPU machine instead, serve the checkpoint with LeRobot's lerobot-policy-server and point the robot at it with Policy("zenoh://gpu-box:7447/").

It has been revealed that up to now we've driven one robot at a time. The mesh is how Strands Robots handles more than one. Picture five SO-101s running the same warehouse task in parallel, a humanoid coordinating with a mobile base, or an arm in another room that an agent on your laptop drives. All of those are mesh patterns. The mesh is built on Zenoh, an open source peer-to-peer protocol, and you don't manage IP addresses, write discovery code, or pick a broker; robots show up on the mesh the moment they're mounted, and the agent can talk to all of them at once.

A robot joins a mesh when you mount it, and the agent reaches every robot on the mesh through one tool, use_mesh:.

According to recent reports, the agent lists the devices on the mesh, reads each one's manifest, and invokes the same actions the robot's own tool has: observe, act, run, stop and estop. Use Mesh("iot://us-west-2") with the iot extra to route the same calls over AWS IoT Core for cross-network fleets; the agent code doesn't change.

In a recent development, safety goes with the robot, not the transport. An agent can always press e-stop, on one robot or with a broadcast to all of them, but it can never resume one: only a named operator can, with resume(approved_by=...). A plain zenoh:// mesh is one any machine on the network can join, so a real robot on it is observe-only until you give the lab certificates (python -m strands_robots.mesh ca and cert); simulated robots take commands on it freely.

The transport scales without touching agent code. On the LAN, Zenoh peers find each other with no broker. Across subnets, run a zenohd router with its own certificate, and for cloud fleets the iot:// mesh carries the same calls over AWS IoT Core with an X.509 certificate per robot.

According to recent reports, the code snippets shown in this setup represent a “hello world” example of setting up Strands Robots with HuggingFace. For more serious, production-ready use cases there are some important considerations owners should be aware of:.

Industry observers note that supplying untrusted data into agents can lead to prompt injection, where untrustworthy context is treated as LLM instructions. Given the actuation of these robots in physical space, this is an important risk to track. To mitigate this behavior, developers should be careful to feed the robots only data that comes from a trusted source. If not all input data can be trusted, developers should restrict the tools available to the agent to prevent the robots from making safety-critical actions.

A plain zenoh:// mesh, as in the snippets in this post, has no access control: any device on the same network can join it, and the peer id in a request is only a claim. That is why a real robot on it answers only describe, observe, stop and estop. For untrusted networks or production environments, give each machine a lab certificate (python -m strands_robots.mesh ca, then cert), so the mesh runs over mutual TLS and only machines with a certificate can reach a robot. On AWS IoT Core, give each robot its own X.509 certificate and an IoT policy limited to its own topics.

Sources indicate that on a real robot, operator= is the gate: one function answers every move a tool, the dashboard or the mesh asks for, and every policy run's blueprint, once, before anything moves. The agent's approval never comes from its own tool arguments, so a prompt-injection attempt that slips an approval into a command cannot bypass it. An agent can always press e-stop but can never release one, calibrate, record, push, or choose a policy address on the network, and it loads a Hub checkpoint by name only if the operator lists it in STRANDS_POLICY_REPOS.

Recent findings suggest that the integration's central design choice is that Strands Robots doesn't reimplement what LeRobot already provides. Calibration, the dataset format, and the policies stay upstream. Strands adds the agent tools, the safety chain and the mesh that make them composable from natural language.

According to recent reports, two consequences follow. For users, every dataset on the Hub is an asset an agent can extend, fine-tune from, and deploy against with no conversion step. For developers, simulation data and hardware data share a single file format, so training scripts written for one consume the other unchanged. The line between sim and real becomes a deployment detail, not an architectural divide.
