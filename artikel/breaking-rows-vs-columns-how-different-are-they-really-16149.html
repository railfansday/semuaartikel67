Breaking: Rows vs. Columns: How different are they, really?

It has been revealed that when we think about structured data, we generally think in terms of rows. Take this simple CSV file, which records some data about bike rides on a bike-sharing app in Latest York City:.

It has been revealed that data in this CSV file is organized into rows, where each row corresponds to a record of data. Each record here is one ride, or one "thing", with everything we know about it on one line. We tend to organize data like this almost everywhere: think of spreadsheets, JSON objects, C-style structs in an array, SQL tables, etc. This is because it matches how we think: one "thing", and all of the details of that "thing".

But not everything we ask of a database is limited to one record.

It has been revealed that if you run the bike-share service that produced the CSV file above, you'll eventually want to learn something from all the data it collects. This kind of work is called analytics. For example, which neighborhood is busiest on Monday and Friday mornings? Do people take longer rides on electric bikes than on classic ones? Observe how no single record can answer these questions. The answers come from the dataset as a whole, so the only way to get them is to look at all of the records.1.

Notice what these questions don't need, however. Finding the busiest neighborhood only needs the start_area and started_at columns, and comparing bike types only needs bike_type and duration_min. Each question may have to look at every row, but it only needs a few of the columns from each one. And a database that keeps each record's details together can't take advantage of that: to read two columns, it has to read all five. We may think in rows, but to answer questions like these quickly, we have to program in columns.

Programming in columns begins with how the data is stored, but that's only the start. Once data is stored by column, the way a database runs a query changes dramatically: how much data it reads, how many values it handles at a time, how many values the CPU can process with one instruction, how well the data compresses, etc.

This post will go over these changes, and by the end, you'll see just how much follows from the "simple" choice to store columns instead of rows.

Let's start with what doesn't change. Whether a database stores rows or columns, the table it shows you when you do SELECT * FROM rides; is the same. You create it with the same SQL, you query it with the same SQL, and you get the same answers. We can say that the two tables are logically equivalent.

Rows vs columns is a physical distinction rather than a logical one: the data represents the same thing, but how that data is actually arranged in memory and on disk is different.

Databases are named after the grouping they choose. A row store keeps each record's values next to each other, just like the CSV we started with. Postgres and MySQL, which we mentioned before, are both row stores. They're built for the small reads and writes behind an application, which is called online transaction processing (OLTP).2.

According to recent reports, A column store does the opposite: it takes every record apart and keeps each column's values next to each other instead.3 DuckDB and ClickHouse are examples of column stores. They're built for analytics, which is called online analytical processing (OLAP).4.

Industry observers note that let's do a fun exercise.5 These are the two SQL queries shown above. Which layout is better for executing each of them?

For the AVG query, computing it requires only the duration_min of every ride and nothing else. In the Columns layout, values are stored together in a single Vec, so the query can scan that one array without touching the other four. For Vec (the Rows layout), there is simply no way to read only the durations. Each duration is stored within a Ride, so the query has to read through every Ride and pass over the other four fields every time.

Note that the code can "ignore" those other fields, but the hardware cannot. A CPU doesn't fetch memory one value at a time: it will fetch fixed-size blocks called cache lines (which are 64 bytes on most machines6), fetching the whole line even when the program needs only a few bytes of it. A Ride is 48 bytes7 and duration_min is only 4 of them, so with the row layout, we have to fetch all 48 bytes to read those 4, which is 12x the amount that we actually need. The CPU can't skip any of these lines either because a Ride is smaller than a cache line, so every cache line of the array has a duration somewhere in it.

This diagram only indicates 8 rides for simplicity (which is why the duration_min line is half empty), but the factor of 12 doesn't depend on the size of the table. With one million rides, we might be fetching 48 MB vs 4 MB.

The second query goes the other way. SELECT * FROM rides WHERE ride_id = 1004 wants every field of a single ride, not just one. Once the database finds the record with that ride (probably via an index8), Vec has all of its fields next to each other, so reading all of them touches only one or two cache lines (it might overlap two cache lines).9 On the other hand, Columns has spread the same ride over five different arrays, so the query has to fetch at least five cache lines to put it back together. For this query, the Rows layout wins.

Industry observers note that now that we have a better idea of what we're working with, let's go a bit deeper into how we can speed up queries over columnar data! Analytical data processing is an active field of research spanning several decades, so we won't be able to go over every possible optimization. Nevertheless, the rest of this post will give a good overview of the techniques that most modern analytical database systems utilize.

In a recent development, the simplest way to run SELECT AVG(duration_min) FROM rides; is to visit one ride at a time: take a ride, add its duration, and repeat, dividing by the length of the column at the end. However, a column store doesn't necessarily have to execute this way. Since all of the durations sit in one contiguous array, it can process them in batches of a few thousand values, where each batch is small enough to stay in the CPU's cache.10 This is called vectorized execution.11.

According to recent reports, but why would a batch be any faster than one value at a time? To understand this, we first need to understand how a database execution engine actually runs these queries.12.

A database has to be able to run any query, so it builds and plans each one with general-purpose pieces called operators. For example, we might have an operator that reads a column, another that performs filters, another that computes a sum, and so on. If the operators pass each other one Ride at a time (this is called the Volcano model13), then for every single ride, the database has to figure out which operator runs next, which column it wants, and what type that column is. All of this bookkeeping and interpretation cost can easily take more time than the summation itself.14 With batches, we only pay for the bookkeeping once per batch instead of once per value, and the actual work turns into a tight loop over an array.

So why stop at a few thousand values, and not just process the entire column at once? Operators hand their results to each other, so a small batch of results can stay in the CPU's cache until the next operator picks it up. An operator result the size of an entire column generally cannot fit inside the CPU's cache, so the CPU would have to write it back out to main memory and then read it back in.

For our query, the work on each batch is a single loop:.

In addition to vectorized execution having better cache locality, we can speed up our execution of the query with data-parallel operations. Modern CPUs have instructions that operate on several values at once, called SIMD (single instruction, multiple data). They work best when the values are the same type and are contiguous in memory, which is exactly what a batch of a column is.

So when the compiler sees the for loop above, it can emit SIMD instructions on its own. This is a technique called autovectorization15 that is supported well in compiler backends such as LLVM.16.

In a recent development, with AVX-512 (which can load 512 bits at once), one vpaddq instruction adds 8 64-bit durations at once.17 Note that vpaddq doesn't add those 8 durations to each other. A 512-bit register has 8 slots of 64 bits, and each slot holds its own running sum: the first duration is added to the first slot, the second duration to the second slot, and so on. Only after the loop does the code add the slots together to get the final sum (the figure below leaves that last step out).

According to recent reports, note that the compiler keeps four registers of running sums (zmm0 to zmm3 in the assembly) instead of one. This is a separate optimization from SIMD called loop unrolling:18 the 8 slots in each register come from SIMD, and the four registers come from the compiler doing four steps of the loop in every pass. Together, every pass of the loop adds 4 × 8 = 32 durations.

In a recent development, note that autovectorization is not unique to sums. Much of the time executing a query (especially a relatively simple one) is spent in tight loops over batches like this one, and the compiler can vectorize many of them in the same way without anyone writing a single SIMD instruction by hand.

It has been revealed that so far, we've only looked at data that is already in memory. In most database systems, data lives on persistent storage (a disk, an SSD, or object storage like S3), and bringing it into memory is usually the bottleneck of query execution (in other words, queries are I/O bound). So the size of our data is very key: the fewer bytes a query has to read, the less time it spends waiting on I/O.

Recent findings suggest that the naive way to make the data smaller is to take each block of it and run it through a general-purpose compression algorithm.19 This kind of compression should be familiar to anyone who has ever dealt with zip files! It treats the data as just a major pile of bytes, and it doesn't care what those bytes actually mean, which is why it works on everything (including both rows and columns).

The problem is that this kind of compression is a "black box": once a block is compressed, the database can't see inside of it anymore. For example, if you wanted to read the one-millionth line of a zipped CSV file, there is no way to jump straight to that line, so you would have to unzip (decompress) everything that comes before it just to access a single line.20 The ability to read any one piece of the data without reading the rest of it is called random access, and this kind of compression is unable to support fast random access.

A database system will have the exact same problem with black-box compressed blocks of data: to read the duration of ride 1004, it has to decompress the entire block (potentially multiple blocks!) that the ride lives in.

Sources indicate that this is another place where columns help. The values in a column all have the same type, and they tend to be similar to each other, which means that a column compresses much better than a row does. We can already see this in our example above: start_area only has 3 distinct values, bike_type only has 2, and ride_id is always increasing.

More importantly, we don't actually need to use black-box compression. We can instead use lightweight encodings: simple schemes that compress the data while retaining the structure and the meaning of the values.21 Instead of turning a column into a big pile of bytes, a lightweight encoding takes advantage of one specific pattern in it (for example, a column with only a few distinct values, or a column of numbers that are all small) to store the same values in less space.

Recent findings suggest that retaining the structure means that we can keep random access. With most lightweight encodings, the database system can jump straight to the value that it wants without decoding everything around it.

Retaining the meaning helps as well. Lightweight encodings are "lighter weight" than black-box compression, but they aren't free, since decoding them still takes CPU time. However, because the encoded values still mean something, a query can often do its work directly on the encoded data without decoding it first, which skips much of that cost. This computation over compressed data is a form of "late materialization".22.

According to recent reports, this is exactly how we built Vortex, an open-source, extensible columnar file format and data processing library. It has a whole collection of lightweight encodings, and it can stack them on top of each other to make the data even smaller.

We started with data from a CSV file and one "simple" choice of storing data in rows vs columns. Yet we have seen just how much follows from that choice, as well as the consequences of choosing one or the other.23.

Those consequences are the reason that most database systems are built for either transactions or analytics, and not both.24 The way a database executes queries and the way it compresses data are both built on top of this one choice, so it isn't something that a system can just flip later. A column store's strength in serving analytical queries is exactly what makes it bad for reading and changing one record at a time, and the opposite is true for a row store.

Industry observers note that there is also a lot more to columnar data than what we can fit in a single introductory post. For example, we never talked about how a column store actually organizes its data on persistent storage,25 how it avoids reading data that a query doesn't need,26 how vectorized execution isn't the only way to run a query more efficiently,27 and we completely ignored writes and modifications to data!28 Each one of these topics is a whole area of active research. If you want to keep going, the CMU database courses are a great place to start, and all of their lectures are free to watch online.29.

In a recent development, people have tried to build one system that does both in the past (HTAP, or hybrid transactional/analytical processing), but those attempts generally didn't work out. Some newer systems seem to be bridging the gap, however. CedarDB, the commercial version of Umbra (a research system from TU Munich), runs transactions and analytics on just one engine and one copy of the data. Databricks' Lakebase keeps Postgres (a row store) as the engine for transactional queries, but its storage layer rewrites the same data into columnar formats in the background, allowing an analytical engine to query it. ↩︎.

Recent findings suggest that most formats split the table into large groups of rows and store the columns separately inside of each group (this is known as a "row group"). This idea goes back to PAX, from Weaving Relations for Cache Performance (VLDB 2001), and it's how Apache Parquet files work today. The most common trick is to keep "zone maps" of the minimum and maximum value of every block of data so that a query can completely skip the blocks that can't contain certain data. We wrote about this in Zone maps, or “queries go brrr”. ↩︎.
